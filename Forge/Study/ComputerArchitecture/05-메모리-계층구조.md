## 1. 지역성 원리 (Principle of Locality)

메모리 계층구조가 실제로 동작하는 이유는 **프로그램이 지역성을 보이기 때문**입니다.

### 1.1 시간 지역성 (Temporal Locality)
- **정의**: 최근에 접근한 데이터는 가까운 미래에 다시 접근될 가능성이 높다.
- **예시**: 루프 내 변수 `i`, 자주 호출되는 함수의 명령어
- **캐시 활용**: 한 번 로드한 데이터를 캐시에 유지 → 재접근 시 빠르게 서비스

### 1.2 공간 지역성 (Spatial Locality)
- **정의**: 최근에 접근한 데이터 근처의 데이터에도 곧 접근할 가능성이 높다.
- **예시**: 배열 순차 접근, 명령어 순차 실행
- **캐시 활용**: 블록(캐시 라인) 단위로 데이터를 로드 → 인접 데이터 미리 적재

```
for (int i = 0; i < N; i++) {
    sum += arr[i];   // arr[i] 접근 → arr[i+1], arr[i+2]... 도 캐시에 적재됨 (공간 지역성)
}                    // sum 변수는 루프마다 재사용 (시간 지역성)
```

> [!tip] 💡 면접 팁
> "캐시가 왜 효과적인가요?" → **지역성 원리** 때문입니다. 시간/공간 지역성 두 가지를 모두 설명하고 코드 예시를 드세요.

## 2. 메모리 계층구조 (Memory Hierarchy)

### 2.1 계층 피라미드

```
        ┌─────────────┐
        │  Registers  │  ← 가장 빠름, 가장 비쌈, 가장 작음
        ├─────────────┤
        │   L1 Cache  │
        ├─────────────┤
        │   L2 Cache  │
        ├─────────────┤
        │   L3 Cache  │
        ├─────────────┤
        │  Main RAM   │
        ├─────────────┤
        │ SSD / HDD   │  ← 가장 느림, 가장 저렴, 가장 큼
        └─────────────┘
```

### 2.2 계층별 비교표

| 계층 | 접근 시간 | 용량 | 비용($/GB) | 기술 |
|------|-----------|------|------------|------|
| Register | ~0.3 ns (1 cycle) | 수십 ~ 수백 B | — | SRAM (flip-flop) |
| L1 Cache | ~1 ns (3-5 cycles) | 32~64 KB | ~$10,000 | SRAM |
| L2 Cache | ~3-10 ns (10-30 cycles) | 256 KB ~ 1 MB | ~$1,000 | SRAM |
| L3 Cache | ~10-40 ns (30-100 cycles) | 4~64 MB | ~$100 | SRAM |
| Main Memory (DRAM) | ~50-100 ns | 4~256 GB | ~$5 | DRAM |
| SSD (NVMe) | ~100 μs | 256 GB ~ 8 TB | ~$0.15 | Flash |
| HDD | ~5-10 ms | 1~20 TB | ~$0.03 | Magnetic |

> [!note] 메모리 계층의 핵심 원칙
> - **상위 계층**: 빠르지만 작고 비싸다
> - **하위 계층**: 느리지만 크고 저렴하다
> - CPU는 항상 상위 계층에 먼저 접근하고, 없으면 아래로 내려간다 (**계층적 포함 관계**)

## 3. 캐시 (Cache)

### 3.1 기본 개념

캐시는 **CPU와 메인 메모리 사이의 소규모 고속 메모리**입니다.

- **Hit**: 요청한 데이터가 캐시에 있는 경우
- **Miss**: 요청한 데이터가 캐시에 없어 하위 계층에서 가져와야 하는 경우
- **Cache Line (Block)**: 캐시가 데이터를 가져오는 최소 단위 (보통 64 bytes)

### 3.2 Direct-Mapped Cache (직접 사상 캐시)

각 메모리 블록이 캐시 내 **정확히 하나의 위치**에만 매핑됩니다.

#### 주소 분해 (Address Decomposition)

$$\text{Physical Address} = \underbrace{\text{Tag}}_{\text{태그}} \mid \underbrace{\text{Index}}_{\text{인덱스}} \mid \underbrace{\text{Offset}}_{\text{블록 오프셋}}$$

- **Offset (블록 오프셋)**: 캐시 블록 내 바이트 위치
  - 블록 크기 = $2^k$ bytes → Offset = $k$ bits
- **Index (인덱스)**: 캐시의 어느 줄(set)에 저장할지 결정
  - 캐시 줄 수 = $2^n$ → Index = $n$ bits
- **Tag (태그)**: 같은 인덱스를 공유하는 여러 블록을 구분
  - Tag = 전체 주소 비트 - Index 비트 - Offset 비트

```
주소 (32 bit):
┌──────────────────────┬──────────────┬─────────────┐
│         Tag          │    Index     │   Offset    │
│  (32 - n - k) bits   │   n bits     │   k bits    │
└──────────────────────┴──────────────┴─────────────┘

예: 32-bit 주소, 캐시 1024줄, 블록 64 bytes
- Offset = log2(64) = 6 bits
- Index  = log2(1024) = 10 bits
- Tag    = 32 - 10 - 6 = 16 bits
```

#### Direct-Mapped 동작 방식

```
1. 주소에서 Index 추출 → 해당 캐시 줄 선택
2. Valid bit 확인 → 0이면 Miss
3. 캐시 줄의 Tag와 주소의 Tag 비교
   - 일치 → Hit! Offset으로 데이터 읽기
   - 불일치 → Miss! 메모리에서 블록 로드, Tag 갱신
```

> [!warning] Direct-Mapped의 단점
> **Conflict Miss**: 서로 다른 메모리 주소가 같은 인덱스를 공유할 때, 번갈아 접근하면 계속 미스 발생
> ```c
> // 캐시가 4 KB, 블록 64 B, Direct-Mapped라면
> // A[0]과 B[0]이 같은 캐시 줄에 매핑될 수 있음
> for (i = 0; i < N; i++)
>     C[i] = A[i] + B[i];  // A와 B가 캐시 충돌 → 성능 급격히 저하
> ```

### 3.3 Fully Associative Cache (완전 연관 캐시)

메모리 블록이 캐시 **어느 위치에나** 저장될 수 있습니다.

```
주소 분해:
┌──────────────────────────────────┬─────────────┐
│               Tag                │   Offset    │
│         (32 - k) bits            │   k bits    │
└──────────────────────────────────┴─────────────┘
(Index 없음 → 전체 캐시를 병렬 검색)
```

| 항목 | 설명 |
|------|------|
| Index 비트 | 없음 |
| 검색 방식 | 모든 캐시 줄을 병렬로 Tag 비교 (CAM, Content Addressable Memory) |
| 장점 | Conflict Miss 없음 |
| 단점 | 하드웨어 비용 매우 높음, 병렬 비교기 필요 |
| 용도 | TLB, 소용량 고성능 캐시 |

### 3.4 N-way Set-Associative Cache (N-웨이 집합 연관 캐시)

Direct-Mapped와 Fully Associative의 **절충안**입니다.

- 캐시를 여러 **Set(집합)**으로 나누고
- 각 Set은 **N개의 Way(줄)**로 구성
- 메모리 블록은 인덱스로 Set을 결정하고, 그 Set의 N개 Way 중 어디에나 저장 가능

```
주소 분해:
┌──────────────────────┬──────────────┬─────────────┐
│         Tag          │  Set Index   │   Offset    │
│  (32 - s - k) bits   │   s bits     │   k bits    │
└──────────────────────┴──────────────┴─────────────┘

Set 수 = 전체 줄 수 / N = 2^s
```

```
예: 32 KB 캐시, 8-way, 64 B 블록
- 전체 줄 수 = 32768 / 64 = 512줄
- Set 수     = 512 / 8 = 64 Sets
- Offset     = log2(64) = 6 bits
- Set Index  = log2(64) = 6 bits
- Tag        = 32 - 6 - 6 = 20 bits
```

#### 세 가지 구조 비교

| 항목 | Direct-Mapped | N-way SA | Fully Associative |
|------|--------------|----------|--------------------|
| 유연성 | 낮음 (고정 1위치) | 중간 (N위치) | 높음 (어디든) |
| Conflict Miss | 많음 | 적음 | 없음 |
| 하드웨어 복잡도 | 낮음 | 중간 | 높음 |
| 검색 속도 | 빠름 | 중간 | 느림 (병렬 비교) |
| 대표 용도 | 간단한 L1 | L1/L2/L3 | TLB |

> [!tip] 💡 면접 팁
> "N-way SA에서 N이 커지면 어떻게 되나요?"
> - N → 전체 줄 수: Fully Associative에 수렴
> - N = 1: Direct-Mapped와 동일
> - 실제 CPU는 보통 L1은 4~8-way, L2/L3는 8~16-way 사용

## 4. 캐시 교체 정책 (Replacement Policy)

N-way SA 및 Fully Associative에서 **어느 블록을 교체할지** 결정합니다.

### 4.1 LRU (Least Recently Used)
- **정책**: 가장 오랫동안 사용되지 않은 블록을 교체
- **장점**: 시간 지역성 활용 → 실제 성능 우수
- **단점**: N이 클수록 추적 오버헤드 증가 (각 Way의 최근 사용 순위 기록 필요)
- **구현**: 실제로는 근사 LRU (Pseudo-LRU) 사용

### 4.2 Random (무작위)
- **정책**: 무작위로 교체 대상 선택
- **장점**: 구현 단순, 하드웨어 비용 낮음
- **단점**: 운이 나쁘면 자주 사용하는 블록이 교체될 수 있음
- **실제**: 고성능 캐시에서 LRU 근사 대신 사용되기도 함

### 4.3 FIFO (First In First Out)
- **정책**: 가장 먼저 적재된 블록을 교체
- **장점**: 구현 간단
- **단점**: 오래된 블록이 여전히 자주 사용될 수 있음 (Belady's Anomaly 가능)

| 정책 | 성능 | 구현 복잡도 | 비고 |
|------|------|-------------|------|
| LRU | 최우수 | 높음 | 대부분의 L1/L2 캐시 |
| Random | 중간 | 낮음 | ARM 프로세서 등 |
| FIFO | 낮음 | 낮음 | 거의 사용 안 함 |
| Optimal (Belady) | 이론적 최적 | 불가능 (미래 예측 필요) | 성능 상한선 측정용 |

## 5. 쓰기 정책 (Write Policy)

### 5.1 Write-Through vs Write-Back

#### Write-Through (즉시 쓰기)
- **동작**: 캐시에 쓸 때 **동시에 하위 메모리에도 즉시** 반영
- **장점**: 캐시와 메모리 항상 일관성 유지, 구현 단순
- **단점**: 모든 쓰기가 느린 메모리 접근을 유발 → 성능 저하
- **완화책**: **Write Buffer** — 메모리 쓰기를 큐에 쌓아 비동기 처리

#### Write-Back (나중 쓰기)
- **동작**: 캐시에만 쓰고, 블록이 교체될 때 **한 번만** 메모리에 반영
- **Dirty bit**: 블록이 수정되었는지 표시 (1이면 교체 시 메모리에 써야 함)
- **장점**: 쓰기 트래픽 대폭 감소 → 성능 우수
- **단점**: 캐시와 메모리 불일치 발생, 복잡한 일관성 관리 필요

```
Write-Through:
CPU write → Cache 갱신 → Memory 즉시 갱신

Write-Back:
CPU write → Cache 갱신 (Dirty bit = 1)
...블록 교체 시...
           → Memory 갱신 (Dirty bit = 1인 경우만)
```

### 5.2 Write-Allocate vs No-Write-Allocate

**Write Miss** (쓰려는 블록이 캐시에 없을 때) 처리 방식:

#### Write-Allocate (쓰기 할당)
- Miss 시 블록을 캐시로 먼저 로드한 뒤 캐시에 씀
- **Write-Back과 주로 함께 사용**
- 이후 같은 블록에 대한 읽기/쓰기가 캐시에서 처리됨

#### No-Write-Allocate (쓰기 비할당)
- Miss 시 캐시에 올리지 않고 직접 하위 메모리에 씀
- **Write-Through와 주로 함께 사용**
- 쓰기 전용 데이터에 적합

| 조합 | 설명 | 주로 사용 |
|------|------|-----------|
| Write-Through + No-Write-Allocate | 쓰기는 항상 메모리로, 미스 시 캐시 적재 안 함 | L1 간단 구현 |
| Write-Back + Write-Allocate | 쓰기는 캐시만, 미스 시 블록 로드 후 캐시에 씀 | L1/L2 고성능 |

> [!tip] 💡 면접 팁
> "Write-Back의 Write-Allocate는 왜 함께 쓰나요?"
> Write-Back에서 No-Write-Allocate를 사용하면, 미스 시 메모리에 직접 쓴 후 나중에 읽기 미스가 날 때 다시 메모리에서 가져와야 하는 비효율이 생깁니다.
> Write-Allocate는 처음 쓸 때 블록 전체를 로드하므로, 이후 읽기/쓰기 모두 캐시에서 처리됩니다.

## 6. 3C 미스 (Three C's of Cache Misses)

모든 캐시 미스는 세 가지 원인 중 하나에 속합니다.

### 6.1 Compulsory Miss (강제 미스 / Cold Miss)
- **원인**: 데이터를 **처음** 접근할 때 (캐시가 비어 있음)
- **특징**: 캐시 크기와 무관, 피할 수 없음
- **해결**: **Prefetching** (미리 가져오기) — 사용 전에 하드웨어/소프트웨어가 미리 로드
- **특이**: 무한히 큰 캐시에서도 발생

### 6.2 Capacity Miss (용량 미스)
- **원인**: 캐시 크기가 **작업 집합(Working Set)**보다 작아서 블록이 교체된 후 다시 필요
- **특징**: Fully Associative에서도 발생 (구조와 무관, 순수 용량 문제)
- **해결**: 캐시 용량 증가, 알고리즘 최적화로 Working Set 축소

### 6.3 Conflict Miss (충돌 미스)
- **원인**: 여러 블록이 **같은 캐시 줄**에 매핑되어 서로를 교체 (Direct-Mapped에서 특히 심함)
- **특징**: Fully Associative에서는 발생하지 않음
- **해결**: Associativity 증가 (N-way SA), 데이터 패딩으로 주소 충돌 회피

```
3C Miss 요약:
┌─────────────────┬──────────────────────────────┬──────────────────────┐
│ 미스 종류        │ 원인                          │ 해결책               │
├─────────────────┼──────────────────────────────┼──────────────────────┤
│ Compulsory      │ 첫 접근 (cold)                │ Prefetching          │
│ Capacity        │ 캐시 너무 작음                 │ 캐시 크기 증가       │
│ Conflict        │ 같은 인덱스에 블록 충돌        │ Associativity 증가   │
└─────────────────┴──────────────────────────────┴──────────────────────┘
```

> [!info] 4번째 C: Coherence Miss
> 멀티프로세서 환경에서 **다른 프로세서의 쓰기**로 인해 캐시 블록이 무효화될 때 발생.
> 단일 프로세서 분석에서는 보통 3C만 다룸.

## 7. 캐시 성능 (Cache Performance)

### 7.1 AMAT (Average Memory Access Time)

$$\boxed{AMAT = \text{Hit Time} + \text{Miss Rate} \times \text{Miss Penalty}}$$

- **Hit Time**: 캐시 히트 시 접근 시간 (보통 L1 접근 시간)
- **Miss Rate**: 전체 접근 중 미스 비율 $= \frac{\text{미스 횟수}}{\text{전체 접근 횟수}}$
- **Miss Penalty**: 미스 발생 시 하위 계층에서 블록을 가져오는 시간

**예시**: L1 Hit Time = 2 cycles, Miss Rate = 5%, Miss Penalty = 100 cycles
$$AMAT = 2 + 0.05 \times 100 = 2 + 5 = 7 \text{ cycles}$$

### 7.2 다단계 캐시 AMAT

L1, L2 두 단계 캐시가 있는 경우:

$$AMAT = T_{L1} + MR_{L1} \times (T_{L2} + MR_{L2} \times T_{MEM})$$

여기서:
- $T_{L1}$: L1 Hit Time
- $MR_{L1}$: L1 Local Miss Rate
- $T_{L2}$: L2 Hit Time
- $MR_{L2}$: L2 Local Miss Rate (L1 미스 중 L2도 미스인 비율)
- $T_{MEM}$: 메인 메모리 접근 시간

**예시**:
- $T_{L1} = 1$ cycle, $MR_{L1} = 5\%$
- $T_{L2} = 10$ cycles, $MR_{L2} = 20\%$
- $T_{MEM} = 200$ cycles

$$AMAT = 1 + 0.05 \times (10 + 0.20 \times 200)$$
$$= 1 + 0.05 \times (10 + 40)$$
$$= 1 + 0.05 \times 50 = 1 + 2.5 = 3.5 \text{ cycles}$$

### 7.3 Local Miss Rate vs Global Miss Rate

| 용어 | 정의 | 예시 (L2 기준) |
|------|------|---------------|
| **Local Miss Rate** | 해당 캐시에 들어온 접근 중 미스 비율 | L2에 온 접근 중 L2 미스 비율 |
| **Global Miss Rate** | CPU에서 나간 전체 접근 중 미스 비율 | CPU 전체 접근 중 L2 미스 비율 = $MR_{L1} \times MR_{L2,local}$ |

$$MR_{L2,global} = MR_{L1} \times MR_{L2,local}$$

> [!tip] 💡 면접 팁
> "L2 Local Miss Rate 10%, L1 Miss Rate 5%이면, L2 Global Miss Rate는?"
> $MR_{L2,global} = 0.05 \times 0.10 = 0.5\%$
> AMAT 계산 시 Global Miss Rate 사용에 주의하세요.

### 7.4 AMAT 감소 전략

| 전략 | 목표 지표 | 방법 |
|------|-----------|------|
| 작은 L1 캐시 | Hit Time 감소 | 더 작고 빠른 L1 (직접 접근 경로 단축) |
| Prefetching | Miss Rate 감소 | 사용 전 미리 하위 계층에서 로드 |
| 높은 Associativity | Miss Rate 감소 | Conflict Miss 감소 |
| 큰 블록 크기 | Miss Rate 감소 | 공간 지역성 활용 (단, 너무 크면 역효과) |
| 다단계 캐시 | Miss Penalty 감소 | L2, L3가 L1 미스를 일부 흡수 |
| Critical Word First | Miss Penalty 감소 | 필요한 워드부터 먼저 전송 |

## 8. 가상 메모리 (Virtual Memory)

### 8.1 개요 및 목적

| 목적 | 설명 |
|------|------|
| **추상화** | 각 프로세스에 독립적인 연속 주소 공간 제공 |
| **보호** | 프로세스 간 메모리 침범 방지 |
| **용량 확장** | 물리 메모리보다 큰 주소 공간 사용 가능 (디스크 활용) |
| **공유** | 여러 프로세스가 물리 페이지를 안전하게 공유 |

### 8.2 페이지와 프레임

- **Page**: 가상 주소 공간의 고정 크기 블록 (보통 4 KB = $2^{12}$ bytes)
- **Frame (Page Frame)**: 물리 메모리의 고정 크기 블록 (페이지와 동일 크기)
- **Page Table**: 가상 페이지 번호 → 물리 프레임 번호 매핑 테이블

```
가상 주소 (VA):
┌──────────────────────────┬────────────────────┐
│   Virtual Page Number    │    Page Offset     │
│        (VPN)             │       (PO)         │
│   (64 - 12 = 52 bits)    │     12 bits        │
└──────────────────────────┴────────────────────┘

물리 주소 (PA):
┌──────────────────────────┬────────────────────┐
│  Physical Frame Number   │    Page Offset     │
│        (PFN)             │       (PO)         │
└──────────────────────────┴────────────────────┘
```

### 8.3 페이지 테이블 엔트리 (PTE) 구조

$$PTE = \underbrace{PFN}_{\text{물리 프레임 번호}} \mid \underbrace{V}_{\text{Valid}} \mid \underbrace{D}_{\text{Dirty}} \mid \underbrace{R}_{\text{Reference}} \mid \underbrace{Prot}_{\text{보호 비트}}$$

| 필드 | 크기 | 의미 |
|------|------|------|
| PFN (Physical Frame Number) | 대부분의 비트 | 매핑된 물리 프레임 번호 |
| Valid (V) | 1 bit | 페이지가 물리 메모리에 있는지 여부 |
| Dirty (D) | 1 bit | 페이지가 수정되었는지 (스왑 아웃 시 필요) |
| Reference (R) | 1 bit | 최근 접근 여부 (교체 정책 결정에 사용) |
| Protection | 2-3 bits | 읽기/쓰기/실행 권한 |
| User/Kernel | 1 bit | 접근 가능한 권한 수준 |

### 8.4 단일 레벨 페이지 테이블

```
가상 주소 → VPN으로 페이지 테이블 인덱싱 → PFN 획득 → 물리 주소 생성

Page Table:
Index | Valid | PFN   | Dirty | Prot
  0   |   1   | 0x3A0 |   0   | RW
  1   |   0   |  ---  |   -   | --   ← Invalid (페이지 폴트 발생)
  2   |   1   | 0x1B2 |   1   | RO
  ...
```

**문제점**: 32-bit 주소 공간, 4 KB 페이지 → $2^{32}/2^{12} = 2^{20} = 1M$ 엔트리 → PTE 4 bytes 가정 시 4 MB 테이블이 **프로세스마다** 필요

### 8.5 다단계 페이지 테이블 (Multi-Level Page Table)

#### 2단계 페이지 테이블 (32-bit 예시)

```
가상 주소 (32 bit):
┌───────────────┬───────────────┬──────────────┐
│  L1 Index     │  L2 Index     │  Offset      │
│   10 bits     │   10 bits     │  12 bits     │
└───────────────┴───────────────┴──────────────┘

CR3 레지스터 → L1 Page Directory → L2 Page Table → Physical Frame
```

**장점**: 사용하는 주소 범위에 대해서만 L2 테이블 생성 → **희소 주소 공간** 효율적 처리

#### 4단계 페이지 테이블 (x86-64, 48-bit VA)

```
48-bit 가상 주소:
┌──────┬──────┬──────┬──────┬──────────────┐
│ PML4 │  PDP │  PD  │  PT  │    Offset    │
│ 9bit │ 9bit │ 9bit │ 9bit │   12 bits    │
└──────┴──────┴──────┴──────┴──────────────┘

CR3 → PML4 Table → PDP Table → PD Table → PT → Physical Page
```

각 레벨은 $2^9 = 512$ 엔트리 × 8 bytes = 4 KB (딱 한 페이지)

### 8.6 페이지 폴트 (Page Fault) 처리 과정

```
1. CPU가 가상 주소에 접근
2. TLB 조회 → Miss
3. 페이지 테이블 워크 → PTE의 Valid bit = 0
4. Page Fault Exception 발생 → OS Page Fault Handler 호출
5. OS가 디스크(Swap Space)에서 해당 페이지를 물리 메모리로 로드
   - 빈 프레임이 없으면 → 교체 정책(LRU 등)으로 희생 페이지 선택
   - 희생 페이지 Dirty → 디스크에 먼저 쓰기
6. PTE 갱신 (Valid = 1, PFN 설정)
7. TLB 갱신
8. Faulting Instruction 재실행
```

> [!warning] 페이지 폴트 비용
> 디스크 I/O가 수반되므로 수십 ms 소요 → CPU 성능에 치명적
> 페이지 폴트를 최소화하는 것이 성능의 핵심

## 9. TLB (Translation Lookaside Buffer)

### 9.1 TLB 개요

페이지 테이블이 메모리에 있어 주소 변환 시 **추가 메모리 접근이 필요**합니다.
TLB는 **최근 사용한 VPN→PFN 매핑을 캐싱**하는 하드웨어 구조입니다.

```
특징:
- 용량: 32~1024 엔트리 (매우 작음)
- 구조: 대부분 Fully Associative (소용량이므로 가능)
- 접근 시간: 0.5~1 cycle (캐시와 병렬 접근하기도 함)
- Hit Rate: 보통 99%+ (지역성 덕분)
```

### 9.2 TLB 엔트리 구조

| 필드 | 설명 |
|------|------|
| VPN | 가상 페이지 번호 (태그 역할) |
| PFN | 물리 프레임 번호 |
| Valid | 엔트리 유효 여부 |
| Dirty | 페이지 수정 여부 |
| ASID | Address Space ID (프로세스 구분) |
| Protection | 접근 권한 |

### 9.3 ASID (Address Space Identifier)

- **문제**: 컨텍스트 스위치 시 TLB를 모두 무효화(flush)해야 함 → TLB Miss 급증
- **해결**: TLB 엔트리에 ASID 저장 → 다른 프로세스의 엔트리를 구분하여 함께 공존
- ASID는 보통 8~16 bit (MIPS: 8 bit = 256 프로세스 동시 TLB 유지)

```
TLB 엔트리 (ASID 포함):
┌──────┬──────────┬──────────┬───┬───┬──────┐
│ ASID │   VPN    │   PFN    │ V │ D │ Prot │
└──────┴──────────┴──────────┴───┴───┴──────┘
```

### 9.4 TLB의 4가지 시나리오

| 시나리오 | TLB | Page Table | 결과 |
|---------|-----|-----------|------|
| TLB Hit | Hit | — | 가장 빠름, 1 cycle로 변환 완료 |
| TLB Miss, Page Hit | Miss | Valid=1 | TLB 갱신 후 접근 (+수 cycles) |
| TLB Miss, Page Fault | Miss | Valid=0 | OS가 페이지 로드, TLB/PT 갱신 후 재실행 (ms 단위) |
| Protection Fault | — | — | 접근 권한 위반 → OS Segmentation Fault |

```
TLB Miss 처리 방식:
1. Hardware-managed TLB (x86): 하드웨어가 자동으로 페이지 테이블 워크
2. Software-managed TLB (MIPS): OS가 TLB Miss Handler 실행하여 TLB 갱신
```

### 9.5 가상 주소 → 물리 주소 전체 변환 과정

```
가상 주소 (VA) 입력
        │
        ▼
   TLB 조회 (VPN 검색)
        │
   ┌────┴────┐
  Hit       Miss
   │          │
   │          ▼
   │   페이지 테이블 워크 (메모리 접근)
   │          │
   │     ┌────┴────┐
   │   Valid     Invalid
   │     │          │
   │     │        Page Fault
   │     │        (OS 처리)
   │     ▼
   │   TLB 갱신 (새 엔트리 삽입)
   │          │
   └──────────┘
              │
              ▼
         PFN 획득
              │
              ▼
   PA = PFN | Page Offset
              │
              ▼
     물리 메모리(캐시) 접근
```

### 9.6 VIPT vs PIPT 캐시

캐시 접근 시 **어떤 주소로 인덱싱/태깅**하는지에 따라 구분됩니다.

#### PIPT (Physically Indexed, Physically Tagged)
- 물리 주소로 인덱싱하고 태깅
- **장점**: 별칭(aliasing) 문제 없음, 일관성 단순
- **단점**: TLB 변환 완료 후 캐시 접근 → 직렬화 → 느림
- **용도**: L2, L3 캐시

#### VIPT (Virtually Indexed, Physically Tagged)
- 가상 주소로 인덱싱, 물리 주소(Tag)로 태깅
- **장점**: TLB 변환과 캐시 인덱싱을 병렬로 수행 → 빠름
- **단점**: 가상 주소 Aliasing 문제 발생 가능
  - **Aliasing**: 서로 다른 가상 주소가 같은 물리 주소를 가리킬 때 서로 다른 캐시 인덱스를 가질 수 있음
  - **해결**: 캐시 크기 ≤ 페이지 크기 × Associativity 이면 Aliasing 자동 방지
    - 예: 4 KB 페이지, 4-way SA, 캐시 ≤ 16 KB 이면 Offset + Set Index ≤ 12 bits → 가상/물리 주소 동일 → 안전
- **용도**: L1 캐시 (속도가 최우선)

| 항목 | VIPT | PIPT |
|------|------|------|
| 인덱싱 | 가상 주소 | 물리 주소 |
| 태깅 | 물리 주소 | 물리 주소 |
| TLB와 병렬 가능 | 가능 | 불가능 |
| Aliasing 문제 | 있음 (조건부 해결) | 없음 |
| 사용 계층 | L1 | L2, L3 |

> [!tip] 💡 면접 팁
> "L1 캐시에서 VIPT를 쓰는 이유는?"
> TLB 변환과 캐시 인덱싱을 병렬로 수행하여 L1 Hit Latency를 1 cycle 줄이기 위해서입니다.
> Aliasing 문제는 캐시 크기를 페이지 크기 × Way 수 이하로 제한하면 해결됩니다.

## 10. 캐시 일관성 (Cache Coherence)

### 10.1 문제 정의

멀티프로세서 시스템에서 각 코어가 자체 캐시를 가질 때, **동일 메모리 위치**에 대해 **서로 다른 값**이 캐시에 존재할 수 있습니다.

```
Core 0 Cache: addr X = 5
Core 1 Cache: addr X = 7  ← 누가 맞는 값?
Memory:       addr X = 5
```

### 10.2 MESI 프로토콜

각 캐시 라인이 네 가지 상태 중 하나를 가집니다:

| 상태 | 의미 | 읽기 | 쓰기 |
|------|------|------|------|
| **M**odified | 이 캐시만 가짐, 메모리와 다름 (Dirty) | 캐시에서 바로 | 캐시에서 바로 |
| **E**xclusive | 이 캐시만 가짐, 메모리와 동일 (Clean) | 캐시에서 바로 | M으로 전이 |
| **S**hared | 여러 캐시가 공유, 메모리와 동일 | 캐시에서 바로 | Invalidate 후 M |
| **I**nvalid | 유효하지 않음 | Miss 발생 | Miss 발생 |

```
상태 전이 다이어그램:

       읽기 (다른 캐시 없음)
I ──────────────────────────→ E
│                               │
│ 읽기 (다른 캐시 있음)          │ 쓰기
│                               ↓
└──────────────────────────→ S → M
                         ↑       │
                         │       │ 다른 캐시의 읽기
                         └───────┘ (Intervention)
```

**Snoop 기반**: 모든 캐시가 버스를 감청(snoop)하여 다른 캐시의 접근을 감지
**Directory 기반**: 중앙 디렉터리가 어느 캐시가 어떤 블록을 보유하는지 추적 (확장성 좋음)

> [!info] False Sharing
> **정의**: 서로 다른 프로세서가 **같은 캐시 라인의 서로 다른 변수**를 접근할 때, 불필요한 캐시 무효화가 반복됨.
> ```c
> struct Data {
>     int a;  // Core 0가 접근
>     int b;  // Core 1이 접근
>     // a와 b가 같은 캐시 라인에 있으면 False Sharing 발생!
> };
> // 해결: 패딩으로 서로 다른 캐시 라인에 배치
> struct Data {
>     int a;
>     char padding[60];  // 캐시 라인(64 B) 채우기
>     int b;
> };
> ```

## 11. 면접 Q&A (20개+)

> [!tip] 💡 면접 빈출 질문 모음

**Q1. 캐시가 왜 필요한가요?**
CPU와 메인 메모리 간의 속도 차이(~100배 이상)를 줄이기 위해서입니다. 프로그램의 지역성(시간/공간)을 활용하여 자주 접근하는 데이터를 빠른 캐시에 보관함으로써 평균 접근 시간(AMAT)을 대폭 줄입니다.

---

**Q2. Direct-Mapped vs Set-Associative vs Fully Associative의 차이는?**
- DM: 각 블록이 캐시 내 하나의 위치에만 매핑. 빠르지만 Conflict Miss 많음.
- SA: 각 블록이 Set 내 N개 위치 중 어디에나 저장. 유연성과 복잡도의 균형.
- FA: 어느 위치에나 저장. Conflict Miss 없지만 병렬 비교 하드웨어 필요로 비쌈.
연관도(Associativity)가 높을수록 Miss Rate 감소, Hit Time 증가.

---

**Q3. Write-Through와 Write-Back 중 어떤 것이 더 좋은가요?**
성능 면에서는 Write-Back이 우수합니다. 메모리 쓰기 트래픽이 적고, Dirty 블록만 교체 시 메모리에 씁니다. 하지만 구현이 복잡하고 일관성 관리가 필요합니다. Write-Through는 구현이 단순하고 디버그하기 쉽지만, 모든 쓰기가 느린 메모리 접근을 유발합니다.

---

**Q4. 3C 미스 각각에 대한 해결책은?**
- Compulsory: Prefetching (소프트웨어/하드웨어 스트림 프리패처)
- Capacity: 캐시 크기 증가, 알고리즘 최적화로 Working Set 축소
- Conflict: Associativity 증가, 데이터 패딩으로 주소 분산

---

**Q5. AMAT를 계산하는 방법은? 다단계 캐시에서는?**
- 단일: $AMAT = HitTime + MissRate \times MissPenalty$
- 다단계: $AMAT = T_{L1} + MR_{L1} \times (T_{L2} + MR_{L2,local} \times T_{MEM})$
Local Miss Rate는 해당 캐시 접근 중 미스 비율, Global Miss Rate는 전체 CPU 접근 중 미스 비율.

---

**Q6. TLB가 없으면 어떻게 되나요?**
모든 메모리 접근마다 페이지 테이블을 조회해야 하므로, 다단계 페이지 테이블에서는 실제 접근당 4~5번의 추가 메모리 접근이 필요합니다. TLB 없이는 실용적인 성능을 달성할 수 없습니다.

---

**Q7. 페이지 폴트가 발생하면 어떤 순서로 처리되나요?**
1. 하드웨어가 페이지 폴트 예외 발생
2. OS의 페이지 폴트 핸들러 실행
3. 해당 페이지를 디스크에서 물리 메모리로 로드
4. 빈 프레임 없으면 교체 정책으로 희생 페이지 선택, Dirty이면 스왑 아웃
5. PTE 갱신 (Valid=1, PFN 설정)
6. TLB 갱신 후 Faulting Instruction 재실행

---

**Q8. ASID가 없으면 컨텍스트 스위치 시 무슨 문제가 있나요?**
컨텍스트 스위치 시 다른 프로세스의 TLB 엔트리가 현재 프로세스에 의해 사용될 수 있어, 보안 문제와 잘못된 주소 변환이 발생합니다. 따라서 ASID 없이는 컨텍스트 스위치마다 TLB를 전부 무효화(flush)해야 하며, 이는 성능 저하로 이어집니다.

---

**Q9. 캐시 친화적인 코드를 작성하는 방법은?**
1. **행 우선 접근(Row-Major)**: C/C++은 행 우선 저장 → `arr[i][j]` 순서로 접근
2. **루프 순서 최적화**: 중첩 루프에서 내부 루프가 연속 메모리를 접근하도록
3. **데이터 지역성**: 자주 함께 사용하는 데이터를 구조체로 묶기 (AoS vs SoA 선택)
4. **Working Set 축소**: 캐시 크기에 맞게 데이터 처리 단위 분할 (Loop Blocking/Tiling)
5. **False Sharing 방지**: 멀티스레드에서 패딩으로 서로 다른 캐시 라인 사용

---

**Q10. False Sharing이란 무엇이고 어떻게 해결하나요?**
서로 다른 스레드/코어가 동일한 캐시 라인 내의 서로 다른 변수에 쓸 때, 불필요한 캐시 무효화가 반복되는 현상입니다. 해결책: 각 변수를 캐시 라인 크기(64 B) 단위로 패딩하거나, `alignas(64)`로 정렬합니다.

---

**Q11. VIPT 캐시에서 Aliasing 문제는 언제 발생하고 어떻게 해결하나요?**
두 가상 주소가 같은 물리 주소를 가리키지만 다른 캐시 인덱스를 가질 때 발생합니다.
해결: 캐시 크기 ≤ 페이지 크기 × Associativity 조건을 유지하면, 인덱스 비트가 페이지 오프셋 내에 포함되어 가상 주소와 물리 주소가 동일하게 됩니다. (예: 4 KB 페이지, 4-way, ≤ 16 KB 캐시)

---

**Q12. 페이지 크기를 크게 하면 어떤 장단점이 있나요?**
- 장점: 페이지 테이블 크기 감소, TLB Coverage 증가, 디스크 I/O 효율 향상
- 단점: **내부 단편화(Internal Fragmentation)** 증가, 페이지 폴트당 로드 시간 증가
- 실제: OS는 보통 4 KB를 기본으로, 대용량 메모리 워크로드에는 Huge Page(2 MB, 1 GB)를 옵션으로 제공

---

**Q13. 멀티레벨 페이지 테이블의 장점은?**
사용하지 않는 가상 주소 범위에 대해 하위 레벨 테이블을 생성하지 않아도 됩니다. 일반 프로세스는 전체 64-bit 공간 중 극히 일부만 사용하므로, 페이지 테이블 메모리를 크게 절약할 수 있습니다 (희소 주소 공간 효율적 표현).

---

**Q14. 캐시 블록 크기를 크게 하면 어떻게 되나요?**
- 장점: 공간 지역성 더 잘 활용, Miss Rate 감소 (순차 접근 패턴)
- 단점: 전송 시간 증가 (Miss Penalty 증가), 캐시 라인 수 감소 → Conflict Miss 증가, 불필요한 데이터까지 로드 (랜덤 접근 패턴에서 오히려 비효율)
- 최적: 대부분의 시스템에서 64 bytes가 최적점

---

**Q15. TLB Shootdown이란?**
한 CPU 코어가 페이지 매핑을 변경(mmap/munmap 등)할 때, 다른 모든 코어의 TLB에서 해당 엔트리를 무효화해야 하는 작업입니다. 모든 코어에 IPI(Inter-Processor Interrupt)를 보내 TLB flush를 요청하며, 규모가 클수록 성능 오버헤드가 큽니다.

---

**Q16. Prefetching이란 무엇이고 어떤 종류가 있나요?**
미래에 필요할 데이터를 미리 하위 메모리 계층에서 캐시로 로드하는 기법입니다.
- **하드웨어 Prefetcher**: 스트라이드 패턴 감지하여 자동으로 다음 블록 로드
- **소프트웨어 Prefetch**: `__builtin_prefetch()` 같은 컴파일러/프로그래머 힌트
- 효과: Compulsory Miss의 Miss Penalty를 숨김 (Hit Time으로 전환)
- 주의: 과도한 Prefetch는 캐시 오염(Cache Pollution) 유발

---

**Q17. Write Buffer는 무엇인가요?**
Write-Through 캐시에서 CPU가 매 쓰기마다 느린 메모리 접근을 기다리지 않도록, 쓰기 요청을 임시 저장하는 작은 큐입니다. CPU는 버퍼에만 쓰고 바로 다음 작업으로 진행하며, 버퍼가 비동기적으로 메모리를 갱신합니다.

---

**Q18. Belady's Anomaly란?**
FIFO 교체 정책에서 캐시 크기를 늘렸는데 오히려 Miss Rate가 증가하는 현상입니다. LRU와 같은 Stack Property를 가진 알고리즘에서는 발생하지 않습니다.

---

**Q19. 소프트웨어 관리 TLB vs 하드웨어 관리 TLB의 차이는?**
- **하드웨어 관리 (x86)**: TLB Miss 시 하드웨어가 자동으로 페이지 테이블 워크. OS는 페이지 테이블 형식을 하드웨어가 요구하는 대로 유지해야 함.
- **소프트웨어 관리 (MIPS)**: TLB Miss 시 OS의 TLB Miss Handler가 실행. 페이지 테이블 형식을 OS가 자유롭게 정의 가능. 유연하지만 핸들러 실행 오버헤드 존재.

---

**Q20. Loop Tiling(Blocking)이란 무엇이고 왜 캐시 성능을 개선하나요?**
대용량 데이터를 캐시에 맞는 작은 블록(타일)으로 나누어 처리하는 최적화 기법입니다. 한 타일을 완전히 처리하는 동안 해당 데이터가 캐시에 유지되어, 다음 반복에서 재사용 시 캐시 히트가 발생합니다. Working Set을 캐시 크기 내로 유지하여 Capacity Miss를 줄입니다.
```c
// 행렬 곱 Loop Blocking 예시
for (ii = 0; ii < N; ii += B)
  for (jj = 0; jj < N; jj += B)
    for (kk = 0; kk < N; kk += B)
      for (i = ii; i < min(ii+B, N); i++)
        for (j = jj; j < min(jj+B, N); j++)
          for (k = kk; k < min(kk+B, N); k++)
            C[i][j] += A[i][k] * B[k][j];
// B = 캐시에 맞는 블록 크기 선택 (예: sqrt(L1_cache_size / 3 / sizeof(double)))
```

**조건**: 32-bit 주소, 8 KB Direct-Mapped 캐시, 블록 크기 32 bytes

**풀이**:

```
32-bit 주소:
┌──────────────────────┬──────────────┬───────────┐
│     Tag (19 bits)    │ Index(8 bits)│Offset(5 b)│
│     [31:13]          │   [12:5]     │  [4:0]    │
└──────────────────────┴──────────────┴───────────┘
```

### 문제 3: AMAT 계산

**조건**:
- L1: Hit Time = 1 cycle, Miss Rate = 8%
- L2: Hit Time = 12 cycles, Miss Rate = 50% (Local)
- Memory: Access Time = 150 cycles

**풀이**:
$$AMAT = T_{L1} + MR_{L1} \times (T_{L2} + MR_{L2,local} \times T_{MEM})$$
$$= 1 + 0.08 \times (12 + 0.50 \times 150)$$
$$= 1 + 0.08 \times (12 + 75)$$
$$= 1 + 0.08 \times 87$$
$$= 1 + 6.96 = 7.96 \text{ cycles}$$

**L2 Global Miss Rate** = $0.08 \times 0.50 = 4\%$

### 문제 4: 캐시 용량 계산

**조건**: 2-way Set-Associative, 32 Sets, 블록 크기 64 bytes

**풀이**:
- 전체 줄 수 = 2-way × 32 Sets = 64줄
- 캐시 데이터 용량 = 64 × 64 = 4096 = **4 KB**
- 각 줄의 오버헤드 (30-bit 주소 가정):
  - Offset = $\log_2(64) = 6$ bits
  - Set Index = $\log_2(32) = 5$ bits
  - Tag = $30 - 6 - 5 = 19$ bits + Valid(1) + Dirty(1) = 21 bits per Way
  - 총 오버헤드 = 64줄 × 21 bits = 1344 bits ≈ 168 bytes

### 문제 11: AMAT 최적화

**조건**: 현재 시스템

- 현재 AMAT = 2 + 0.10 × 80 = **10 cycles**

두 가지 개선안 중 어느 것이 더 효과적인가?

**안 A가 더 효과적** (7 cycles < 8 cycles)

### 문제 12: 코드 패턴 분석 (캐시 친화성)

다음 두 행렬 전치 코드 중 캐시 친화적인 것은?

```c
// 코드 A (naive)
for (i = 0; i < N; i++)
    for (j = 0; j < N; j++)
        B[j][i] = A[i][j];  // B는 열 방향 쓰기 → 비친화적

// 코드 B (blocked)
for (ii = 0; ii < N; ii += B)
    for (jj = 0; jj < N; jj += B)
        for (i = ii; i < ii+B; i++)
            for (j = jj; j < jj+B; j++)
                B[j][i] = A[i][j];
```

**분석**:
- 코드 A: A는 행 방향(친화적), B는 열 방향(비친화적) → B 쓰기마다 캐시 미스
- 코드 B: 블록 단위로 처리하면 B의 블록도 캐시에 남아있어 재사용 → Miss 감소
- Blocking 크기 B는 $B^2 \leq$ 캐시 크기 / 2 (A, B 동시 보유) 로 설정

### 문제 14: Write-Back Dirty 비용 계산

**조건**:
- L1 캐시: 64줄, 블록 64 bytes, Write-Back
- Dirty Rate: 30% (교체 시 30%의 블록이 Dirty)
- Miss Penalty (Clean block): 50 cycles
- Extra Write-Back Penalty (Dirty block): +50 cycles (메모리에 다시 써야 함)

평균 미스 패널티를 계산하세요.

**풀이**:
$$\text{Avg Miss Penalty} = P_{clean} \times (1 - D) + P_{dirty} \times D$$
$$= 50 \times 0.70 + (50 + 50) \times 0.30$$
$$= 35 + 30 = 65 \text{ cycles}$$

**해결책**: Victim Cache 또는 Write Buffer로 Write-Back 지연 처리

### 문제 15: 종합 문제 — 메모리 시스템 설계

**요구사항**: 32-bit 시스템, AMAT ≤ 5 cycles 달성
- 메인 메모리: 100 cycles
- L1 제약: Hit Time = 1 cycle, 최대 크기 32 KB

**풀이 과정**:

1) L1만 있을 때 최대 허용 Miss Rate:
$$5 = 1 + MR_{L1} \times 100 \Rightarrow MR_{L1} \leq 4\%$$
→ 32 KB L1으로 4% 달성 어려움 (일반적으로 8~10%)

2) L2 추가 (Hit Time = 10 cycles, Miss Rate = 20%):
$$AMAT = 1 + MR_{L1} \times (10 + 0.20 \times 100)$$
$$= 1 + MR_{L1} \times 30$$
$$MR_{L1} \leq \frac{5-1}{30} = 13.3\%$$
→ 32 KB L1으로 달성 가능 (일반적 L1 Miss Rate ~5~10%)

3) 실제 AMAT 추정 ($MR_{L1}$ = 8%):
$$AMAT = 1 + 0.08 \times 30 = 1 + 2.4 = 3.4 \text{ cycles}$$

**결론**: L1(32KB) + L2(적절한 크기, 10 cycle) 구성으로 AMAT ≤ 5 cycles 달성 가능

## 13. 공식 요약표

### 핵심 공식

| 공식 | 표현 |
|------|------|
| AMAT (단일 캐시) | $HitTime + MissRate \times MissPenalty$ |
| AMAT (2단계) | $T_{L1} + MR_{L1}(T_{L2} + MR_{L2} \times T_{MEM})$ |
| Global Miss Rate | $MR_{L1} \times MR_{L2,local}$ |
| Offset bits | $\log_2(\text{Block Size})$ |
| Index bits | $\log_2(\text{Number of Sets})$ |
| Tag bits | $\text{Addr bits} - \text{Index bits} - \text{Offset bits}$ |
| Set 수 | $\text{Total Lines} / N\text{-way}$ |
| 캐시 총 용량 | $\text{Sets} \times N \times \text{Block Size}$ |
| 페이지 수 | $2^{\text{VA bits}} / \text{Page Size}$ |
| PFN 비트 수 | $\log_2(\text{Physical Memory} / \text{Page Size})$ |

### 주소 분해 치트시트

```
Direct-Mapped:    [  Tag  |  Index  |  Offset  ]
N-way SA:         [  Tag  | Set Idx |  Offset  ]
Fully Assoc:      [       Tag       |  Offset  ]
Virtual Addr:     [       VPN       |  PO      ]
Physical Addr:    [       PFN       |  PO      ]
```

## 14. 메모리 계층 치트시트

```
┌─────────────────────────────────────────────────────────────────┐
│                    메모리 계층 치트시트                           │
├──────────────┬──────────┬────────────┬──────────────────────────┤
│   계층        │ 접근시간  │   용량     │  관리 주체               │
├──────────────┼──────────┼────────────┼──────────────────────────┤
│ Registers    │ 0.3 ns   │ < 1 KB     │ 컴파일러                 │
│ L1 Cache     │ 1 ns     │ 32-64 KB   │ 하드웨어                 │
│ L2 Cache     │ 5 ns     │ 256KB-4MB  │ 하드웨어                 │
│ L3 Cache     │ 20 ns    │ 4-64 MB    │ 하드웨어                 │
│ Main Memory  │ 80 ns    │ 4-256 GB   │ OS + 하드웨어            │
│ SSD          │ 100 μs   │ < 8 TB     │ OS                       │
│ HDD          │ 10 ms    │ < 20 TB    │ OS                       │
└──────────────┴──────────┴────────────┴──────────────────────────┘

캐시 구조 비교:
┌──────────────┬──────────────┬────────────────┬──────────────────┐
│              │ Direct-Mapped│ N-way SA       │ Fully Assoc.     │
├──────────────┼──────────────┼────────────────┼──────────────────┤
│ Index 비트   │ log2(Lines)  │ log2(Sets)     │ 없음             │
│ Conflict Miss│ 많음         │ 적음           │ 없음             │
│ 하드웨어 비용│ 낮음         │ 중간           │ 높음             │
│ 주요 용도    │ 단순 L1      │ L1/L2/L3       │ TLB              │
└──────────────┴──────────────┴────────────────┴──────────────────┘

3C 미스:
┌──────────────┬──────────────────────────┬──────────────────────┐
│ 종류          │ 원인                     │ 해결책               │
├──────────────┼──────────────────────────┼──────────────────────┤
│ Compulsory   │ 첫 접근 (cold)            │ Prefetching          │
│ Capacity     │ 캐시 크기 < Working Set   │ 캐시 증설, 알고리즘  │
│ Conflict     │ 같은 인덱스 충돌          │ Associativity 증가   │
└──────────────┴──────────────────────────┴──────────────────────┘

쓰기 정책 조합:
┌───────────────────────────────────────────────────────────────┐
│ Write-Through + No-Write-Allocate: 단순, 항상 메모리 접근      │
│ Write-Back + Write-Allocate: 고성능, 복잡한 일관성 관리        │
└───────────────────────────────────────────────────────────────┘

가상 메모리 변환:
VA → [TLB 조회] → Hit → PFN → PA → [캐시 접근]
             → Miss → [PT Walk] → Valid → TLB 갱신 → PFN
                               → Invalid → Page Fault → OS
```
