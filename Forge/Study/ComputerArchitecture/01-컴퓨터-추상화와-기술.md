# Chapter 1: 컴퓨터 추상화와 기술 (Computer Abstractions and Technology)

## 1. 컴퓨터의 8대 아이디어 (Eight Great Ideas)

> [!tip] 면접 빈출
> 8대 아이디어는 단순 암기보다 각 아이디어가 **현대 컴퓨터 설계에 어떻게 적용되는지** 연결해서 설명할 수 있어야 합니다.

| # | 아이디어 | 설명 |
|---|----------|------|
| 1 | **무어의 법칙을 위한 설계** (Design for Moore's Law) | 집적도는 2년마다 2배 → 미래 기술 수준에 맞춰 설계 |
| 2 | **추상화로 복잡성 감소** (Use Abstraction to Simplify Design) | 하위 구현을 숨기고 단순한 인터페이스 제공 |
| 3 | **자주 쓰이는 것을 빠르게** (Make the Common Case Fast) | 드문 케이스보다 일반 케이스 최적화 (Amdahl's Law 기반) |
| 4 | **병렬성으로 성능 향상** (Performance via Parallelism) | 여러 작업을 동시에 수행 |
| 5 | **파이프라이닝으로 성능 향상** (Performance via Pipelining) | 명령어 실행을 겹쳐서 처리량 향상 |
| 6 | **예측으로 성능 향상** (Performance via Prediction) | 추측 실행(Speculative Execution)으로 지연 시간 감소 |
| 7 | **메모리 계층구조** (Hierarchy of Memories) | 레지스터 → 캐시 → DRAM → 디스크 계층으로 속도/용량 균형 |
| 8 | **중복성으로 신뢰성 향상** (Dependability via Redundancy) | 오류 감지·복구를 위한 중복 설계 (ECC, RAID 등) |

## 2. 추상화 계층 (Abstraction Layers)

컴퓨터는 여러 추상화 계층으로 구성되며, 각 계층은 하위 계층의 세부사항을 숨깁니다.

```
┌─────────────────────────────┐
│   응용 소프트웨어 (Application Software)   │  ← 사용자가 보는 계층
├─────────────────────────────┤
│   시스템 소프트웨어 (System Software)      │
│   - OS: I/O, 메모리 관리, 멀티태스킹       │
│   - 컴파일러: 고급 언어 → 기계어 변환       │
├─────────────────────────────┤
│   하드웨어 (Hardware)                     │
│   - 프로세서, 메모리, I/O 장치             │
├─────────────────────────────┤
│   논리 게이트 (Logic Gates)               │
├─────────────────────────────┤
│   트랜지스터 (Transistors)                │  ← 물리적 계층
└─────────────────────────────┘
```

### 핵심 인터페이스: ISA (Instruction Set Architecture)

- **ISA**: 하드웨어와 소프트웨어 사이의 추상화 경계
- 소프트웨어는 ISA를 통해 하드웨어와 소통
- RISC-V, x86, ARM 모두 ISA의 구현체
- **ABI (Application Binary Interface)**: ISA + OS 인터페이스 = 바이너리 이식성 보장

> [!warning] 추상화의 트레이드오프
> 추상화는 복잡성을 감소시키지만, 하위 계층의 세부사항을 무시하면 성능 최적화 기회를 놓칠 수 있습니다. 예: 캐시 미스, 메모리 정렬 문제.

## 3. 성능 지표 (Performance Metrics)

### 3.1 실행 시간과 처리량 (Response Time & Throughput)

| 지표 | 정의 | 관점 |
|------|------|------|
| **응답 시간 (Response Time)** | 작업 시작부터 완료까지 걸리는 시간 | 개인 사용자 |
| **처리량 (Throughput)** | 단위 시간당 완료되는 작업 수 | 서버/데이터센터 |

> [!example] 트레이드오프 예시
> CPU를 더 빠른 것으로 교체 → 응답 시간 감소 + 처리량 증가 (둘 다 개선)
> 프로세서 추가 → 처리량만 증가 (응답 시간은 동일할 수 있음)

### 3.2 성능 정의

$$\text{Performance} = \frac{1}{\text{Execution Time}}$$

컴퓨터 X가 Y보다 n배 빠르다:

$$\frac{\text{Performance}_X}{\text{Performance}_Y} = \frac{\text{Execution Time}_Y}{\text{Execution Time}_X} = n$$

### 3.3 CPU 시간 (CPU Time)

$$\text{CPU Time} = \text{IC} \times \text{CPI} \times \text{Clock Period} = \frac{\text{IC} \times \text{CPI}}{\text{Clock Rate}}$$

| 변수 | 의미 | 영향 요인 |
|------|------|----------|
| **IC** (Instruction Count) | 실행된 명령어 수 | ISA, 컴파일러, 알고리즘 |
| **CPI** (Cycles Per Instruction) | 명령어당 평균 클럭 사이클 수 | CPU 구조, 명령어 종류 |
| **Clock Period** | 1 클럭 사이클 시간 (= 1/Clock Rate) | 하드웨어 기술 |

> [!tip] 핵심 통찰
> 이 세 변수는 **독립적으로 최적화**할 수 있지만, 하나를 개선하면 다른 것이 악화될 수 있습니다.
> - 컴파일러 최적화: IC 감소, but CPI 증가 가능 (복잡한 명령어 사용)
> - 클럭 속도 증가: Clock Period 감소, but CPI 증가 가능 (파이프라인 위험)

### 3.4 평균 CPI

여러 종류의 명령어가 있을 때:

$$\text{CPI} = \sum_{i=1}^{n} \left( \text{CPI}_i \times \frac{\text{IC}_i}{\text{IC}} \right)$$

## 4. Amdahl's Law (암달의 법칙)

> [!warning] 면접 최빈출 — 반드시 공식과 한계 모두 설명 가능해야 합니다.

### 4.1 공식

$$\text{Speedup}_{\text{overall}} = \frac{1}{(1 - f) + \frac{f}{s}}$$

- $f$: 개선된 부분의 전체 실행 시간 비율 (0 ~ 1)
- $s$: 개선된 부분의 속도 향상 배율

또는 실행 시간 기준:

$$T_{\text{new}} = T_{\text{old}} \times \left[ (1 - f) + \frac{f}{s} \right]$$

### 4.2 핵심 함의

$$\lim_{s \to \infty} \text{Speedup} = \frac{1}{1 - f}$$

아무리 한 부분을 빠르게 해도, **개선하지 않은 나머지 부분**이 성능의 상한을 결정합니다.

> [!example] 예제 1: 기본 Amdahl's Law 계산
> **문제**: 프로그램 실행 시간의 40%가 부동소수점 연산이다. FPU를 5배 빠르게 했을 때 전체 속도 향상은?
>
> **풀이**:
> $$\text{Speedup} = \frac{1}{(1 - 0.4) + \frac{0.4}{5}} = \frac{1}{0.6 + 0.08} = \frac{1}{0.68} \approx 1.47$$
>
> **결론**: FPU를 5배 빠르게 해도 전체는 약 1.47배만 빨라진다.

> [!example] 예제 2: 최대 속도 향상 한계
> **문제**: 위 예제에서 FPU를 무한히 빠르게 한다면?
>
> **풀이**:
> $$\text{Speedup}_{\max} = \frac{1}{1 - 0.4} = \frac{1}{0.6} \approx 1.67$$
>
> **결론**: 아무리 FPU를 개선해도 1.67배가 이론적 상한.

### 4.3 Amdahl's Law의 역설

"**자주 쓰이는 것을 빠르게** (Make the Common Case Fast)"의 수학적 근거입니다.

- 드물게 실행되는 부분(1%)을 100배 빨리해도 전체 속도 향상은 미미
- 자주 실행되는 부분(90%)을 2배 빨리하는 것이 훨씬 효과적

## 5. MIPS와 한계점 (MIPS as a Performance Metric)

### 5.1 MIPS 정의

$$\text{MIPS} = \frac{\text{IC}}{\text{Execution Time} \times 10^6} = \frac{\text{Clock Rate}}{\text{CPI} \times 10^6}$$

- Million Instructions Per Second

### 5.2 MIPS의 한계 (왜 MIPS는 신뢰할 수 없는가?)

> [!warning] MIPS는 잘못된 성능 지표
> 면접에서 MIPS의 문제점을 구체적으로 설명할 수 있어야 합니다.

1. **ISA 간 비교 불가**: x86의 1 instruction ≠ RISC-V의 1 instruction (명령어 복잡도 차이)
2. **CPI 무시**: 명령어 수가 많아도 CPI가 작으면 더 빠를 수 있음
3. **프로그램 의존성**: 같은 CPU라도 프로그램에 따라 MIPS 값이 달라짐
4. **실제 작업량 미반영**: 실제 얼마나 많은 계산을 했는지와 무관

## 6. 전력 장벽 (Power Wall)

### 6.1 동적 전력 소비 (Dynamic Power)

$$P_{\text{dynamic}} \propto C \times V^2 \times f$$

- $C$: 스위칭되는 커패시턴스 (트랜지스터 수에 비례)
- $V$: 공급 전압 (Voltage)
- $f$: 스위칭 주파수 (Clock Frequency)

### 6.2 왜 클럭 속도가 멈췄나?

- 더 많은 트랜지스터 → $C$ 증가
- 클럭 증가 → $f$ 증가
- 전압을 줄이면 → 트랜지스터 동작 마진 감소, 정적 누설 전류(Static Leakage) 증가
- **결론**: 2004년경 ~4GHz에서 단일 코어 클럭 속도 증가가 사실상 정지

### 6.3 해결책: 멀티코어 (Multicore)

> [!tip] 전력 장벽 → 멀티코어 전환의 흐름
> 클럭 속도 증가 대신 코어 수를 늘려서 처리량을 향상.
> 단, 소프트웨어가 병렬화되지 않으면 성능 이점 없음 (Amdahl's Law 적용).

$$P_{\text{2 cores at half freq}} = 2 \times C \times V^2 \times \frac{f}{2} = C \times V^2 \times f$$

동일한 전력으로 이론상 2배의 처리량 가능 (단, 소프트웨어 병렬화 필요).

## 7. 무어의 법칙과 현재 상황 (Moore's Law)

### 7.1 원래 정의

> **Gordon Moore (1965)**: 집적 회로의 트랜지스터 수는 약 **2년마다 2배**씩 증가한다.

### 7.2 현재 상황 (2020년대)

| 항목 | 과거 (1990~2005) | 현재 (2020년대) |
|------|-----------------|----------------|
| 트랜지스터 수 증가 | 무어의 법칙 유효 | 여전히 증가하나 속도 둔화 |
| 단일 코어 성능 | 연 50% 향상 | 연 ~3~5% 향상 |
| 클럭 속도 | 지속 증가 | ~3~5GHz에서 정체 |
| 전압 스케일링 | Dennard Scaling 유효 | 2004년경 한계 도달 |

> [!warning] Dennard Scaling의 종료
> 트랜지스터가 작아져도 전압을 같이 줄여 전력 밀도를 유지하던 법칙(Dennard Scaling)이 2004년경 종료됨 → 전력 장벽의 근본 원인.

## 8. 벤치마크 (Benchmarks)

### 8.1 SPEC CPU

- **Standard Performance Evaluation Corporation**
- 실제 애플리케이션 기반 벤치마크 스위트
- `SPEC CPU2017`: 정수 연산(SPECrate2017_int) + 부동소수점(SPECrate2017_fp)

### 8.2 SPEC CPU 점수 계산

$$\text{SPEC Ratio} = \frac{\text{Reference Time}}{\text{Execution Time on target}}$$

$$\text{SPEC Score} = \sqrt[n]{\prod_{i=1}^{n} \text{SPEC Ratio}_i} \quad \text{(기하평균)}$$

> [!tip] 왜 기하평균인가?
> 산술평균은 큰 값에 편향되지만, 기하평균은 비율(ratio)을 공정하게 평균화합니다. 성능 비율 평균에는 기하평균이 올바른 방법입니다.

### 8.3 벤치마크의 함정 (Benchmark Traps)

- **SPECmarks 게임**: 컴파일러를 벤치마크에 맞게 최적화
- **Waterfall effect**: 특정 벤치마크만 잘 되는 CPU 설계
- **대표성 부재**: 실제 워크로드와 다를 수 있음

## 9. 면접 빈출 질문 + 모범 답변

### Q1. CPU Time 공식에서 IC, CPI, Clock Rate를 각각 무엇이 결정하나요?

**A.** IC(Instruction Count)는 알고리즘과 컴파일러 최적화, ISA의 표현력이 결정합니다. CPI(Cycles Per Instruction)는 CPU 마이크로아키텍처 설계(파이프라인 깊이, 캐시 구조, 분기 예측)가 결정합니다. Clock Rate는 반도체 공정 기술과 회로 설계가 결정합니다. 세 요소는 독립적으로 최적화할 수 있지만 서로 트레이드오프가 있습니다. 예를 들어 클럭을 높이면 파이프라인이 깊어져 CPI가 증가할 수 있습니다.

---

### Q2. Amdahl's Law란 무엇이고, 현실에서 어떤 의미를 가지나요?

**A.** Amdahl's Law는 시스템 일부를 개선할 때 전체 성능 향상의 상한을 나타내는 법칙입니다. 공식은 $\text{Speedup} = 1 / [(1-f) + f/s]$로, 개선 비율 $f$와 개선 배율 $s$로 표현됩니다. 핵심 교훈은 병렬화하지 못한 순차 부분(1-f)이 전체 성능의 상한을 결정한다는 점입니다. 멀티코어 시대에 특히 중요하며, 코어를 아무리 늘려도 순차 실행 구간 때문에 선형 속도 향상은 불가능합니다. 따라서 "자주 쓰이는 것을 빠르게" 하는 설계 원칙의 수학적 근거가 됩니다.

---

### Q3. MIPS가 왜 신뢰할 수 없는 성능 지표인가요?

**A.** MIPS(Million Instructions Per Second)는 초당 실행 명령어 수만 측정하므로 세 가지 근본적인 문제가 있습니다. 첫째, ISA가 다르면 명령어 하나의 작업량이 다르므로 CISC와 RISC 간 직접 비교가 불가합니다. 둘째, 같은 CPU라도 프로그램의 명령어 혼합(instruction mix)에 따라 MIPS 값이 달라집니다. 셋째, 클럭 속도가 높고 CPI도 높은 CPU가 클럭은 낮지만 CPI도 낮은 CPU보다 MIPS는 높아도 실제로는 느릴 수 있습니다. 따라서 실제 실행 시간(Execution Time)이나 SPEC 벤치마크가 더 신뢰할 수 있는 지표입니다.

---

### Q4. 전력 장벽(Power Wall)이 발생한 원인과 업계의 대응은?

**A.** 전력 소비는 $P \propto C \times V^2 \times f$로, 클럭 주파수와 전압의 제곱에 비례합니다. 2004년경 Dennard Scaling이 무너지면서 트랜지스터를 작게 만들어도 전압을 줄이지 못하게 되었고, 클럭을 높이면 열 밀도가 급증하여 냉각이 불가능해졌습니다. 업계는 단일 코어 속도 대신 멀티코어, 전용 가속기(GPU, NPU, DSP), 저전력 설계로 대응했습니다. 소프트웨어 입장에서는 더 이상 단일 스레드 성능의 자동 향상을 기대할 수 없으며, 명시적인 병렬 프로그래밍이 필요합니다.

---

### Q5. 추상화(Abstraction)가 컴퓨터 시스템에서 왜 중요한가요?

**A.** 추상화는 복잡한 하위 구현을 단순한 인터페이스 뒤에 숨겨 각 계층이 독립적으로 발전할 수 있게 합니다. ISA가 대표적 예로, 하드웨어는 Intel에서 AMD로 바뀌어도 동일한 x86 바이너리가 동작합니다. OS는 다양한 하드웨어를 추상화하여 응용 프로그램에 균일한 인터페이스를 제공합니다. 단점은 추상화 경계를 넘는 최적화가 어려워진다는 것으로, 예를 들어 캐시 친화적 코드 작성에는 메모리 계층 지식이 필요합니다. 결국 추상화는 생산성과 최적화 가능성 사이의 트레이드오프입니다.

---

### Q6. 응답 시간(Response Time)과 처리량(Throughput)의 차이와 각각 중요한 상황은?

**A.** 응답 시간은 단일 작업의 완료까지 걸리는 시간이고, 처리량은 단위 시간당 완료되는 작업 수입니다. 인터랙티브 시스템(게임, UI)에서는 응답 시간이 사용자 경험을 결정하므로 핵심입니다. 반면 데이터센터나 배치 처리 시스템에서는 처리량이 비용 효율성을 결정합니다. 프로세서를 추가하면 처리량은 증가하지만 단일 작업의 응답 시간은 개선되지 않을 수 있습니다. 두 지표는 종종 상충하며, 시스템의 사용 목적에 따라 최적화 목표를 명확히 해야 합니다.

---

### Q7. 무어의 법칙은 아직도 유효한가요?

**A.** 트랜지스터 수 자체는 여전히 증가하고 있어 좁은 의미의 무어의 법칙은 유지되고 있습니다. 그러나 단일 스레드 성능 향상 속도는 크게 둔화되었고, Dennard Scaling 붕괴로 클럭 속도 증가는 사실상 멈췄습니다. 업계는 3D 적층 메모리, Gate-All-Around 트랜지스터, 이종 집적(Chiplet) 등 새로운 기술로 대응 중입니다. 소프트웨어 개발자는 더 이상 "다음 세대 하드웨어가 자동으로 내 코드를 빠르게 해줄 것"이라고 기대할 수 없습니다. 대신 도메인 특화 아키텍처(DSA)와 소프트웨어 병렬화가 성능 향상의 주된 경로입니다.

---

### Q8. 기하평균(Geometric Mean)을 벤치마크 집계에 쓰는 이유는?

**A.** 벤치마크 점수는 절대 시간이 아닌 기준 시스템 대비 **비율(ratio)**로 표현됩니다. 비율 데이터는 산술평균으로 집계하면 큰 값에 편향되는 문제가 있습니다. 기하평균은 비율의 곱의 n제곱근이므로, 각 비율을 공정하게 반영합니다. 예를 들어 A 벤치마크에서 2배 빠르고 B에서 0.5배라면 산술평균은 1.25이지만 기하평균은 1로, 실제 같은 성능을 올바르게 반영합니다. 따라서 SPEC CPU는 기하평균으로 최종 점수를 계산합니다.

---

### Q9. "Make the Common Case Fast"의 원칙을 실제 예시로 설명하세요.

**A.** 이 원칙은 드문 케이스를 완벽히 처리하는 것보다 자주 발생하는 케이스를 빠르게 만드는 것이 전체 성능에 더 유리하다는 것입니다. 캐시(Cache)가 대표적 예로, 모든 데이터를 DRAM에 두는 대신 자주 쓰는 데이터를 빠른 SRAM 캐시에 보관합니다. RISC 명령어 설계도 마찬가지로, 복잡한 명령어 대신 자주 쓰이는 단순 명령어를 빠르게 실행하도록 설계합니다. 분기 예측(Branch Prediction)도 "분기가 taken일 가능성이 높다"는 패턴을 학습해 자주 발생하는 케이스를 미리 처리합니다. Amdahl's Law가 이 원칙의 수학적 근거입니다.

---

### Q10. CPU Time과 Wall Clock Time의 차이는 무엇인가요?

**A.** CPU Time은 프로그램이 실제로 CPU를 점유한 시간만 측정하며, I/O 대기나 다른 프로세스가 CPU를 쓰는 시간은 제외됩니다. Wall Clock Time(Elapsed Time)은 사용자가 체감하는 실제 경과 시간으로, I/O, 메모리 접근, OS 오버헤드, 타 프로세스 대기 시간을 모두 포함합니다. CPU 성능 평가에는 CPU Time이 더 공정한 지표이나, 사용자 경험 측면에서는 Wall Clock Time이 중요합니다. 멀티스레드 프로그램에서는 CPU Time이 Wall Clock Time보다 클 수 있습니다 (여러 코어를 동시에 사용하면 총 CPU 사용량이 경과 시간보다 많음).

## 10. 연습 문제

### 문제 1 — CPU Time 기본 계산

**문제**: 프로그램이 $5 \times 10^9$개의 명령어를 실행한다. CPU의 클럭 속도는 2GHz이고 평균 CPI는 2.0이다. CPU Time을 구하시오.

**풀이**:

$$\text{CPU Time} = \frac{\text{IC} \times \text{CPI}}{\text{Clock Rate}} = \frac{5 \times 10^9 \times 2.0}{2 \times 10^9} = \frac{10^{10}}{2 \times 10^9} = 5 \text{ 초}$$

**정답**: 5초

---

### 문제 2 — CPI 비교로 CPU 성능 비교

**문제**: 두 CPU A, B가 있다. 같은 프로그램에 대해:
- CPU A: 클럭 2GHz, CPI = 2.0
- CPU B: 클럭 3GHz, CPI = 3.0

어느 CPU가 더 빠른가? (IC는 동일하다고 가정)

**풀이**:

$$\text{CPU Time}_A = \frac{\text{IC} \times 2.0}{2 \times 10^9} = \frac{\text{IC}}{10^9}$$

$$\text{CPU Time}_B = \frac{\text{IC} \times 3.0}{3 \times 10^9} = \frac{\text{IC}}{10^9}$$

**정답**: 두 CPU의 성능은 동일하다. 클럭 속도만으로 성능을 판단할 수 없음을 보여주는 예시.

---

### 문제 3 — 평균 CPI 계산

**문제**: 프로그램이 다음과 같은 명령어 구성을 갖는다:

| 명령어 타입 | CPI | 비율 |
|------------|-----|------|
| ALU | 1 | 40% |
| Load | 3 | 30% |
| Store | 2 | 15% |
| Branch | 2 | 15% |

평균 CPI를 구하시오.

**풀이**:

$$\text{CPI} = (1 \times 0.4) + (3 \times 0.3) + (2 \times 0.15) + (2 \times 0.15)$$
$$= 0.4 + 0.9 + 0.3 + 0.3 = 1.9$$

**정답**: 평균 CPI = 1.9

---

### 문제 4 — Amdahl's Law 적용

**문제**: 어떤 프로그램의 실행 시간 중 60%가 부동소수점 연산이다. 새 FPU를 도입하여 부동소수점 연산을 10배 빠르게 했다. 전체 속도 향상은?

**풀이**:

$$\text{Speedup} = \frac{1}{(1 - 0.6) + \frac{0.6}{10}} = \frac{1}{0.4 + 0.06} = \frac{1}{0.46} \approx 2.17$$

**정답**: 약 2.17배 향상. FPU를 10배 빠르게 해도 전체는 2.17배에 불과.

---

### 문제 5 — Amdahl's Law: 목표 성능 달성을 위한 개선 비율

**문제**: 전체 성능을 2배로 향상시키려 한다. 개선 대상 부분이 전체의 70%라면, 해당 부분을 몇 배 빠르게 해야 하는가?

**풀이**:

목표: $\text{Speedup} = 2$, $f = 0.7$

$$2 = \frac{1}{(1-0.7) + \frac{0.7}{s}} = \frac{1}{0.3 + \frac{0.7}{s}}$$

$$0.3 + \frac{0.7}{s} = 0.5$$

$$\frac{0.7}{s} = 0.2 \implies s = \frac{0.7}{0.2} = 3.5$$

**정답**: 해당 부분을 3.5배 빠르게 해야 한다.

---

### 문제 6 — 전력 소비 비교

**문제**: CPU A와 B의 스펙이 다음과 같다:
- CPU A: $V = 1.0V$, $f = 3\text{GHz}$, $C = C_0$
- CPU B: $V = 0.8V$, $f = 3\text{GHz}$, $C = C_0$

CPU B의 동적 전력은 A의 몇 %인가?

**풀이**:

$$\frac{P_B}{P_A} = \frac{C_0 \times (0.8)^2 \times 3}{C_0 \times (1.0)^2 \times 3} = \frac{0.64}{1.0} = 0.64$$

**정답**: CPU B의 전력은 CPU A의 64%. 전압을 20% 줄이면 전력은 36% 감소.

---

### 문제 7 — 성능 비교 (멀티 프로그램)

**문제**: 컴파일러 A와 B로 컴파일한 프로그램의 IC, CPI가 다음과 같다. 클럭 속도는 2GHz로 동일하다. 어느 컴파일러가 더 좋은가?

| 컴파일러 | IC | CPI |
|---------|-----|-----|
| A | $4 \times 10^9$ | 1.5 |
| B | $5 \times 10^9$ | 1.1 |

**풀이**:

$$\text{CPU Time}_A = \frac{4 \times 10^9 \times 1.5}{2 \times 10^9} = \frac{6 \times 10^9}{2 \times 10^9} = 3 \text{ 초}$$

$$\text{CPU Time}_B = \frac{5 \times 10^9 \times 1.1}{2 \times 10^9} = \frac{5.5 \times 10^9}{2 \times 10^9} = 2.75 \text{ 초}$$

**정답**: 컴파일러 B가 0.25초 빠르다. IC가 많아도 CPI가 낮으면 더 빠를 수 있음을 보여준다.

---

### 문제 8 — SPEC 기하평균 계산

**문제**: 어떤 CPU가 3개의 SPEC 벤치마크에서 기준 대비 다음 비율을 기록했다: 4.0, 1.0, 0.25. SPEC 점수(기하평균)를 구하시오.

**풀이**:

$$\text{Geometric Mean} = \sqrt[3]{4.0 \times 1.0 \times 0.25} = \sqrt[3]{1.0} = 1.0$$

> [!example] 산술평균과 비교
> 산술평균 = $(4.0 + 1.0 + 0.25) / 3 = 1.75$
> 기하평균 = $1.0$
>
> 산술평균은 4.0이라는 큰 값에 편향되어 실제 성능을 과대평가한다.

**정답**: SPEC 점수 = 1.0 (전반적으로 기준과 동일한 수준)

## 11. 핵심 공식 요약표

| 공식명 | 공식 | 설명 |
|--------|------|------|
| **CPU Time** | $T_{cpu} = \text{IC} \times \text{CPI} \times T_{clock}$ | 명령어 수 × 명령어당 사이클 × 사이클 시간 |
| **CPU Time (Rate)** | $T_{cpu} = \dfrac{\text{IC} \times \text{CPI}}{\text{Clock Rate}}$ | 클럭 속도 버전 |
| **평균 CPI** | $\text{CPI} = \sum_i \left(\text{CPI}_i \times \dfrac{\text{IC}_i}{\text{IC}}\right)$ | 명령어 타입별 가중 평균 |
| **성능 정의** | $\text{Perf} = \dfrac{1}{\text{Execution Time}}$ | 실행 시간의 역수 |
| **성능 비율** | $n = \dfrac{\text{Perf}_X}{\text{Perf}_Y} = \dfrac{T_Y}{T_X}$ | X가 Y보다 n배 빠르다 |
| **Amdahl's Law** | $\text{Speedup} = \dfrac{1}{(1-f) + \frac{f}{s}}$ | 부분 개선의 전체 효과 |
| **Amdahl's 상한** | $\text{Speedup}_{\max} = \dfrac{1}{1-f}$ | $s \to \infty$ 일 때 |
| **동적 전력** | $P \propto C \times V^2 \times f$ | 커패시턴스 × 전압² × 주파수 |
| **MIPS** | $\text{MIPS} = \dfrac{\text{Clock Rate}}{\text{CPI} \times 10^6}$ | 초당 백만 명령어 (신뢰 불가) |
| **SPEC 점수** | $\text{Score} = \sqrt[n]{\prod_{i=1}^{n} \text{Ratio}_i}$ | SPEC 비율의 기하평균 |
| **새 CPU Time** | $T_{\text{new}} = T_{\text{old}} \times \left[(1-f) + \dfrac{f}{s}\right]$ | Amdahl's 실행 시간 버전 |
