## 1. Flynn 분류 (Flynn's Taxonomy)

> [!tip] 면접 빈출
> Flynn 분류는 단순 암기보다 각 카테고리의 **대표 아키텍처**와 **왜 그 범주인지** 연결해서 설명해야 합니다.

Michael Flynn(1966)이 제안한 명령어 스트림(Instruction Stream)과 데이터 스트림(Data Stream) 수에 따른 4분류.

### 1.1 Flynn 분류 매트릭스

|  | **단일 데이터 스트림** (Single Data) | **복수 데이터 스트림** (Multiple Data) |
|---|---|---|
| **단일 명령어 스트림** (Single Instruction) | **SISD** — 순차 프로세서 | **SIMD** — 벡터·GPU |
| **복수 명령어 스트림** (Multiple Instruction) | **MISD** — 이론적 존재 (내결함성) | **MIMD** — 멀티코어·클러스터 |

### 1.2 각 범주 상세

#### SISD (Single Instruction, Single Data)
- 전통적인 단일 코어 순차 프로세서
- 한 번에 명령어 하나, 데이터 하나 처리
- 예: 초기 인텔 x86 (단일 파이프라인, 슈퍼스칼라 이전)

#### SIMD (Single Instruction, Multiple Data)
- **하나의 명령어**가 **여러 데이터 원소**에 동시 적용
- 데이터 수준 병렬성(DLP) 활용
- 예: x86 SSE/AVX, ARM NEON, GPU 셰이더 유닛

```
SIMD 덧셈 (4-wide):
[a0, a1, a2, a3]        [b0, b1, b2, b3]
       +                        +
[a0+b0, a1+b1, a2+b2, a3+b3]   ← 1개 명령어로 처리
```

#### MISD (Multiple Instruction, Single Data)
- 같은 데이터에 서로 다른 명령어를 적용
- 실용적 구현 거의 없음 — 내결함성(Fault Tolerance) 시스템의 이론 모델
- 예: NASA 우주선 삼중 중복 표결 시스템(투표로 오류 검출)

#### MIMD (Multiple Instruction, Multiple Data)
- 각 프로세서가 독립적인 명령어와 데이터로 동작
- 가장 범용적이고 현재 주류
- 예: 멀티코어 CPU, 클러스터 컴퓨터, 클라우드 서버

### 1.3 아키텍처 비교표

| 특성 | SISD | SIMD | MIMD |
|------|------|------|------|
| **병렬성 유형** | 없음 (ILP만) | 데이터 (DLP) | 태스크 + 데이터 (TLP) |
| **제어 복잡도** | 낮음 | 중간 | 높음 |
| **프로그래밍 난이도** | 낮음 | 중간 (벡터화) | 높음 (동기화) |
| **대표 하드웨어** | 초기 인텔 CPU | GPU, SSE/AVX | 멀티코어 CPU |
| **메모리 모델** | 단순 | 공유/분산 | 공유/분산/혼합 |
| **확장성** | 없음 | 중간 | 높음 |

## 2. 병렬성의 세 종류: ILP, DLP, TLP

### 2.1 ILP (Instruction-Level Parallelism, 명령어 수준 병렬성)

- **정의**: 단일 프로세서 내에서 여러 명령어를 동시에 실행
- **하드웨어 구현**: 파이프라이닝(Pipelining), 슈퍼스칼라(Superscalar), 비순서 실행(Out-of-Order Execution)
- **한계**: 데이터 의존성(RAW/WAW/WAR), 제어 해저드, 메모리 해저드

```
슈퍼스칼라 (4-wide):
클럭 1: [I1] [I2] [I3] [I4]  ← 4개 명령어 동시 발행
클럭 2: [I5] [I6] [I7] [I8]
```

### 2.2 DLP (Data-Level Parallelism, 데이터 수준 병렬성)

- **정의**: 동일한 연산을 대규모 데이터셋의 여러 원소에 동시 적용
- **하드웨어 구현**: SIMD 명령어, 벡터 레지스터, GPU 연산 유닛
- **적합한 작업**: 배열 연산, 행렬 곱, 이미지 필터링, 딥러닝 추론

### 2.3 TLP (Thread-Level Parallelism, 스레드 수준 병렬성)

- **정의**: 여러 독립적인 실행 스레드/프로세스를 동시에 처리
- **하드웨어 구현**: 멀티코어(Multi-core), 멀티프로세서(Multi-processor), 동시 멀티스레딩(SMT/Hyper-Threading)
- **적합한 작업**: 서버 워크로드, 게임 물리 연산, 백그라운드 작업

### 2.4 비교 정리

| 구분 | ILP | DLP | TLP |
|------|-----|-----|-----|
| **대상** | 명령어 스트림 | 데이터 원소 | 실행 스레드 |
| **하드웨어** | 파이프라인, OoO | SIMD, 벡터 | 멀티코어, SMT |
| **소프트웨어 부담** | 낮음 (컴파일러) | 중간 (벡터화) | 높음 (스레드 관리) |
| **한계 요인** | 데이터 의존성 | 규칙성 필요 | 동기화 오버헤드 |

## 3. SIMD — 벡터 처리와 확장 명령어 집합

### 3.1 벡터 처리 (Vector Processing)

벡터 프로세서는 스칼라 레지스터 대신 **벡터 레지스터**에 여러 원소를 저장하고 단일 명령어로 전체를 처리합니다.

$$\text{벡터 속도 향상} \approx \min\!\left(n,\ \frac{\text{벡터 길이}}{\text{오버헤드 비율}}\right)$$

- $n$: 벡터 레지스터 폭 (원소 수)

**장점:**
- 루프 오버헤드 제거 (분기·카운터 명령어 불필요)
- 메모리 접근 패턴 예측 가능 → 프리페치 효율 향상
- 긴 파이프라인에서 해저드 발생 빈도 감소

### 3.2 x86 SIMD 확장: SSE / AVX

| 확장 명령어 | 도입 | 레지스터 폭 | 단정밀도 float | 배정밀도 double |
|------------|------|------------|--------------|----------------|
| **SSE** (Streaming SIMD Extensions) | 1999 (Pentium III) | 128비트 | 4개 | 2개 |
| **SSE2** | 2001 (Pentium 4) | 128비트 | 4개 | 2개 |
| **AVX** (Advanced Vector Extensions) | 2011 (Sandy Bridge) | 256비트 | 8개 | 4개 |
| **AVX-512** | 2016 (Skylake-X) | 512비트 | 16개 | 8개 |

```c
// AVX 256비트 벡터 덧셈 (C 인트린식)
#include <immintrin.h>

void add_arrays(float *a, float *b, float *c, int n) {
    for (int i = 0; i < n; i += 8) {
        __m256 va = _mm256_loadu_ps(&a[i]);   // 8개 float 로드
        __m256 vb = _mm256_loadu_ps(&b[i]);
        __m256 vc = _mm256_add_ps(va, vb);    // 8개 동시 덧셈
        _mm256_storeu_ps(&c[i], vc);           // 저장
    }
}
```

### 3.3 ARM NEON

- ARM 계열(모바일, Apple Silicon)의 SIMD 확장
- 128비트 레지스터 32개 (v0–v31)
- 단정밀도 float 4개, 배정밀도 2개, 8비트 정수 16개
- Apple M 시리즈는 추가로 **AMX** (Apple Matrix Extensions) 탑재

```
NEON 128비트 레지스터 레이아웃:
┌────┬────┬────┬────┐
│ f0 │ f1 │ f2 │ f3 │  ← 32비트 float × 4
└────┴────┴────┴────┘
```

> [!note] SIMD의 제약
> - 분기(Branch)가 많은 코드에서 성능 저하: 모든 레인이 같은 명령어를 실행해야 하므로, 조건부 연산은 마스킹(Masking)으로 처리
> - 메모리 정렬(Alignment) 요구: 비정렬 접근은 페널티 발생 (최신 AVX는 완화)
> - 코드 이식성 낮음: SSE는 ARM에서 동작하지 않음 → 이식성을 위해 auto-vectorization 또는 라이브러리 사용

## 4. 멀티코어와 메모리 구조 (Multicore & Memory Architecture)

### 4.1 SMP (Symmetric Multiprocessing)

- 모든 프로세서가 **동일한 물리 메모리**를 공유
- 단일 OS 이미지로 모든 코어 관리
- 현대 멀티코어 CPU의 기본 구조

```
SMP 구조:
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│ Core0│ │ Core1│ │ Core2│ │ Core3│
│ L1$  │ │ L1$  │ │ L1$  │ │ L1$  │
└──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘
   │         │         │         │
   └────────┬┴─────────┴─────────┘
            │   공유 L3 캐시 (LLC)
            │
     ┌──────┴──────┐
     │  메인 메모리  │
     └─────────────┘
```

### 4.2 UMA vs NUMA

| 구분 | **UMA** (Uniform Memory Access) | **NUMA** (Non-Uniform Memory Access) |
|------|--------------------------------|--------------------------------------|
| **메모리 접근 지연** | 모든 프로세서에서 동일 | 로컬 메모리 < 원격 메모리 |
| **확장성** | 낮음 (버스 병목) | 높음 (소켓별 로컬 메모리) |
| **대표 구조** | 단일 소켓 멀티코어 | 멀티 소켓 서버 (EPYC, Xeon) |
| **OS 고려사항** | 없음 | NUMA-aware 스케줄링 필요 |
| **프로그래밍** | 투명 | `numactl`, `libnuma`로 최적화 |

```
NUMA 구조 (2소켓):
┌─────────────────┐         ┌─────────────────┐
│    Socket 0     │         │    Socket 1     │
│  Core0  Core1   │         │  Core2  Core3   │
│    L1    L1     │         │    L1    L1     │
│      L3 캐시    │         │      L3 캐시    │
│   로컬 메모리   │◄──QPI──►│   로컬 메모리   │
└─────────────────┘         └─────────────────┘
  빠른 접근 (~100ns)          느린 접근 (~300ns, 원격)
```

> [!warning] NUMA 함정
> NUMA 시스템에서 스레드가 원격 메모리에 반복 접근하면 성능이 급격히 저하됩니다. OS의 NUMA-aware 메모리 할당(`first-touch` 정책)과 프로세스 핀닝(Process Pinning)이 중요합니다.

## 5. 캐시 일관성 (Cache Coherence)

### 5.1 캐시 일관성 문제

멀티코어에서 각 코어가 독립적인 L1 캐시를 가지면, 같은 메모리 주소에 대해 서로 다른 값을 가질 수 있습니다.

```
문제 시나리오:
초기: 메모리[0x100] = 0

Core0: Load  → L1$ = 0,  메모리 = 0
Core0: Store → L1$ = 1,  메모리 = 0  ← 아직 write-back 안 됨
Core1: Load  → L1$ = 0  ← 메모리에서 로드, 이미 stale!
```

### 5.2 Snooping (스누핑) 프로토콜

- 모든 캐시가 **공유 버스를 감청(Snoop)**
- 다른 코어의 쓰기 트랜잭션을 감지하면 자신의 사본을 무효화 또는 갱신
- 소규모(4~16코어) 시스템에 적합
- 버스 대역폭이 병목 → 대규모 확장 어려움

### 5.3 MESI 프로토콜 상태 전이

MESI는 각 캐시 라인이 가질 수 있는 4가지 상태:

| 상태 | 이름 | 의미 |
|------|------|------|
| **M** | Modified | 이 캐시만 보유, 메모리와 불일치 (Dirty) |
| **E** | Exclusive | 이 캐시만 보유, 메모리와 일치 (Clean) |
| **S** | Shared | 여러 캐시가 보유, 메모리와 일치 (Read-only) |
| **I** | Invalid | 유효하지 않은 사본 (캐시 미스와 동일) |

**MESI 상태 전이도:**

```
                   다른 캐시가 같은 라인 읽음
        ┌──────────────────────────────────┐
        ▼                                  │
┌───────────┐  로컬 읽기(캐시 미스)  ┌───────────┐
│     I     │─────────────────────►│     E     │
│  Invalid  │                      │ Exclusive │
└───────────┘                      └─────┬─────┘
        ▲                                │ 로컬 쓰기
        │                                ▼
        │  다른 캐시가          ┌───────────┐
        │  쓰기(Invalidate)    │     M     │
        │◄─────────────────────│ Modified  │
        │                      └─────┬─────┘
        │                            │ 다른 캐시가 읽음
        │                            │ (Write-back + 공유)
        │                      ┌─────▼─────┐
        └──────────────────────│     S     │
           다른 캐시가 쓰기     │  Shared   │
                               └───────────┘
```

**주요 전이 요약:**

| 현재 상태 | 이벤트 | 다음 상태 | 동작 |
|---------|--------|---------|------|
| I | 로컬 읽기 | E 또는 S | 메모리/다른 캐시에서 로드 |
| E | 로컬 쓰기 | M | 데이터 수정 (버스 트랜잭션 불필요) |
| E | 원격 읽기 | S | 공유 허용 |
| M | 원격 읽기 | S | Write-back 후 공유 |
| M | 원격 쓰기 | I | Write-back 후 무효화 |
| S | 로컬 쓰기 | M | 다른 모든 사본에 Invalidate 전송 |
| S | 원격 쓰기 | I | 무효화됨 |

> [!tip] MESI 기억법
> **M**y dirty data / **E**xclusive clean / **S**hared read-only / **I**nvalid

### 5.4 Directory 프로토콜 (디렉토리 프로토콜)

- 공유 버스 없이 **중앙 디렉토리**가 각 캐시 라인의 상태를 추적
- 대규모 NUMA 시스템(수십~수백 코어)에 적합
- 디렉토리: 각 메모리 블록에 대해 "어느 캐시가 사본을 보유하는지" 비트벡터 유지

```
Directory 구조 (메모리 블록당):
┌──────────────────────────────────────┐
│ Dirty bit │ Presence bits (한 비트/코어) │
│    [1]    │  [1, 0, 1, 0, ...코어0,1,2]  │
└──────────────────────────────────────┘
```

| 비교 항목 | Snooping | Directory |
|----------|----------|-----------|
| **통신 방식** | 브로드캐스트 | 점대점 메시지 |
| **확장성** | 낮음 (버스 병목) | 높음 |
| **지연 시간** | 낮음 (단순) | 높음 (디렉토리 룩업) |
| **적합한 규모** | ≤ 16코어 | 64코어 이상 |

## 6. 메모리 일관성 (Memory Consistency)

> [!warning] 캐시 일관성 vs 메모리 일관성
> - **캐시 일관성**: 같은 주소에 대한 여러 캐시 사본이 일치하는가?
> - **메모리 일관성**: 서로 **다른 주소**에 대한 메모리 연산이 어떤 순서로 다른 프로세서에게 보이는가?

### 6.1 Sequential Consistency (순차 일관성, SC)

- Lamport(1979) 정의: "모든 프로세서의 연산이 어떤 전체 순서(Total Order)로 실행되는 것처럼 보이며, 각 프로세서 내부의 순서는 프로그램 순서와 일치"
- **직관적이고 이해하기 쉬움**
- **성능 비용**: 모든 쓰기를 즉시 전파해야 하므로, OoO 실행 · 스토어 버퍼 사용 제한

### 6.2 Relaxed Consistency (완화된 일관성)

현대 프로세서는 성능을 위해 순서를 완화:

| 모델 | 허용하는 재순서화 | 대표 아키텍처 |
|------|----------------|------------|
| **TSO** (Total Store Order) | Write → Read 재순서화 | x86, SPARC |
| **PSO** (Partial Store Order) | Write → Read, Write → Write | SPARC PSO |
| **WO** (Weak Ordering) | 동기화 외 모든 재순서화 | ARM, RISC-V (기본) |
| **RC** (Release Consistency) | Acquire/Release 사이 완전 완화 | ARM, PowerPC |

> [!example] 재순서화 문제 예시 (x86 TSO)
> ```
> 초기: x = 0, y = 0
>
> Thread 0:          Thread 1:
>   x = 1              y = 1
>   r0 = y             r1 = x
>
> SC에서는 r0=0, r1=1 또는 r0=1, r1=0 또는 r0=1, r1=1 만 가능
> TSO에서는 r0=0, r1=0 도 가능 (스토어 버퍼 때문에 쓰기가 늦게 전파)
> ```

### 6.3 Memory Fence / Barrier

재순서화를 방지하기 위한 명시적 명령어:

```asm
# RISC-V fence 명령어
fence rw, rw    # 이전 모든 R/W가 이후 R/W보다 먼저 완료됨을 보장

# x86
mfence          # 완전 메모리 배리어
sfence          # 스토어 배리어
lfence          # 로드 배리어

# ARM
dmb ish         # Data Memory Barrier (Inner Shareable domain)
```

## 7. 동기화 (Synchronization)

### 7.1 Lock (락)

**스핀락 (Spinlock):**

```c
// 나쁜 예 — 원자성 없음
while (lock != 0);   // 대기
lock = 1;            // 획득 시도 ← 두 스레드가 동시에 통과 가능!
```

```asm
# RISC-V 원자적 스핀락 (lr.w/sc.w 사용)
acquire:
    lr.w  t0, (a0)       # Load-Reserved: 주소 a0의 값을 t0에 로드, 예약 설정
    bnez  t0, acquire    # 이미 잠겨 있으면 재시도
    li    t1, 1
    sc.w  t1, t1, (a0)   # Store-Conditional: 예약 유효하면 1 저장, t1에 성공(0)/실패(1)
    bnez  t1, acquire    # SC 실패(다른 코어가 먼저 획득)하면 재시도
    ret

release:
    sw    zero, 0(a0)    # 락 해제 (단순 저장으로 충분)
    ret
```

### 7.2 lr.w / sc.w (Load-Reserved / Store-Conditional)

RISC-V의 LL/SC (Load-Linked/Store-Conditional) 메커니즘:

- **lr.w (Load-Reserved)**: 메모리에서 값을 읽고 해당 주소에 **예약(Reservation)**을 설정
- **sc.w (Store-Conditional)**: 예약이 여전히 유효하면 값을 쓰고 성공(0) 반환; 다른 코어가 그 사이에 해당 주소에 접근했으면 실패(1) 반환
- **ABA 문제 없음**: 예약은 값이 아닌 주소에 대한 접근 여부로 판단

```
lr.w t0, (a0) → 예약 설정
    │
    ├── 다른 코어가 a0에 쓰기 → 예약 무효화
    │
sc.w t1, t1, (a0)
    ├── 예약 유효 → 성공 (t1 = 0), 저장 완료
    └── 예약 무효 → 실패 (t1 = 1), 저장 안 됨
```

### 7.3 CAS (Compare-And-Swap)

x86 계열에서 사용하는 원자적 연산:

$$\text{CAS}(addr, expected, new) = \begin{cases} *addr \leftarrow new & \text{if } *addr = expected \\ \text{실패} & \text{otherwise} \end{cases}$$

```c
// C++11 atomic CAS
std::atomic<int> val{0};
int expected = 0;
bool success = val.compare_exchange_strong(expected, 1);
// success = true이면 0→1 변경 성공, false이면 expected에 현재값 저장
```

**Lock-Free 스택 구현 예:**

```c
// CAS 기반 lock-free push
void push(Stack *s, Node *n) {
    do {
        n->next = s->top;          // 현재 top 읽기
    } while (!CAS(&s->top, n->next, n));  // top이 변경되지 않았으면 n을 새 top으로
}
```

### 7.4 Barrier (배리어)

- 모든 스레드가 배리어 지점에 도달할 때까지 대기
- 단계별 병렬 계산에서 필수

```
스레드0 ──────────────►[배리어]──────────────►
스레드1 ────────►[배리어]──────────────────►
스레드2 ──────────────────────►[배리어]──────►
                                ↑
                     모두 도달할 때까지 대기
```

```c
// OpenMP 배리어
#pragma omp parallel
{
    do_phase1();
    #pragma omp barrier   // 모든 스레드가 phase1 완료 후 진행
    do_phase2();
}
```

### 7.5 동기화 기법 비교

| 기법 | 방식 | 오버헤드 | 적합한 상황 |
|------|------|---------|-----------|
| **Mutex** | Blocking (OS 개입) | 높음 (context switch) | 임계구역이 길 때 |
| **Spinlock** | Busy-wait | CPU 낭비 | 임계구역 매우 짧을 때 |
| **CAS/LL-SC** | Lock-Free | 낮음 | 단일 변수 원자 갱신 |
| **Barrier** | 전체 대기 | 중간 | 단계 경계 동기화 |
| **Semaphore** | 카운팅 신호 | 중간 | 자원 개수 제한 |

## 8. GPU 아키텍처 (GPU Architecture)

### 8.1 CPU vs GPU 설계 철학

> [!tip] 핵심 비교
> CPU는 **지연 시간(Latency)** 최소화, GPU는 **처리량(Throughput)** 최대화를 목표로 설계됩니다.

| 설계 요소 | **CPU** | **GPU** |
|----------|---------|---------|
| **코어 수** | 4~128개 (고성능 코어) | 수천~수만 개 (단순 코어) |
| **클럭 속도** | 높음 (3~5GHz) | 낮음 (1~2GHz) |
| **캐시 크기** | 수 MB (L1~L3) | 수십~수백 KB/SM |
| **분기 처리** | 강력한 예측기, 추측 실행 | 마스킹(Warp Divergence) |
| **메모리 지연** | 숨김 (OoO, 캐시) | 다른 Warp로 전환 |
| **최적화 대상** | 단일 스레드 성능 | 병렬 처리량 |
| **프로그래밍** | C/C++, OS 스레드 | CUDA, OpenCL |

```
CPU 다이 배치 (개념):
┌────────────────────────────────────────┐
│  대형 캐시 (LLC)                        │  ← 다이의 상당 부분
│ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐  │
│ │Core0 │ │Core1 │ │Core2 │ │Core3 │  │  ← 복잡한 OoO 코어
│ │OoO   │ │OoO   │ │OoO   │ │OoO   │  │
│ └──────┘ └──────┘ └──────┘ └──────┘  │
└────────────────────────────────────────┘

GPU 다이 배치 (개념):
┌────────────────────────────────────────┐
│ SM  SM  SM  SM  SM  SM  SM  SM        │
│ SM  SM  SM  SM  SM  SM  SM  SM        │  ← 수십~수백 SM
│ SM  SM  SM  SM  SM  SM  SM  SM        │
│ SM  SM  SM  SM  SM  SM  SM  SM        │
│           공유 L2 캐시                  │
└────────────────────────────────────────┘
```

### 8.2 CUDA 아키텍처 계층

NVIDIA GPU의 실행 계층 구조 (CUDA 기준):

```
소프트웨어 계층:
  Grid       ← 전체 커널 실행 단위
    └─ Block ← 공유 메모리를 공유하는 스레드 그룹
         └─ Thread ← 개별 실행 스레드

하드웨어 계층:
  GPU
    └─ SM (Streaming Multiprocessor)  ← Block이 여기에 할당
         └─ CUDA Core / Tensor Core   ← Thread가 여기서 실행
              Warp (32스레드)          ← 실제 실행 단위
```

### 8.3 SM (Streaming Multiprocessor)

- GPU의 핵심 연산 단위
- 하나의 SM은 수십~수백 개의 **CUDA 코어** 보유
- 공유 메모리(Shared Memory), L1 캐시, 레지스터 파일을 포함
- 여러 **Warp**를 동시에 관리 (Warp Scheduler)

```
SM 내부 구조 (Ampere 기준, A100):
┌─────────────────────────────────────────┐
│                SM                       │
│  ┌──────────────────────────────────┐  │
│  │  64 CUDA Cores (FP32)            │  │
│  │   4 Tensor Cores (행렬 연산)     │  │
│  └──────────────────────────────────┘  │
│  ┌──────────┐  ┌────────────────────┐  │
│  │레지스터  │  │  공유 메모리/L1$   │  │
│  │파일 256KB│  │      192KB         │  │
│  └──────────┘  └────────────────────┘  │
│  ┌──────────────────────────────────┐  │
│  │  Warp Scheduler × 4             │  │
│  └──────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

### 8.4 Warp (워프)

- GPU의 **실제 실행 단위**: 32개 스레드가 항상 함께 실행 (SIMD 방식)
- Warp 내 모든 스레드는 **같은 명령어**를 실행 (SIMT: Single Instruction Multiple Threads)
- 메모리 접근 지연이 발생하면 다른 Warp로 즉시 전환 → 지연 시간 숨김

**Warp Divergence (워프 발산):**

```cuda
// 나쁜 예 — Warp 발산 발생
if (threadIdx.x % 2 == 0) {
    // 짝수 스레드 실행 경로
    result = a + b;
} else {
    // 홀수 스레드 실행 경로 ← 직렬화!
    result = a * b;
}
// 두 경로를 순차 실행 → 성능 50% 저하
```

```cuda
// 좋은 예 — 분기 최소화
// 짝수/홀수 스레드를 분리된 Warp로 구성
// (커널 설계 단계에서 데이터 배치 조정)
```

### 8.5 GPU 메모리 계층

| 메모리 종류 | 위치 | 크기 | 지연 시간 | 접근 방식 |
|-----------|------|------|---------|---------|
| **레지스터** | SM 내부 | 수십 KB/스레드 | ~1 사이클 | 스레드 전용 |
| **공유 메모리** | SM 내부 | 수십~수백 KB | ~5 사이클 | Block 내 공유 |
| **L1 캐시** | SM 내부 | 공유메모리와 파티션 | ~30 사이클 | 자동 |
| **L2 캐시** | GPU 칩 | 수 MB | ~200 사이클 | 자동 |
| **글로벌 메모리** | GDDR/HBM | 수십 GB | ~600 사이클 | 모든 스레드 |
| **상수 메모리** | GDDR (캐시됨) | 64KB | 캐시히트 시 빠름 | 읽기 전용 |

> [!example] Coalesced Memory Access (메모리 합병 접근)
> Warp 내 32스레드가 연속된 메모리 주소에 접근하면 하나의 메모리 트랜잭션으로 처리됩니다 (Coalesced).
> ```
> 좋은 패턴 (Coalesced):
> thread 0 → addr[0]
> thread 1 → addr[1]
> thread 2 → addr[2]  ← 연속 → 1번 트랜잭션
> ...
>
> 나쁜 패턴 (Strided):
> thread 0 → addr[0]
> thread 1 → addr[32]
> thread 2 → addr[64] ← 비연속 → 32번 트랜잭션
> ```

## 9. 병렬 성능 법칙 (Parallel Performance Laws)

### 9.1 Amdahl's Law — 강한 스케일링 (Strong Scaling)

**강한 스케일링(Strong Scaling)**: 문제 크기는 고정, 프로세서 수를 증가

$$S(n) = \frac{1}{(1 - p) + \dfrac{p}{n}}$$

- $p$: 병렬화 가능한 비율 (0 ≤ p ≤ 1)
- $n$: 프로세서 수
- $1 - p$: 순차 실행 비율 (병렬화 불가)

**이론적 한계:**

$$S_{\max} = \lim_{n \to \infty} S(n) = \frac{1}{1 - p}$$

> [!example] Amdahl's Law 계산 예제
> **문제**: 프로그램의 90%가 병렬화 가능하다. 프로세서를 1개 → 100개로 늘리면 속도 향상은?
>
> **풀이**:
> $$S(100) = \frac{1}{(1 - 0.9) + \dfrac{0.9}{100}} = \frac{1}{0.1 + 0.009} = \frac{1}{0.109} \approx 9.17$$
>
> **최대 한계** ($n \to \infty$):
> $$S_{\max} = \frac{1}{1 - 0.9} = \frac{1}{0.1} = 10$$
>
> **결론**: 100개 프로세서를 써도 9.17배 향상에 그침. 순차 코드 10%가 병목.

**병렬화 비율별 최대 속도 향상:**

| 병렬화 비율 ($p$) | 이론적 최대 속도 향상 |
|-----------------|-------------------|
| 50% | 2× |
| 75% | 4× |
| 90% | 10× |
| 95% | 20× |
| 99% | 100× |

### 9.2 Gustafson's Law — 약한 스케일링 (Weak Scaling)

**약한 스케일링(Weak Scaling)**: 프로세서당 작업량이 일정 (전체 문제 크기도 함께 증가)

$$S(n) = n - \alpha \cdot (n - 1) = \alpha + n(1 - \alpha)$$

- $\alpha$: 순차 비율 (serial fraction)
- $n$: 프로세서 수

**Gustafson vs Amdahl 비교:**

| 구분 | Amdahl | Gustafson |
|------|--------|-----------|
| **문제 크기** | 고정 | 프로세서에 비례하여 증가 |
| **관점** | 특정 문제를 얼마나 빠르게? | 같은 시간에 얼마나 큰 문제를? |
| **스케일링 유형** | 강한 스케일링 | 약한 스케일링 |
| **낙관성** | 비관적 (한계 명확) | 낙관적 (대규모 병렬화 정당화) |
| **적합한 상황** | 실시간 응답 요구 | 과학 시뮬레이션, HPC |

> [!note] Gustafson의 핵심 통찰
> 프로세서가 많아지면 더 큰 문제를 풀 수 있습니다. 실제 과학 계산(기상 예보, 유체 시뮬레이션)에서는 프로세서 증가에 맞춰 해상도나 정밀도를 높입니다. 이 경우 Amdahl의 비관적 한계가 적용되지 않습니다.

### 9.3 Amdahl's Law — 병렬 버전 (다중 개선)

두 부분을 동시에 개선하는 경우:

$$T_{\text{new}} = T_{\text{old}} \times \left[ \frac{f_1}{s_1} + \frac{f_2}{s_2} + (1 - f_1 - f_2) \right]$$

> [!example] 다중 개선 예제
> **문제**: 프로그램에서 정수 연산 40%, 부동소수점 연산 50%, 나머지 10%.
> 정수 연산을 2배, 부동소수점 연산을 4배 빠르게 하면?
>
> **풀이**:
> $$T_{\text{new}} = T_{\text{old}} \times \left[\frac{0.4}{2} + \frac{0.5}{4} + 0.1\right]$$
> $$= T_{\text{old}} \times [0.2 + 0.125 + 0.1] = T_{\text{old}} \times 0.425$$
>
> $$\text{Speedup} = \frac{1}{0.425} \approx 2.35$$

## 10. WSC (Warehouse-Scale Computer) / 클라우드 병렬 처리

### 10.1 WSC 개요

- 구글, 아마존, 마이크로소프트 등이 운영하는 데이터센터 규모의 단일 컴퓨터
- 수만~수십만 대의 서버가 하나의 컴퓨터처럼 동작
- **특성**: 범용 서버 + 고속 네트워크 + 공통 분산 스토리지

### 10.2 MapReduce 패러다임

Google이 2004년 발표한 대규모 데이터 처리 프레임워크:

**처리 흐름:**

```
Input ──► Map ──► Shuffle/Sort ──► Reduce ──► Output

예) 단어 세기 (Word Count):
Input: "hello world hello"
  │
Map: (hello,1) (world,1) (hello,1)
  │
Shuffle: hello → [1,1], world → [1]
  │
Reduce: hello → 2, world → 1
  │
Output: {hello:2, world:1}
```

**Map 단계:**
- 입력 데이터를 독립적인 청크로 분할
- 각 청크에 Map 함수 병렬 적용 → (key, value) 쌍 생성

**Reduce 단계:**
- 같은 key를 가진 값들을 한 노드로 모음 (Shuffle)
- Reduce 함수로 집계

**장점:**
- 자동 병렬화 및 부하 분산
- 노드 장애 시 자동 재실행 (내결함성)
- 수천 노드로 선형에 가까운 확장

### 10.3 클라우드 병렬 처리의 성능 고려사항

| 요소 | 설명 |
|------|------|
| **Request-Level Parallelism** | 수백만 개의 독립 요청을 동시에 처리 |
| **Data Parallelism** | MapReduce, Spark 등으로 데이터 분할 처리 |
| **Tail Latency** | 99번째 백분위 지연 시간 관리 (Straggler 문제) |
| **Power Usage Effectiveness (PUE)** | 총 전력/IT 장비 전력 (목표: 1.1 이하) |

## 11. 면접 빈출 Q&A

> [!question] Q1. Flynn 분류에서 GPU는 어느 범주에 속하고, 그 이유는?
> **A:** GPU는 **SIMD** (또는 MIMD의 하위 분류로 보는 SIMT)에 속합니다.
>
> 각 SM 내에서 하나의 Warp(32스레드)가 **동일한 명령어**를 **서로 다른 데이터**에 적용하기 때문입니다. NVIDIA는 이를 **SIMT (Single Instruction Multiple Threads)**라 부르며, 조건부 분기 시 마스킹으로 처리하는 점이 전통적 SIMD와 차이점입니다.
>
> GPU 전체로 보면 여러 SM이 독립적으로 다른 Block을 실행하므로 MIMD적 요소도 있지만, 기본 실행 단위(Warp)는 SIMD 방식입니다.

---

> [!question] Q2. MESI 프로토콜에서 E(Exclusive)와 S(Shared) 상태의 차이는?
> **A:**
> - **E (Exclusive)**: 해당 캐시 라인이 **오직 이 캐시에만** 존재하며 메모리와 일치합니다. 쓰기 시 다른 코어에 Invalidate를 보낼 필요 없이 바로 M으로 전이 가능 → 쓰기 효율 높음
> - **S (Shared)**: 해당 캐시 라인이 **여러 캐시**에 존재하며 메모리와 일치합니다. 쓰기 시 다른 모든 사본에 Invalidate를 전송해야 함 → 추가 버스 트랜잭션 필요
>
> E 상태는 "이 코어만 읽었고 아직 아무도 공유하지 않음"을 의미하며, 캐시 미스 직후 단독으로 로드한 경우입니다.

---

> [!question] Q3. UMA와 NUMA의 차이는? NUMA에서 성능 최적화 방법은?
> **A:**
> - **UMA**: 모든 프로세서가 메모리에 동일한 접근 시간을 가짐. 단순하지만 버스 대역폭 한계로 확장성 낮음
> - **NUMA**: 각 소켓이 로컬 메모리를 가지며, 원격 메모리 접근은 더 느림 (1.5~3× 지연)
>
> **최적화 방법:**
> 1. **프로세스/스레드 핀닝**: `taskset`, `numactl --cpunodebind` 로 NUMA 노드에 고정
> 2. **메모리 로컬리티**: `numactl --membind` 또는 `mmap` 시 first-touch 정책 활용
> 3. **NUMA-aware 데이터 구조**: 각 노드가 자신의 데이터만 주로 접근하도록 분할
> 4. **False Sharing 방지**: 서로 다른 소켓의 스레드가 같은 캐시 라인을 수정하지 않도록 패딩

---

> [!question] Q4. 캐시 일관성(Cache Coherence)과 메모리 일관성(Memory Consistency)의 차이는?
> **A:**
> - **캐시 일관성**: **같은 주소**에 대한 여러 캐시 사본이 일치하는 문제. "코어 A가 주소 X를 썼을 때 코어 B가 읽으면 새 값을 볼 수 있는가?" MESI 프로토콜이 해결
> - **메모리 일관성**: **서로 다른 주소**에 대한 연산이 다른 프로세서에게 어떤 순서로 보이는가의 문제. "코어 A가 X를 쓰고 Y를 읽을 때, 코어 B가 보는 순서는?" 메모리 모델(SC, TSO 등)이 정의
>
> 예: x = 1 쓴 후 flag = 1 써도, 다른 코어에서 flag = 1을 보는 시점에 x가 아직 0일 수 있음 (Relaxed Consistency 때문).

---

> [!question] Q5. lr.w/sc.w가 CAS(Compare-And-Swap)보다 나은 점은?
> **A:** **ABA 문제 해결**입니다.
>
> CAS는 값을 비교하므로, 값이 A→B→A로 변경된 경우 감지 못합니다 (ABA 문제). 반면 lr.w/sc.w는 값이 아닌 **주소에 대한 접근 여부**를 예약으로 추적하므로, 값이 같더라도 사이에 다른 쓰기가 있었다면 sc.w가 실패합니다.
>
> 추가로 lr.w/sc.w 기반 코드는 CAS로 표현 가능하지만, CAS를 lr.w/sc.w로 구현하기 더 쉬운 방향이므로 RISC-V는 LL/SC를 기본으로 채택했습니다.

---

> [!question] Q6. Warp Divergence란 무엇이고, 어떻게 성능에 영향을 주는가?
> **A:** Warp(32스레드)는 SIMT 방식으로 모든 스레드가 같은 명령어를 실행합니다. 조건부 분기(if-else)에서 스레드들이 서로 다른 경로를 가면 **Warp Divergence**가 발생합니다.
>
> GPU는 두 경로를 순차적으로 실행하고 각 경로에서 해당 스레드만 활성화(마스킹)합니다.
>
> **영향**: Warp 내 n가지 분기 경로가 있으면 실행 효율이 1/n로 저하. 예를 들어 절반씩 두 경로로 나뉘면 처리량이 50% 감소합니다.
>
> **해결책**: 데이터를 같은 분기 경로를 가지는 스레드끼리 묶어 배치, 분기를 수식(선택 연산)으로 대체.

---

> [!question] Q7. Amdahl의 법칙이 실제 병렬화에 주는 시사점은?
> **A:** 순차 실행 비율이 병렬 성능의 절대적 상한을 결정합니다.
>
> 핵심 시사점:
> 1. **순차 부분 최소화가 최우선**: 병렬화 가능 비율을 높이는 것이 코어 수를 늘리는 것보다 효과적
> 2. **수확 체감**: 코어 수를 2배 늘려도 속도 향상은 2배 미만 (순차 부분이 있는 한)
> 3. **Make the Common Case Fast**: 가장 자주 실행되는 순차 코드 경로를 최적화해야 함
>
> 예: 순차 비율 1%만 있어도 최대 속도 향상은 100×에 불과 → 수천 코어를 써도 100배 이상 불가.

---

> [!question] Q8. Sequential Consistency(SC)와 Relaxed Memory Model의 차이는? 왜 현대 CPU는 SC를 안 쓰는가?
> **A:**
> - **SC**: 모든 프로세서의 메모리 연산이 어떤 전체 순서로 실행되는 것처럼 보임. 직관적이지만 스토어 버퍼, OoO 실행, 비순서 메모리 완료를 금지 → 성능 저하
> - **Relaxed**: 특정 조건(동기화 경계 사이)에서만 순서를 보장. 스토어 버퍼, 비순서 로드 허용 → 성능 향상
>
> **현대 CPU가 Relaxed를 사용하는 이유**: 스토어가 L1 캐시에 즉시 반영되길 기다리면 메모리 지연(수백 사이클)만큼 CPU가 멈춥니다. 스토어 버퍼로 먼저 버퍼링하고 계속 실행하면 IPC가 크게 향상됩니다. 프로그래머는 필요할 때 `fence` 명령어로 명시적 순서를 보장합니다.

---

> [!question] Q9. GPU가 메모리 접근 지연을 숨기는 방법은?
> **A:** **Warp 전환 (Warp Switching)** 기법입니다.
>
> SM은 수백~수천 개의 스레드(여러 Warp)를 동시에 관리합니다. 한 Warp가 글로벌 메모리 접근으로 수백 사이클을 기다리는 동안, SM은 즉시 **다른 준비된 Warp로 전환**하여 실행합니다. 메모리 응답이 오면 해당 Warp는 다시 실행 대기열에 올라갑니다.
>
> CPU가 큰 캐시와 OoO 실행으로 지연을 숨기는 것과 달리, GPU는 **스레드 수의 방대함**으로 지연을 숨깁니다. 따라서 GPU 프로그래밍에서는 충분한 **Occupancy** (SM당 활성 Warp 비율)를 높이는 것이 핵심입니다.

---

> [!question] Q10. 강한 스케일링과 약한 스케일링의 차이는? 언제 각각을 사용하는가?
> **A:**
> - **강한 스케일링 (Strong Scaling)**: 문제 크기 고정, 프로세서 증가 → 실행 시간 감소. Amdahl 법칙 적용. 실시간 응답이 필요한 상황 (실시간 렌더링, 트랜잭션 처리)에 사용
> - **약한 스케일링 (Weak Scaling)**: 프로세서당 작업량 고정, 프로세서·문제 크기 동시 증가 → 실행 시간 유지. Gustafson 법칙 적용. 더 큰 문제를 풀고 싶은 상황 (기후 모델, 분자 역학, 천문학 시뮬레이션)에 사용
>
> 이상적 약한 스케일링 효율 = 1.0 (프로세서 n배 → 같은 시간에 n배 큰 문제 해결)

---

> [!question] Q11. SIMD에서 False Sharing이 발생하는 이유와 해결책은?
> **A:** **False Sharing**은 두 스레드가 **서로 다른 변수**를 수정하는데, 그 변수들이 **같은 캐시 라인** (일반적으로 64바이트)에 위치할 때 발생합니다.
>
> MESI 프로토콜 상 한 스레드가 캐시 라인을 수정하면 다른 스레드의 사본이 무효화되고, 반대쪽 스레드가 접근할 때 캐시 미스가 발생합니다. 실제로는 두 변수가 독립적인데도 마치 공유 데이터처럼 일관성 트래픽이 발생합니다.
>
> **해결책**:
> ```c
> // 잘못된 예 — false sharing 발생
> struct Counter { int val; };
> Counter counters[NUM_THREADS];   // 연속 배치 → 같은 캐시 라인
>
> // 올바른 예 — 캐시 라인 패딩
> struct alignas(64) Counter { int val; char pad[60]; };
> Counter counters[NUM_THREADS];   // 각 카운터가 독립 캐시 라인
> ```

> 2. Core1이 주소 A를 읽는다
> 3. Core0가 주소 A에 쓴다
> 4. Core1이 주소 A를 읽는다

> [!question] 문제 2. Amdahl's Law 계산
> 프로그램 실행 시간의 80%가 병렬화 가능하다. 다음을 계산하라.
> (a) 프로세서 4개 사용 시 속도 향상
> (b) 프로세서 16개 사용 시 속도 향상
> (c) 이론적 최대 속도 향상
> (d) 프로세서 몇 개가 있어야 최대 속도 향상의 80%를 달성하는가?

**풀이:**

**(a) n = 4:**

$$S(4) = \frac{1}{(1-0.8) + \frac{0.8}{4}} = \frac{1}{0.2 + 0.2} = \frac{1}{0.4} = 2.5$$

**(b) n = 16:**

$$S(16) = \frac{1}{0.2 + \frac{0.8}{16}} = \frac{1}{0.2 + 0.05} = \frac{1}{0.25} = 4$$

**(c) 이론적 최대:**

$$S_{\max} = \frac{1}{1 - 0.8} = \frac{1}{0.2} = 5$$

**(d) 최대의 80% = 4배 달성에 필요한 n:**

$$4 = \frac{1}{0.2 + \frac{0.8}{n}} \implies 0.2 + \frac{0.8}{n} = 0.25 \implies \frac{0.8}{n} = 0.05 \implies n = 16$$

**정답: (a) 2.5배, (b) 4배, (c) 5배, (d) 16개**

> [!question] 문제 3. lr.w/sc.w 원자적 연산
> RISC-V lr.w/sc.w를 사용하여 원자적 fetch-and-add (FAA) 연산을 구현하라.
> (`int atomic_fetch_add(int *addr, int delta)` — addr의 값에 delta를 더하고 이전 값 반환)

**풀이:**

```asm
# a0 = addr (포인터), a1 = delta
# 반환값 a0 = 이전 값

atomic_fetch_add:
    lr.w  t0, (a0)        # t0 = *addr (예약 설정)
    add   t1, t0, a1      # t1 = t0 + delta (새 값 계산)
    sc.w  t2, t1, (a0)    # *addr = t1 (성공 시), t2 = 0(성공)/1(실패)
    bnez  t2, atomic_fetch_add   # 실패하면 재시도
    mv    a0, t0           # 반환값 = 이전 값
    ret
```

**설명:**
- lr.w로 이전 값을 읽고 예약 설정
- add로 새 값 계산 (이 연산 자체는 원자적 필요 없음)
- sc.w로 원자적 저장 시도
- 다른 코어가 사이에 개입했으면 sc.w 실패 → 전체 재시도
- 성공하면 이전 값(t0)을 반환

> [!question] 문제 4. GPU Occupancy 계산
> SM의 사양이 다음과 같다:
> - 최대 Warp 수: 64
> - 최대 Block 수: 32
> - 레지스터 파일: 65536개
> - 공유 메모리: 98304 bytes
>
> 커널 설정: Block 크기 = 256스레드, 레지스터 = 32개/스레드, 공유 메모리 = 8192 bytes/block
>
> SM당 최대 몇 개의 Block이 동시에 실행되는가? Occupancy(%)는?

**풀이:**

**Warp 수 제약:**
- Block당 Warp 수 = 256 / 32 = 8 Warps
- 최대 Block 수 (Warp 기준) = 64 / 8 = **8 Blocks**

**Block 수 제약:**
- 최대 Block 수 = **32** (하드웨어 한계)

**레지스터 제약:**
- Block당 레지스터 = 256 스레드 × 32 레지스터 = 8192
- 최대 Block 수 (레지스터 기준) = 65536 / 8192 = **8 Blocks**

**공유 메모리 제약:**
- 최대 Block 수 (공유 메모리 기준) = 98304 / 8192 = **12 Blocks**

**최소값 = min(8, 32, 8, 12) = 8 Blocks**

**Occupancy:**

$$\text{Occupancy} = \frac{\text{실제 Warp 수}}{\text{최대 Warp 수}} = \frac{8 \times 8}{64} = \frac{64}{64} = 100\%$$

**정답: 8 Blocks, Occupancy = 100%**

> [!question] 문제 5. Gustafson's Law
> 순차 비율 5%인 프로그램을 100개 프로세서로 실행한다. Gustafson's Law에 따른 속도 향상은?
> 같은 조건에서 Amdahl's Law의 속도 향상과 비교하라.

**풀이:**

**Gustafson's Law** ($\alpha = 0.05$, $n = 100$):

$$S_G(100) = 0.05 + 100 \times (1 - 0.05) = 0.05 + 95 = 95.05$$

**Amdahl's Law** ($p = 0.95$, $n = 100$):

$$S_A(100) = \frac{1}{(1-0.95) + \frac{0.95}{100}} = \frac{1}{0.05 + 0.0095} = \frac{1}{0.0595} \approx 16.81$$

**비교:**

| 법칙 | 속도 향상 | 가정 |
|------|---------|------|
| **Gustafson** | 95.05× | 문제 크기가 함께 증가 (더 큰 문제 해결) |
| **Amdahl** | 16.81× | 문제 크기 고정 (같은 문제를 빠르게) |

**해석:** HPC 시뮬레이션처럼 더 높은 해상도로 같은 시간 내에 실행하는 경우 Gustafson이 적합. 특정 트랜잭션 처리 시간을 줄이는 경우 Amdahl이 적합.

> [!question] 문제 6. 캐시 일관성 — False Sharing 성능 분석
> 4코어 시스템에서 각 코어가 배열의 연속된 원소를 수정한다.
>
> ```c
> int arr[4] = {0, 0, 0, 0};  // 캐시 라인 크기 = 64 bytes = 16개 int
>
> // 각 코어 i가 arr[i]를 10,000,000번 ++한다
> ```
>
> (a) False Sharing이 발생하는 이유를 설명하라
> (b) 이를 해결하는 코드를 작성하라
> (c) 성능 차이가 발생하는 원리를 MESI 관점에서 설명하라

**풀이:**

**(a) False Sharing 발생 이유:**

`arr[4]`는 4 × 4 = 16 bytes로 **하나의 캐시 라인(64 bytes)** 안에 들어갑니다. Core0가 `arr[0]`을 수정하면 그 캐시 라인 전체가 Modified 상태가 되고, 다른 코어들의 사본이 Invalid가 됩니다. Core1이 `arr[1]`을 수정하려면 먼저 Core0의 캐시 라인을 Write-back 받아야 합니다. `arr[0]`과 `arr[1]`은 논리적으로 독립이지만 물리적으로 같은 캐시 라인이므로 캐시 트래픽이 발생합니다.

**(b) 해결 코드:**

```c
// 각 카운터를 캐시 라인 크기로 패딩
struct alignas(64) PaddedCounter {
    int val;
    char padding[60];   // 64 - sizeof(int) = 60 bytes
};

PaddedCounter arr[4];  // 각 원소가 독립 캐시 라인

// 또는 C++17
struct PaddedCounter {
    alignas(64) int val;
};
```

**(c) MESI 관점 설명:**

```
False Sharing 발생 시 (1,000만 번 반복):
① Core0: arr[0]++ → S→M (다른 코어에 Invalidate 전송)
② Core1: arr[1] 접근 → I→S (Core0에서 Write-back 요청, 캐시 미스)
③ Core1: arr[1]++ → S→M (Core0에 Invalidate 전송)
④ Core0: arr[0] 접근 → I→S (Core1에서 Write-back 요청, 캐시 미스)
... 1,000만 번 반복 = 수천만 번의 버스 트랜잭션

패딩 적용 시:
각 core가 독립 캐시 라인 → 다른 코어가 Invalidate를 받지 않음
arr[0] 수정: E→M (버스 트랜잭션 없음!)
```

> [!question] 문제 7. Warp Divergence 성능 계산
> GPU Warp(32스레드)에서 다음 코드를 실행한다.
>
> ```cuda
> if (threadIdx.x < 16) {
>     A();   // 16개 스레드, 100 사이클
> } else {
>     B();   // 16개 스레드, 200 사이클
> }
> ```
>
> (a) Divergence 없이 이상적으로 실행될 경우 예상 사이클 수는?
> (b) Warp Divergence로 실제 실행 사이클 수는?
> (c) 효율(%)은?

**풀이:**

**(a) 이상적 사이클 (Divergence 없다고 가정):**

SIMD라면 16개 × A(100) + 16개 × B(200)의 최솟값을 동시에 처리 → 이상적으로는 max(100, 200) = **200 사이클**

**(b) 실제 Warp Divergence 사이클:**

Warp는 두 경로를 순차 실행:
- Phase 1: 스레드 0~15가 A() 실행, 스레드 16~31은 비활성 → **100 사이클**
- Phase 2: 스레드 16~31이 B() 실행, 스레드 0~15는 비활성 → **200 사이클**
- 합계: **300 사이클**

**(c) 효율:**

$$\text{효율} = \frac{\text{이상적}}{\text{실제}} = \frac{200}{300} \approx 66.7\%$$

또는 활성 스레드 비율로 계산:

$$\text{효율} = \frac{16 \times 100 + 16 \times 200}{32 \times (100 + 200)} = \frac{4800}{9600} = 50\%$$

> [!note] 두 계산 방식의 차이
> - 첫 번째 (66.7%): 이상적 병렬 실행 시간 대비
> - 두 번째 (50%): 전체 슬롯 활용률 기준 (더 보수적, 교재에서 주로 사용)

> [!question] 문제 8. 종합 — 병렬 시스템 설계 트레이드오프
> 다음 두 설계 중 어느 것이 더 나은지 조건에 따라 분석하라.
>
> **설계 A**: 단일 고성능 코어 (클럭 4GHz, CPI 1.5, 단일 스레드 성능 최고)
> **설계 B**: 8코어 저전력 프로세서 (코어당 클럭 1.5GHz, CPI 2.0, 병렬 프로그램)
>
> 프로그램: 총 10억 개 명령어, 병렬화 가능 비율 75%
>
> (a) 설계 A의 실행 시간
> (b) 설계 B의 이론적 실행 시간 (Amdahl's Law 적용)
> (c) 어느 설계가 이 워크로드에 적합한가?

**풀이:**

**(a) 설계 A 실행 시간:**

$$T_A = \frac{\text{IC} \times \text{CPI}}{\text{Clock Rate}} = \frac{10^9 \times 1.5}{4 \times 10^9} = 0.375 \text{ 초}$$

**(b) 설계 B 실행 시간:**

단일 코어 기준 시간:

$$T_{B,\text{single}} = \frac{10^9 \times 2.0}{1.5 \times 10^9} = \frac{2}{1.5} \approx 1.333 \text{ 초}$$

Amdahl's Law로 8코어 속도 향상 ($p = 0.75$, $n = 8$):

$$S(8) = \frac{1}{(1-0.75) + \frac{0.75}{8}} = \frac{1}{0.25 + 0.09375} = \frac{1}{0.34375} \approx 2.909$$

$$T_{B,\text{parallel}} = \frac{1.333}{2.909} \approx 0.458 \text{ 초}$$

**(c) 비교 및 결론:**

| 설계 | 실행 시간 | 코어 수 | 소비 전력 |
|------|---------|--------|---------|
| **A** (단일 고성능) | **0.375초** | 1 | 높음 |
| **B** (8코어 저전력) | 0.458초 | 8 | 낮음 |

- **순수 성능**으로는 설계 A가 유리 (이 워크로드에서는 병렬화 비율 75%가 낮아 멀티코어 이점이 제한됨)
- **전력 효율** 또는 **다중 독립 요청 처리** (서버 워크로드)에서는 설계 B가 유리
- 병렬화 비율이 95% 이상이면 설계 B가 역전될 수 있음

**결론**: 이 특정 워크로드(병렬화 75%)에서는 설계 A가 빠르지만, 실제 서버 환경에서 독립적 요청이 동시에 오면 설계 B의 8코어가 8배 더 많은 요청을 처리할 수 있어 처리량 관점에서 설계 B가 우월합니다.

## 13. 핵심 개념 요약

```
병렬 프로세서 핵심 지도:

Flynn 분류
├── SISD → 순차 CPU
├── SIMD → GPU, SSE/AVX
├── MISD → 이론적 (내결함성)
└── MIMD → 멀티코어, 클러스터

병렬성 종류
├── ILP → 파이프라인, 슈퍼스칼라, OoO
├── DLP → SIMD, 벡터, GPU
└── TLP → 멀티코어, SMT

멀티코어 메모리
├── UMA (단일 소켓, 균일 접근)
└── NUMA (멀티 소켓, 비균일 접근)
    └── NUMA-aware 프로그래밍 필요

캐시 일관성
├── Snooping (소규모, 브로드캐스트)
│   └── MESI: Modified/Exclusive/Shared/Invalid
└── Directory (대규모, 점대점)

메모리 일관성
├── Sequential Consistency (직관적, 느림)
└── Relaxed (TSO/WO, 빠름, fence 필요)

동기화
├── Lock: Mutex(blocking), Spinlock(busy-wait)
├── Atomic: lr.w/sc.w, CAS
└── Barrier: 단계 경계 동기화

GPU
├── SM → Block 할당
├── Warp(32스레드) → SIMT 실행
├── Warp Divergence → 성능 저하
└── Coalesced Access → 성능 향상

성능 법칙
├── Amdahl: 강한 스케일링, S = 1/((1-p)+p/n)
└── Gustafson: 약한 스케일링, S = α + n(1-α)
```
