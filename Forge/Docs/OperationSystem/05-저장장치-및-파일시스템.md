## Chapter 11–12. 대용량 저장장치 & I/O 시스템

### 11-1. 디스크 구조

```
물리 디스크 계층
├── 플래터(Platter)  — 자기 디스크 원판
│   ├── 트랙(Track)   — 원형 데이터 띠
│   │   └── 섹터(Sector) — 최소 R/W 단위 (전통 512B → 최신 4 KB)
│   └── 실린더(Cylinder) — 동일 트랙 번호의 집합 (헤드 이동 없이 접근 가능)
└── 헤드(Head)       — 플래터당 1개 (상·하면 각 1)
```

**접근 시간 3요소**

| 요소 | 설명 | 크기 |
|------|------|------|
| Seek Time (탐색 시간) | 헤드가 목표 트랙으로 이동하는 시간 | 수 ms — 지배적 |
| Rotational Latency (회전 대기) | 목표 섹터가 헤드 아래로 돌아올 때까지 기다리는 시간 | 평균 = 1/2 회전 |
| Transfer Time (전송 시간) | 실제 데이터 읽기/쓰기 | 매우 짧음 |

> 최적화 목표: **Seek Time 최소화** → 디스크 스케줄링의 핵심

### 11-2. 디스크 스케줄링 알고리즘

> 💡 **면접 포인트**
> - FCFS vs SCAN: FCFS는 구현 단순, SCAN은 처리량↑·기아 방지
> - C-SCAN: 단방향 스윕 → 균등한 대기 시간 보장 (엘리베이터와 비교 단골)
> - LOOK vs SCAN: 끝까지 가지 않고 마지막 요청에서 반환 → 실제 OS 구현에 가까움

**요청 큐 예시** (시작 헤드 = 53): `98, 183, 37, 122, 14, 124, 65, 67`

#### FCFS (First-Come, First-Served)
- 요청 순서대로 처리
- 총 이동 = 640 실린더 (예시)
- 단순하지만 **헤드 이동 최악** → 스래싱(Thrashing) 유발 가능

#### SSTF (Shortest Seek Time First)
- 현재 헤드에서 가장 가까운 요청 우선
- 처리량 ↑, but **기아(Starvation)** 가능
- 최적(Optimal)이 아님 — 탐욕적(Greedy)

#### SCAN (엘리베이터 알고리즘)
- 한 방향으로 끝까지 이동하며 처리 → 끝에 도달하면 역방향
- 균등한 서비스, 기아 없음
- 디스크 끝 부근 트랙은 방금 지나쳤으면 거의 한 바퀴 대기

#### C-SCAN (Circular SCAN)
- 한 방향만 서비스 → 끝 도달 시 **처음으로 즉시 점프 (서비스 없이)**
- 균일한 대기 시간 → **실용적 선택**

#### LOOK
- SCAN과 동일하지만 **마지막 요청 위치에서 반전** (물리적 끝까지 가지 않음)
- 불필요한 이동 제거

#### C-LOOK
- C-SCAN + LOOK 결합: 마지막 요청까지만 이동 후 최솟값으로 점프
- **현대 OS에서 가장 많이 사용**

**알고리즘 비교 요약**

| 알고리즘 | 처리량 | 기아 | 균등성 | 특징 |
|----------|--------|------|--------|------|
| FCFS | 낮음 | 없음 | 낮음 | 구현 단순 |
| SSTF | 높음 | 가능 | 낮음 | 그리디, 불공평 |
| SCAN | 높음 | 없음 | 중간 | 엘리베이터 |
| C-SCAN | 높음 | 없음 | 높음 | 균등 대기 |
| LOOK | 높음 | 없음 | 중간 | SCAN 개선 |
| C-LOOK | 높음 | 없음 | 높음 | 실제 OS 사용 |

### 11-3. SSD (Solid State Drive) 특성

**HDD vs SSD 핵심 차이**

| 항목 | HDD | SSD |
|------|-----|-----|
| 기계적 이동 | 있음 (헤드 탐색) | 없음 |
| 랜덤 읽기 | 느림 (Seek 때문) | 매우 빠름 |
| 쓰기 단위 | 섹터(512B~4KB) | 페이지(4~16KB) |
| 소거 단위 | 섹터 | 블록(페이지 묶음, 128~512KB) |
| 디스크 스케줄링 | 필요 | 불필요 (FCFS 충분) |

#### Wear Leveling (마모 평준화)
- NAND 플래시는 **P/E(Program/Erase) 사이클 한계** 존재 (SLC~3000회 / TLC~300회)
- FTL(Flash Translation Layer)이 논리 주소 → 물리 주소 동적 매핑
- 자주 쓰이는 블록에만 집중되지 않도록 **쓰기 분산**
- 종류:
  - **Dynamic Wear Leveling**: 소거된 빈 블록 중 가장 덜 사용된 블록 선택
  - **Static Wear Leveling**: 정적 데이터(콜드 데이터)도 주기적으로 이동

#### TRIM 명령
- OS가 "이 논리 블록은 이제 쓸모없다"고 SSD에 알리는 ATA 명령
- **Delete 즉시 무효 블록 표시** → 가비지 컬렉션(GC) 효율화
- TRIM 없으면: 유효 데이터인지 모르고 → GC 시 복사 후 소거 → 쓰기 증폭(Write Amplification)

#### 쓰기 증폭 (Write Amplification, WA)
```
WA = 실제 NAND 쓰기 양 / 호스트가 요청한 쓰기 양
이상적: WA = 1.0 / 실제: 1.5~10 (GC 오버헤드 포함)
```

### 11-4. RAID (Redundant Array of Independent Disks)

> 💡 **면접 포인트**
> - RAID 0 vs 1 vs 5 vs 6 차이 → 반드시 외울 것
> - RAID 5: 패리티 분산, 디스크 1개 고장 허용 — "스트라이핑 + 패리티"
> - RAID 6: 패리티 2개, 디스크 2개 동시 고장 허용
> - RAID 10 = RAID 1+0: 미러링 후 스트라이핑 — 성능+신뢰성 균형
> - "RAID는 백업이 아니다" (논리 오류·랜섬웨어 비보호)

| RAID 레벨 | 구성 | 최소 디스크 | 읽기 성능 | 쓰기 성능 | 가용 공간 | 허용 고장 | 특징 |
|-----------|------|------------|-----------|-----------|-----------|-----------|------|
| RAID 0 | 스트라이핑(Striping) | 2 | ↑↑ | ↑↑ | 100% | 0 | 성능 최대, 신뢰성 없음 |
| RAID 1 | 미러링(Mirroring) | 2 | ↑ (양쪽 읽기) | = | 50% | N/2 | 단순, 비용 높음 |
| RAID 5 | 스트라이핑 + 분산 패리티 | 3 | ↑↑ | ↓ (패리티 계산) | (N-1)/N | 1 | 범용, 비용 효율적 |
| RAID 6 | 스트라이핑 + 이중 패리티 | 4 | ↑↑ | ↓↓ | (N-2)/N | 2 | 대용량 어레이 안전 |
| RAID 10 | RAID 1 후 RAID 0 | 4 | ↑↑ | ↑ | 50% | 각 미러에서 1개 | 성능+신뢰성 균형 |

**패리티 계산 (XOR)**
```
디스크 1: 1 0 1 1
디스크 2: 0 1 1 0
패리티:   1 1 0 1   ← XOR
복구: 디스크 1 = 패리티 XOR 디스크 2
```

**RAID 5 vs RAID 6 선택 기준**

| 상황 | 권장 |
|------|------|
| 디스크 ≤ 5개, 비용 절감 | RAID 5 |
| 디스크 6개 이상 또는 장시간 리빌드 위험 | RAID 6 |
| 최대 성능 + 신뢰성 (예산 여유) | RAID 10 |

### 12-1. I/O 시스템 개요

#### 폴링(Polling) vs 인터럽트(Interrupt) vs DMA

| 방식 | 동작 | CPU 부하 | 적합 상황 |
|------|------|----------|-----------|
| **폴링** | CPU가 주기적으로 장치 상태 레지스터 확인 | 높음 (Busy-Wait) | 빠른 장치, 짧은 대기 |
| **인터럽트** | 장치 완료 시 CPU에 신호 → ISR 실행 | 낮음 | 느린 장치, 일반적 경우 |
| **DMA** | DMA 컨트롤러가 메모리↔장치 직접 전송, 완료 후 인터럽트 1회 | 매우 낮음 | 대용량 블록 전송 |

**DMA 동작 흐름**
```
1. CPU → DMA 컨트롤러에 전송 명령 (소스, 목적지, 크기)
2. DMA가 버스를 점유해 메모리↔I/O 직접 전송 (CPU 독립)
3. 전송 완료 → DMA가 CPU에 인터럽트 1회 발생
4. CPU는 인터럽트 처리만 수행 (모든 데이터 이동 불관여)
```

#### I/O 소프트웨어 계층

```
애플리케이션 I/O 인터페이스
    ↕
커널 I/O 서브시스템 (버퍼링, 캐싱, 스풀링, 에러 처리)
    ↕
장치 드라이버 (장치별 구현)
    ↕
인터럽트 핸들러
    ↕
하드웨어 (디스크, NIC, …)
```

**스풀링(Spooling)**: 단일 접근 장치(프린터 등)에 여러 프로세스가 동시 출력할 수 있도록 큐 관리

### 12-2. 블로킹 / 논블로킹 / 비동기 I/O

| 유형 | 설명 | 반환 시점 | 예 |
|------|------|------------|-----|
| **블로킹(Blocking)** | I/O 완료 전까지 프로세스 대기 (WAITING 상태) | I/O 완료 후 | `read()`, `fread()` |
| **논블로킹(Non-blocking)** | 즉시 반환 (준비된 데이터만 처리), 완료 미보장 | 즉시 (데이터 없으면 -1/EAGAIN) | `O_NONBLOCK` + `select()` |
| **비동기(Asynchronous)** | 요청 후 바로 반환 → 완료 시 콜백/시그널 | 요청 직후 (완료는 나중에 알림) | POSIX `aio_read()`, WinAPI `OVERLAPPED` |

> 논블로킹 vs 비동기의 차이:
> - 논블로킹: "지금 당장 데이터 있으면 줘, 없으면 에러 반환" (동기적 호출)
> - 비동기: "요청 걸어두고 나중에 콜백으로 알려줘" (완전히 분리된 완료 통지)

## Chapter 13–14. 파일 시스템

### 13-1. 파일 할당 방법

#### 연속 할당 (Contiguous Allocation)

```
파일 A: [블록 0][블록 1][블록 2]   ← 연속된 블록
```

- 디렉토리에 (시작 블록, 길이) 저장
- **장점**: 순차/랜덤 접근 모두 빠름, 단순
- **단점**: 외부 단편화, 파일 크기 사전 지정 필요, 파일 확장 어려움

#### 연결 할당 (Linked Allocation)

```
블록 5 → 블록 12 → 블록 26 → NULL   (각 블록 끝에 다음 블록 포인터)
```

- 디렉토리에 (첫 블록, 마지막 블록) 저장
- **장점**: 외부 단편화 없음, 파일 크기 유연
- **단점**: 랜덤 접근 불가(순차 탐색), 포인터 오버헤드, 포인터 손상 시 데이터 유실
- **FAT(File Allocation Table)**: 포인터를 별도 테이블로 분리 → 랜덤 접근 개선

#### 인덱스 할당 (Indexed Allocation)

```
인덱스 블록: [블록5][블록12][블록26][블록3][…]   ← 포인터 배열
```

- 디렉토리에 인덱스 블록 번호 저장
- **장점**: 외부 단편화 없음, 랜덤 접근 O(1)
- **단점**: 인덱스 블록 자체 오버헤드, 작은 파일에 낭비
- 대형 파일 → 다단계 인덱스 (indirect block) 또는 결합 방식

**비교 표**

| 방식 | 순차 접근 | 랜덤 접근 | 단편화 | 파일 확장 | 사용처 |
|------|-----------|-----------|--------|-----------|--------|
| 연속 할당 | 빠름 | 빠름 | 외부 단편화 | 어려움 | CD-ROM, 일부 DB |
| 연결 할당 | 빠름 | 느림 (O(n)) | 없음 | 쉬움 | FAT12/16 (간단 FS) |
| 인덱스 할당 | 빠름 | 빠름 (O(1)) | 없음 | 쉬움 | Unix/ext (inode) |

### 13-2. Free Space 관리

#### 비트맵 (Bit Vector)

```
블록 0~n: [1][0][1][1][0][0][1][0][…]
            ↑ 사용 중   ↑ 여유
```

- 각 블록에 1비트 → 디스크 크기 1TB / 4KB 블록 = 256MB 비트맵
- **장점**: 연속 빈 블록 찾기 효율적, CPU 비트 연산 활용
- **단점**: 비트맵을 메모리에 유지해야 함 (대용량 디스크에서 오버헤드)
- **사용처**: ext2/3/4, APFS

#### 연결 리스트 (Free List)

```
Head → [블록 5 | next→블록 12] → [블록 12 | next→블록 26] → NULL
```

- 빈 블록들을 연결 리스트로 유지
- **장점**: 추가 공간 오버헤드 없음
- **단점**: 연속 블록 탐색 비효율, 순차 탐색 필요
- 실제로는 **그루핑(Grouping)** 또는 **카운팅(Counting)** 변형 사용

### 14-1. 파일 시스템 구조

**디스크 파티션 레이아웃**

```
┌─────────────┬─────────────┬──────────────┬───────────────────┐
│ Boot Block  │ Superblock  │ Inode Table  │ Data Blocks       │
│ (MBR/VBR)  │ (FS 메타)   │ (파일 메타)  │ (실제 파일 데이터) │
└─────────────┴─────────────┴──────────────┴───────────────────┘
```

#### Boot Block (부트 블록)
- 파티션의 첫 번째 블록
- 부트로더 코드 또는 VBR(Volume Boot Record) 포함
- 파일 시스템 없이도 존재

#### Superblock (수퍼블록)
- 파일 시스템 전체의 메타데이터
- 총 블록 수, 빈 블록 수, 블록 크기, inode 수, 마운트 정보 등
- **손상 시 FS 전체 마운트 불가** → 백업 복사본 여러 블록 그룹에 유지

#### Inode (Index Node)
- 파일 1개 = inode 1개 (파일명 제외 모든 메타데이터)
- 포함 내용: 소유자, 권한, 크기, 타임스탬프, 데이터 블록 포인터
- 파일명은 디렉토리 엔트리에 저장 (inode 번호와 이름 매핑)

**ext4 inode 블록 포인터 구조**
```
Direct Pointers (12개):    블록 0~11 직접 참조 → 12 × 4KB = 48KB
Indirect (1개):            포인터 블록 → 1024 × 4KB = 4MB
Double Indirect (1개):     2단계 → 4GB
Triple Indirect (1개):     3단계 → 4TB
```

### 14-2. ext4 vs NTFS 간략 비교

| 항목 | ext4 | NTFS |
|------|------|------|
| 사용 OS | Linux | Windows |
| 최대 파일 크기 | 16TB | 256TB |
| 최대 볼륨 크기 | 1EB | 256TB |
| 저널링 | 있음 (journal/ordered/writeback) | 있음 ($LogFile) |
| 메타데이터 구조 | inode + 디렉토리 엔트리 | MFT (Master File Table) |
| 작은 파일 최적화 | inline data (extents) | MFT 내 인라인 저장 |
| ACL 지원 | POSIX ACL | Windows ACL (더 세밀) |
| 파일명 대소문자 | 구분 | 기본 미구분 |
| 단편화 | 낮음 (extents 기반) | 낮음 (자동 단편화 방지) |

**저널링 모드 (ext4)**

| 모드 | 저널 대상 | 성능 | 안전성 |
|------|-----------|------|--------|
| `journal` | 데이터 + 메타데이터 | 느림 | 최고 |
| `ordered` (기본) | 메타데이터만 (데이터 먼저 기록) | 중간 | 높음 |
| `writeback` | 메타데이터만 (순서 보장 없음) | 빠름 | 낮음 |

## Chapter 15. 파일 시스템 내부 (간략)

### 15-1. VFS (Virtual File System)

```
사용자 공간: open(), read(), write(), close()
                ↓
커널: VFS 레이어 (공통 인터페이스)
      ├── ext4 드라이버
      ├── NTFS 드라이버 (ntfs-3g)
      ├── tmpfs 드라이버
      └── NFS / 네트워크 FS 드라이버
```

- VFS는 **파일 시스템 추상화 레이어** → 애플리케이션은 구체적인 FS 몰라도 됨
- 핵심 VFS 객체:
  - **superblock object**: 마운트된 FS 표현
  - **inode object**: 특정 파일 표현
  - **dentry object**: 디렉토리 엔트리 (경로 → inode 매핑, 캐시 대상)
  - **file object**: 프로세스가 열어둔 파일 표현 (오프셋 등 포함)

### 15-2. 버퍼 캐시 & 페이지 캐시

#### 버퍼 캐시 (Buffer Cache)
- 디스크 블록 단위로 메모리에 캐시
- **목적**: 반복적인 디스크 I/O 감소
- 현대 Linux: 페이지 캐시에 통합

#### 페이지 캐시 (Page Cache)
- 파일 데이터를 **페이지(4KB) 단위**로 메모리에 캐시
- `read()` 시 → 페이지 캐시에서 먼저 확인, miss면 디스크에서 읽어 캐시에 저장
- **Write-back 정책**: 쓰기를 캐시에만 반영 후 나중에 flush (`dirty page` 관리)
- `mmap()`: 파일을 직접 페이지 캐시에 매핑 → `read()`/`write()` 시스템콜 없이 접근

**Unified Buffer Cache (통합 캐시)**
```
이전: 버퍼 캐시(디스크 블록) + 페이지 캐시(파일 데이터) 이중 캐시 → 중복
현재: 통합 페이지 캐시 — mmap과 read() 경로 모두 같은 캐시 사용
```
