## Section A: OS 면접 빈출 Top 30 Q&A

### Q1. 프로세스(Process)와 스레드(Thread)의 차이는?

프로세스는 독립된 메모리 공간(코드·데이터·힙·스택)을 가지는 실행 단위이고, 스레드는 같은 프로세스 내에서 코드·데이터·힙을 공유하되 스택만 독립적으로 가지는 실행 흐름이다. 프로세스 간 통신(IPC)은 비용이 크지만 스레드 간 통신은 공유 메모리라 빠르다. 프로세스 하나가 크래시해도 다른 프로세스에 영향이 없지만, 스레드 하나의 오류는 같은 프로세스 내 모든 스레드에 영향을 줄 수 있다.

---

### Q2. 컨텍스트 스위칭(Context Switching)이란?

CPU가 현재 실행 중인 프로세스/스레드의 상태(PC, 레지스터, 스택 포인터 등)를 PCB(Process Control Block)에 저장하고, 다음 실행할 프로세스/스레드의 상태를 복원하는 과정이다. 스위칭 자체는 유용한 작업을 하지 않는 순수 오버헤드이며, TLB 플러시와 캐시 미스를 유발한다. 스레드 간 스위칭은 같은 주소 공간을 공유하므로 프로세스 간 스위칭보다 비용이 낮다.

---

### Q3. 데드락(Deadlock)의 4가지 필요충분조건은?

1. **상호 배제(Mutual Exclusion)**: 자원을 한 번에 하나의 프로세스만 사용할 수 있다.
2. **점유 대기(Hold and Wait)**: 자원을 점유한 채 다른 자원을 기다린다.
3. **비선점(No Preemption)**: 자원을 강제로 빼앗을 수 없다.
4. **순환 대기(Circular Wait)**: 프로세스들이 순환 형태로 자원을 기다린다.

4가지 조건 중 하나만 제거해도 데드락은 발생하지 않는다. 예방(Prevention)은 조건 원천 차단, 회피(Avoidance)는 Banker's Algorithm으로 안전 상태 유지, 탐지(Detection)+회복(Recovery)은 발생 후 처리한다.

---

### Q4. 뮤텍스(Mutex)와 세마포어(Semaphore)의 차이는?

| 항목 | Mutex | Semaphore |
|---|---|---|
| 소유권 | 잠근 스레드만 해제 가능 | 누구든 signal 가능 |
| 값 범위 | 0 또는 1 (Binary) | 0 이상 정수 |
| 용도 | 상호 배제(단일 자원 보호) | 카운팅 자원 관리, 시그널링 |
| 우선순위 역전 | Priority Inheritance로 해결 가능 | 해결 어려움 |

뮤텍스는 "내가 잠근 자물쇠는 내가 연다"는 소유권 개념이 있어 임계 구역 보호에 적합하다. 세마포어는 특정 자원을 N개까지 동시에 허용할 때(예: DB 커넥션 풀) 사용한다.

---

### Q5. 가상 메모리(Virtual Memory)란?

물리 메모리 크기에 관계없이 각 프로세스가 독립적인 대형 주소 공간을 사용할 수 있게 하는 추상화 기법이다. 페이지 테이블을 통해 가상 주소를 물리 주소로 변환하며, 실제 사용 중인 페이지만 물리 메모리에 로드(Demand Paging)한다. 프로세스 간 메모리 보호, 메모리 공유(공유 라이브러리), 스왑(Swap) 공간 활용이 가능해진다.

---

### Q6. 페이지 폴트(Page Fault)란? 처리 과정은?

가상 주소에 접근했을 때 해당 페이지가 물리 메모리에 없어 발생하는 인터럽트다. 처리 과정:

1. CPU가 페이지 폴트 예외 발생
2. OS가 디스크(스왑 영역)에서 해당 페이지를 찾음
3. 빈 프레임 선택(없으면 교체 알고리즘으로 희생 페이지 선택)
4. 디스크에서 페이지를 물리 메모리로 로드
5. 페이지 테이블 갱신 후 명령어 재실행

페이지 폴트가 과도하게 발생하면 Thrashing이 된다.

---

### Q7. 캐시(Cache)란? 지역성의 원리는?

CPU와 메인 메모리 사이에 위치하는 고속 소형 메모리로, 자주 접근하는 데이터를 저장해 평균 접근 시간을 줄인다. 두 가지 지역성을 활용한다:
- **시간적 지역성(Temporal Locality)**: 최근 접근한 데이터는 곧 다시 접근될 가능성이 높다.
- **공간적 지역성(Spatial Locality)**: 접근한 주소 근처의 데이터도 곧 접근될 가능성이 높다 (캐시 라인 단위 로드).

L1(~수 KB, ~1ns) → L2(~수백 KB, ~수 ns) → L3(수 MB, ~수십 ns) → 메인 메모리(~수십 ns~수백 ns) 계층을 가진다.

---

### Q8. 동기화(Synchronization)가 필요한 이유는?

멀티스레드 환경에서 여러 스레드가 공유 자원에 동시에 접근하면 레이스 컨디션(Race Condition)이 발생한다. 예를 들어 `count++`는 읽기-수정-쓰기 3단계 연산인데, 두 스레드가 동시에 실행하면 증분이 한 번만 반영될 수 있다. 임계 구역(Critical Section)에 대한 상호 배제를 보장하여 데이터 일관성을 유지해야 한다. 또한 메모리 가시성(Memory Visibility) 문제로 인해 한 스레드의 변경이 다른 스레드에 즉시 보이지 않을 수도 있어 메모리 배리어(Memory Barrier)가 필요하다.

---

### Q9. 스레드 풀(Thread Pool)이란?

미리 생성된 스레드 집합으로, 작업 요청이 오면 유휴 스레드에 작업을 할당하고 완료 후 다시 풀로 반환하는 패턴이다. 스레드 생성/소멸 오버헤드를 제거하고, 시스템 자원 사용량을 제한하여 과부하를 방지한다. 최적 스레드 수는 CPU-bound 작업이면 `코어 수`, I/O-bound 작업이면 `코어 수 * (1 + I/O대기시간/CPU시간)` 정도가 일반적인 가이드라인이다.

---

### Q10. LRU(Least Recently Used) 페이지 교체 알고리즘은?

가장 오랫동안 사용되지 않은 페이지를 교체하는 알고리즘이다. 시간적 지역성을 기반으로 하며 이론적 성능이 우수하지만, 정확한 구현은 모든 페이지 접근을 추적해야 해 오버헤드가 크다. 실무에서는 **Clock 알고리즘(NRU: Not Recently Used)** 으로 근사 구현한다. 페이지마다 참조 비트를 두고, 시계 방향으로 순회하면서 참조 비트가 0인 페이지를 교체 대상으로 선택한다.

---

### Q11. 선점형(Preemptive)과 비선점형(Non-Preemptive) 스케줄링의 차이는?

선점형 스케줄링은 OS가 실행 중인 프로세스를 강제로 CPU에서 내릴 수 있다(예: 타임 슬라이스 만료, 높은 우선순위 프로세스 도착). 응답성이 좋고 기아(Starvation)를 방지하기 쉬우나, 컨텍스트 스위칭 오버헤드와 공유 자원 보호 복잡성이 증가한다. 비선점형은 프로세스가 자발적으로 CPU를 양보할 때까지 실행된다. 구현이 단순하지만 긴 작업이 CPU를 독점할 수 있다. 현대 OS는 대부분 선점형이다(Linux CFS, Windows MLFQ).

---

### Q12. 유저 스레드(User Thread)와 커널 스레드(Kernel Thread)의 차이는?

유저 스레드는 사용자 공간의 스레드 라이브러리가 관리하므로 커널은 인식하지 못한다. 생성/스위칭이 빠르지만, 한 스레드가 블로킹 시스템 콜을 하면 같은 프로세스의 모든 유저 스레드가 블록된다(1:N 모델). 커널 스레드는 OS가 직접 관리하며, 진정한 병렬 실행이 가능하고 한 스레드의 블로킹이 다른 스레드에 영향을 주지 않는다(1:1 모델). 현대 OS(Linux pthreads, Windows threads)는 1:1 모델을 기본으로 사용한다.

---

### Q13. TLB(Translation Lookaside Buffer)란?

페이지 테이블 조회를 가속하는 CPU 내부의 하드웨어 캐시다. 최근 사용된 가상-물리 주소 변환 쌍을 저장해, TLB 히트 시 메모리 접근 없이 즉시 물리 주소를 얻는다. 컨텍스트 스위칭 시 TLB를 플러시(flush)해야 하므로 비용이 발생한다(ASID, Address Space Identifier로 플러시 최소화 가능). 일반적으로 히트율이 99% 이상이어야 가상 메모리 성능 손실이 무시할 만하다.

---

### Q14. 스래싱(Thrashing)이란? 원인과 해결책은?

물리 메모리가 부족해 페이지 폴트가 과도하게 발생하고, OS가 페이지를 교체하는 데 대부분의 시간을 소비해 실제 작업이 거의 이루어지지 않는 상태다. 원인은 다중 프로그래밍 정도(Degree of Multiprogramming)가 너무 높을 때다. 해결책:
- **워킹 셋(Working Set) 모델**: 각 프로세스가 현재 필요한 페이지 집합을 추적해 메모리를 할당
- **페이지 폴트 빈도(Page Fault Frequency) 제어**: 폴트 빈도가 높으면 더 많은 프레임 할당, 낮으면 회수
- 프로세스 수를 줄이거나 물리 메모리를 증설

---

### Q15. COW(Copy-on-Write)란?

`fork()` 시 부모/자식 프로세스가 처음에는 같은 물리 페이지를 공유하다가, 어느 한쪽이 쓰기를 시도할 때 비로소 해당 페이지를 복사해 독립 공본을 만드는 최적화 기법이다. `exec()`을 곧바로 호출하는 경우처럼 실제로 쓰기가 일어나지 않으면 복사 비용이 전혀 발생하지 않는다. Linux의 `fork()`가 대표적이며, 문자열, STL 컨테이너, Redis의 RDB 스냅샷 등에서도 활용된다.

---

### Q16. DMA(Direct Memory Access)란?

CPU 개입 없이 I/O 장치와 메모리 간 데이터를 전송하는 메커니즘이다. CPU는 DMA 컨트롤러에 전송 시작 주소, 목적지 주소, 전송 크기를 알려주고 다른 작업을 수행한다. 전송 완료 시 DMA 컨트롤러가 인터럽트로 CPU에 알린다. CPU 사이클을 절약해 I/O 집중 시스템의 처리량을 크게 향상시킨다. 디스크 컨트롤러, 네트워크 카드, GPU 등에서 활용된다.

---

### Q17. 시스템 콜(System Call)이란?

유저 모드 프로그램이 커널이 제공하는 서비스(파일 I/O, 프로세스 생성, 네트워크 등)를 요청하는 인터페이스다. 소프트웨어 인터럽트(trap)를 발생시켜 CPU 모드를 커널 모드로 전환한 후, 커널 내 시스템 콜 핸들러가 요청을 처리하고 유저 모드로 복귀한다. 모드 전환 비용이 발생하므로 고성능 코드는 시스템 콜 횟수를 최소화한다(예: `read()` 대신 `mmap()`).

---

### Q18. 모놀리식 커널(Monolithic Kernel) vs 마이크로커널(Microkernel)은?

| 항목 | 모놀리식 커널 | 마이크로커널 |
|---|---|---|
| 구조 | 커널 기능 전부 커널 공간에 존재 | 최소 기능만 커널, 나머지는 유저 공간 서비스 |
| 성능 | 서비스 간 통신이 함수 호출이라 빠름 | IPC 오버헤드로 느릴 수 있음 |
| 안정성 | 커널 버그가 전체 시스템에 영향 | 서비스 분리로 안정성·보안 우수 |
| 예시 | Linux, Windows NT (하이브리드) | Mach, QNX, seL4 |

Linux는 모놀리식 기반이지만 로드 가능 커널 모듈(LKM)로 유연성을 확보한다.

---

### Q19. RAID(Redundant Array of Independent Disks)란?

여러 디스크를 묶어 성능과 가용성을 높이는 기술이다.

| 레벨 | 방식 | 특징 |
|---|---|---|
| RAID 0 | 스트라이핑 | 속도↑, 장애 허용 없음 |
| RAID 1 | 미러링 | 장애 허용 우수, 용량 50% |
| RAID 5 | 스트라이핑 + 분산 패리티 | 디스크 1개 장애 허용, 최소 3개 |
| RAID 6 | 스트라이핑 + 이중 패리티 | 디스크 2개 장애 허용, 최소 4개 |
| RAID 10 | RAID 1+0 | 성능+안정성, 최소 4개, 비용 높음 |

---

### Q20. inode란?

Unix/Linux 파일시스템에서 파일의 메타데이터(크기, 권한, 타임스탬프, 소유자, 데이터 블록 포인터)를 저장하는 자료구조다. 파일 이름은 디렉터리 엔트리가 보관하고 이를 inode 번호와 연결한다. 하드 링크는 같은 inode를 가리키는 여러 이름으로, inode의 링크 카운트가 0이 되면 실제 파일이 삭제된다. `ls -i`로 inode 번호를 확인할 수 있다.

---

### Q21. 스핀락(Spinlock)과 뮤텍스(Mutex)의 차이는? 언제 어떤 것을 쓰나?

스핀락은 락을 획득할 때까지 CPU를 점유하며 루프를 돈다(busy-wait). 컨텍스트 스위칭이 없어 임계 구역이 매우 짧고 대기 시간이 짧을 때 유리하다. 뮤텍스는 락이 없으면 스레드를 sleep 상태로 만들어 CPU를 양보한다. 임계 구역이 길거나 I/O를 포함하면 뮤텍스가 적합하다. **단일 코어 환경**에서는 스핀락이 항상 비효율적이다(스핀하는 동안 락 보유 스레드가 실행되지 못함). 커널 내부 인터럽트 핸들러처럼 sleep이 불가능한 컨텍스트에서는 스핀락만 사용 가능하다.

---

### Q22. 커널 모드(Kernel Mode)와 유저 모드(User Mode)란?

CPU의 권한 레벨로, 커널 모드에서는 모든 하드웨어 명령 실행과 메모리 접근이 가능하다. 유저 모드에서는 제한된 명령만 실행 가능하며, 특권 연산은 시스템 콜을 통해 커널에 위임해야 한다. 이 분리가 시스템 안정성(잘못된 유저 프로그램이 커널을 파괴하지 못함)과 보안(프로세스 간 메모리 보호)의 핵심이다. 현대 CPU는 x86의 링(Ring 0~3), ARM의 EL0~EL3 등으로 다단계 권한을 구현한다.

---

### Q23. 인터럽트(Interrupt)란? 하드웨어 인터럽트와 소프트웨어 인터럽트의 차이는?

인터럽트는 CPU의 현재 실행 흐름을 중단하고 특정 핸들러(ISR: Interrupt Service Routine)를 실행하게 하는 메커니즘이다.
- **하드웨어 인터럽트**: I/O 완료, 타이머, 키보드 입력 등 외부 장치가 비동기적으로 발생시킨다.
- **소프트웨어 인터럽트(Trap/Exception)**: 시스템 콜, 제로 나눗셈, 페이지 폴트처럼 프로그램 실행 중 동기적으로 발생한다.

인터럽트가 발생하면 현재 레지스터 상태를 저장하고 IDT(Interrupt Descriptor Table)로 핸들러를 찾아 실행한 뒤 복귀한다.

---

### Q24. PCB(Process Control Block)에 담기는 정보는?

OS가 프로세스를 관리하기 위해 유지하는 자료구조다. 포함 정보:
- **식별자**: PID, 부모 PID
- **CPU 상태**: 레지스터, PC, 스택 포인터 (컨텍스트 스위칭 시 저장/복원)
- **프로세스 상태**: New / Ready / Running / Waiting / Terminated
- **메모리 관리 정보**: 페이지 테이블 포인터, 세그먼트 테이블
- **스케줄링 정보**: 우선순위, 누적 CPU 시간
- **I/O 상태**: 열린 파일 디스크립터 목록

### Q25. 파이프(Pipe)와 소켓(Socket)의 차이는?

| 항목 | 파이프 | 소켓 |
|---|---|---|
| 통신 범위 | 같은 호스트의 관련 프로세스 간 | 네트워크를 통한 다른 호스트 간도 가능 |
| 방향성 | 단방향(익명 파이프), 양방향(Named Pipe) | 양방향 |
| 주소 지정 | 없음 (부모-자식 관계로 연결) | IP:Port 또는 Unix Socket Path |
| 사용 예 | `ls | grep "foo"`, `popen()` | HTTP 서버, TCP/UDP 통신 |

익명 파이프는 `fork()` 후 부모-자식 간에만 사용한다. Named Pipe(FIFO)는 파일시스템 경로로 비관련 프로세스도 사용 가능하다.

### Q26. 세그멘테이션(Segmentation)과 페이징(Paging)의 차이는?

| 항목 | 세그멘테이션 | 페이징 |
|---|---|---|
| 분할 단위 | 논리적 의미 단위 (코드, 스택, 힙) | 고정 크기 페이지 (4KB 등) |
| 외부 단편화 | 발생 | 발생 안 함 |
| 내부 단편화 | 발생 안 함 | 발생 가능 |
| 보호 | 세그먼트별 권한 설정 용이 | 페이지 단위 권한 설정 |
| 현대 OS | x86에서 평탄화(flat)되어 사실상 비사용 | 페이지+세그먼트 혼합(x86 Protected Mode) |

현대 OS는 주로 페이징을 사용하며, x86의 세그멘테이션은 사실상 비활성화 상태다.

### Q27. 페이지 프레임(Frame)과 페이지(Page)의 차이는?

**페이지(Page)**는 가상 주소 공간을 고정 크기로 나눈 단위고, **프레임(Frame)**은 물리 메모리를 같은 크기로 나눈 단위다. 가상 주소의 페이지 번호가 페이지 테이블을 통해 물리 메모리의 프레임 번호로 매핑된다. 페이지와 프레임의 크기는 동일해야 한다(일반적으로 4KB, 2MB, 1GB 대용량 페이지도 지원).

---

### Q28. 워킹 셋(Working Set) 모델이란?

프로세스가 특정 시간 구간 내에 실제로 참조한 페이지들의 집합이다. 워킹 셋 크기만큼의 물리 프레임이 확보되어야 Thrashing 없이 원활히 실행된다. OS는 각 프로세스의 워킹 셋을 추적해 메모리 할당량을 동적으로 조절한다. 전체 워킹 셋 합이 사용 가능한 물리 메모리를 초과하면 일부 프로세스를 스왑 아웃시켜 나머지 프로세스의 실행을 보장한다.

---

### Q29. CFS(Completely Fair Scheduler)란?

Linux의 기본 CPU 스케줄러로, 각 프로세스에 CPU 시간을 공평하게 분배하는 것을 목표로 한다. **vruntime(virtual runtime)** 이라는 가중치 적용 실행 시간을 추적하며, 항상 vruntime이 가장 작은(즉, 가장 덜 실행된) 프로세스를 선택한다. Red-Black Tree로 vruntime을 관리해 O(log n) 스케줄링을 달성한다. nice 값(-20~+19)으로 가중치를 조절할 수 있으며, `cgroups`와 결합해 컨테이너 자원 제한에 활용된다.

---

### Q30. fork()와 exec()은 어떻게 동작하나?

`fork()`는 현재 프로세스의 복사본을 만들어 새 프로세스를 생성한다. 부모에게는 자식의 PID를, 자식에게는 0을 반환한다. COW로 인해 실제 메모리 복사는 쓰기 시점까지 지연된다. `exec()`는 현재 프로세스의 주소 공간을 새로운 실행 파일로 완전히 교체한다. PID는 유지되고 파일 디스크립터는 상속된다. 셸은 `fork()`로 자식을 만들고 자식이 `exec()`으로 명령어를 실행하는 `fork-exec` 패턴을 사용한다.

### B-1. Thread Safety와 메모리 가시성

**Thread-safe**란 여러 스레드가 동시에 호출해도 올바른 결과를 보장하는 코드를 말한다. 세 가지 위협:

1. **레이스 컨디션**: 결과가 실행 순서에 의존
2. **데드락**: 두 스레드가 서로의 락을 기다림
3. **메모리 가시성**: CPU 캐시/컴파일러 재정렬로 인해 변경 내용이 다른 코어에 즉시 반영 안 됨

C++의 `std::atomic`과 메모리 오더링(`memory_order_acquire/release/seq_cst`)이 가시성 문제를 해결한다.

### B-2. 동기화 도구 실전

#### Mutex — 상호 배제

```cpp
// C++
#include <mutex>
#include <thread>

std::mutex mtx;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(mtx);  // RAII: 스코프 종료 시 자동 해제
    ++counter;
}
```

#### Semaphore — 리소스 카운팅

```cpp
// C++17 (세마포어 없음, condition_variable로 구현)
#include <mutex>
#include <condition_variable>

class Semaphore {
    int count;
    std::mutex mtx;
    std::condition_variable cv;
public:
    explicit Semaphore(int n) : count(n) {}
    void acquire() {
        std::unique_lock<std::mutex> lk(mtx);
        cv.wait(lk, [this]{ return count > 0; });
        --count;
    }
    void release() {
        std::unique_lock<std::mutex> lk(mtx);
        ++count;
        cv.notify_one();
    }
};
```

#### Condition Variable — 조건 대기

```cpp
// C++ — Producer-Consumer 조건 대기
std::queue<int> queue;
std::mutex mtx;
std::condition_variable cv;

void producer(int val) {
    {
        std::lock_guard<std::mutex> lk(mtx);
        queue.push(val);
    }
    cv.notify_one();  // 대기 중인 소비자 하나를 깨움
}

int consumer() {
    std::unique_lock<std::mutex> lk(mtx);
    // Spurious wakeup 방지를 위해 람다로 조건 확인
    cv.wait(lk, []{ return !queue.empty(); });
    int val = queue.front();
    queue.pop();
    return val;
}
```

#### ReadWrite Lock — 읽기 병렬, 쓰기 배타

```cpp
// C++17
#include <shared_mutex>

std::shared_mutex rwmtx;
std::map<int, std::string> cache;

std::string read(int key) {
    std::shared_lock<std::shared_mutex> lk(rwmtx);  // 읽기 — 동시 허용
    return cache.at(key);
}

void write(int key, const std::string& val) {
    std::unique_lock<std::shared_mutex> lk(rwmtx);  // 쓰기 — 배타적
    cache[key] = val;
}
```

### B-3. Lock-Free / Wait-Free 개념

| 보장 수준 | 정의 | 예시 |
|---|---|---|
| **Blocking** | 락을 기다리는 동안 블록됨 | Mutex |
| **Lock-Free** | 전체 시스템 진행 보장 (일부 스레드는 재시도 가능) | CAS 루프 |
| **Wait-Free** | 모든 스레드가 유한 단계 내에 완료 보장 | 구현 복잡, 드묾 |

Lock-Free 스택(Treiber Stack):

```cpp
template<typename T>
class LockFreeStack {
    struct Node {
        T data;
        Node* next;
        Node(T val) : data(val), next(nullptr) {}
    };
    std::atomic<Node*> head{nullptr};
public:
    void push(T val) {
        Node* node = new Node(val);
        do {
            node->next = head.load(std::memory_order_relaxed);
        } while (!head.compare_exchange_weak(node->next, node,
                                              std::memory_order_release,
                                              std::memory_order_relaxed));
    }
    // ABA 문제 주의: 실제로는 tagged pointer 또는 hazard pointer 사용
};
```

> **ABA 문제**: CAS에서 A→B→A 변경을 A가 그대로인 것으로 오인하는 문제. 버전 태그나 Hazard Pointer로 해결.

### B-4. 패턴: Producer-Consumer

```cpp
// C++ — Bounded Buffer (유계 버퍼)
#include <queue>
#include <mutex>
#include <condition_variable>

template<typename T>
class BoundedQueue {
    std::queue<T> q;
    const size_t maxSize;
    std::mutex mtx;
    std::condition_variable notFull, notEmpty;
public:
    explicit BoundedQueue(size_t n) : maxSize(n) {}

    void produce(T item) {
        std::unique_lock<std::mutex> lk(mtx);
        notFull.wait(lk, [this]{ return q.size() < maxSize; });
        q.push(std::move(item));
        notEmpty.notify_one();
    }

    T consume() {
        std::unique_lock<std::mutex> lk(mtx);
        notEmpty.wait(lk, [this]{ return !q.empty(); });
        T item = std::move(q.front());
        q.pop();
        notFull.notify_one();
        return item;
    }
};
```

### B-5. 패턴: Thread Pool 구현

```cpp
// C++ — 간단한 스레드 풀
#include <vector>
#include <queue>
#include <functional>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <future>

class ThreadPool {
    std::vector<std::thread> workers;
    std::queue<std::function<void()>> tasks;
    std::mutex mtx;
    std::condition_variable cv;
    bool stop = false;
public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i) {
            workers.emplace_back([this] {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lk(mtx);
                        cv.wait(lk, [this]{ return stop || !tasks.empty(); });
                        if (stop && tasks.empty()) return;
                        task = std::move(tasks.front());
                        tasks.pop();
                    }
                    task();
                }
            });
        }
    }

    template<typename F, typename... Args>
    auto enqueue(F&& f, Args&&... args) -> std::future<std::invoke_result_t<F, Args...>> {
        using RetType = std::invoke_result_t<F, Args...>;
        auto promise = std::make_shared<std::packaged_task<RetType()>>(
            std::bind(std::forward<F>(f), std::forward<Args>(args)...));
        std::future<RetType> result = promise->get_future();
        {
            std::unique_lock<std::mutex> lk(mtx);
            tasks.emplace([promise]{ (*promise)(); });
        }
        cv.notify_one();
        return result;
    }

    ~ThreadPool() {
        { std::unique_lock<std::mutex> lk(mtx); stop = true; }
        cv.notify_all();
        for (auto& w : workers) w.join();
    }
};
```

### B-7. 패턴: Actor Model

Actor는 독립적인 상태를 가지고, 메시지 전달만으로 통신하는 동시성 단위다. 공유 메모리와 락을 사용하지 않아 데드락을 구조적으로 방지한다.

```cpp
// C++ — 단일 스레드 mailbox 기반 Actor 개념 구현
#include <functional>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <thread>

class CounterActor {
    std::queue<std::function<void()>> mailbox;
    std::mutex mtx;
    std::condition_variable cv;
    std::thread worker;
    bool stopped = false;
    int count = 0;
public:
    CounterActor() : worker([this] {
        while (true) {
            std::function<void()> msg;
            {
                std::unique_lock<std::mutex> lk(mtx);
                cv.wait(lk, [this]{ return stopped || !mailbox.empty(); });
                if (stopped && mailbox.empty()) return;
                msg = std::move(mailbox.front());
                mailbox.pop();
            }
            msg();  // 액터 전용 단일 스레드에서 실행 — 동시 접근 없음
        }
    }) {}

    void tell(std::function<void()> msg) {
        { std::lock_guard<std::mutex> lk(mtx); mailbox.push(std::move(msg)); }
        cv.notify_one();
    }
    void increment() { tell([this]{ ++count; }); }
    ~CounterActor() {
        { std::lock_guard<std::mutex> lk(mtx); stopped = true; }
        cv.notify_all();
        worker.join();
    }
};
```

### B-8. 언어별 멀티스레딩

#### C++ — std::thread / mutex / atomic / future

```cpp
#include <thread>
#include <mutex>
#include <atomic>
#include <future>
#include <iostream>

std::atomic<int> sharedCounter{0};

void workerAtomic() {
    for (int i = 0; i < 1000; ++i)
        sharedCounter.fetch_add(1, std::memory_order_relaxed);
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 4; ++i)
        threads.emplace_back(workerAtomic);

```

메모리 오더링 요약:

| 오더 | 설명 |
|---|---|
| `memory_order_relaxed` | 순서 보장 없음, 원자성만 보장. 카운터에 적합 |
| `memory_order_acquire` | 이후 읽기가 이전으로 재정렬 불가 |
| `memory_order_release` | 이전 쓰기가 이후로 재정렬 불가 |
| `memory_order_acq_rel` | acquire + release |
| `memory_order_seq_cst` | 전체 순서 보장, 기본값. 가장 강하고 느림 |

```cpp
// acquire/release 패턴 — 생산자/소비자 플래그
#include <atomic>
#include <cassert>

std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;                                    // 일반 쓰기
    ready.store(true, std::memory_order_release); // release: 이전 쓰기가 이 store 이후로 재정렬 불가
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)); // acquire: 이후 읽기가 이 load 이전으로 재정렬 불가
    assert(data == 42);                             // 반드시 42를 읽음이 보장됨
}
```

        printFirst();
        sem12.release();

        sem12.acquire();
        printSecond();
        sem23.release();

    }
};

#### [LC 1115] Print FooBar Alternately

```cpp
// C++ — 두 세마포어로 교대 실행
#include <semaphore>

class FooBar {
    int n;
    std::binary_semaphore fooSem{1}, barSem{0};
public:
    FooBar(int n) : n(n) {}

    void foo(std::function<void()> printFoo) {
        for (int i = 0; i < n; ++i) {
            fooSem.acquire();
            printFoo();
            barSem.release();
        }
    }
    void bar(std::function<void()> printBar) {
        for (int i = 0; i < n; ++i) {
            barSem.acquire();
            printBar();
            fooSem.release();
        }
    }
};
```

#### [LC 1226] Dining Philosophers

```cpp
// C++ — 짝수 번호 철학자는 왼쪽 먼저, 홀수는 오른쪽 먼저 (순환 대기 방지)
#include <mutex>
#include <functional>

class DiningPhilosophers {
    std::mutex forks[5];
public:
    void wantsToEat(int philosopher,
                    std::function<void()> pickLeftFork,
                    std::function<void()> pickRightFork,
                    std::function<void()> eat,
                    std::function<void()> putLeftFork,
                    std::function<void()> putRightFork) {
        int left  = philosopher;
        int right = (philosopher + 1) % 5;
        // 짝수 철학자: 작은 번호 포크 먼저 (데드락 방지)
        if (philosopher % 2 == 0) {
            std::lock(forks[left], forks[right]);
        } else {
            std::lock(forks[right], forks[left]);
        }
        std::lock_guard<std::mutex> lgLeft(forks[left],   std::adopt_lock);
        std::lock_guard<std::mutex> lgRight(forks[right], std::adopt_lock);
        pickLeftFork(); pickRightFork();
        eat();
        putLeftFork(); putRightFork();
    }
};
```

## Section C: 한 장 요약 — 면접 직전 5분 복습

### 프로세스 & 스레드

```
프로세스: 독립 메모리 (코드/데이터/힙/스택) → IPC 통신
스레드:  공유 힙/코드, 독립 스택 → 빠른 통신, 동기화 필요
PCB:    PID, 레지스터, 페이지테이블, 파일디스크립터
상태:   New → Ready → Running → Waiting → Terminated
fork(): COW 복사, exec(): 주소공간 교체
```

### 스케줄링

```
FCFS → SJF → SRTF → Round Robin → Priority → MLFQ
선점형: 타임슬라이스 만료 시 강제 교체
Linux CFS: vruntime 기준 Red-Black Tree, O(log n)
```

### 메모리 관리

```
가상메모리: 페이지테이블로 VA→PA 변환, TLB로 캐시
페이지폴트: 디스크에서 로드 → 테이블 갱신 → 재실행
교체알고리즘: OPT > LRU ≈ Clock(NRU) > FIFO
Thrashing: 워킹셋 초과 → 폴트 폭증 → 스왑 지옥
COW: fork 후 쓰기 시점에만 복사
세그멘테이션: 논리 단위 분할, 외부단편화
페이징: 고정크기, 내부단편화, 현대 OS 표준
```

### 동기화 & 교착상태

```
임계구역 3요건: 상호배제 / 진행 / 유한대기
뮤텍스: 소유권 있음, 단일 자원
세마포어: 카운팅, 시그널링 가능
스핀락: busy-wait, 짧은 임계구역, 커널 ISR
데드락 4조건: 상호배제 / 점유대기 / 비선점 / 순환대기
Banker's: 안전 순서 계산으로 데드락 회피
```

### 멀티스레딩 핵심

```
Thread Safety: 레이스컨디션 + 메모리가시성 해결
Lock-Free: CAS 루프, ABA 문제 주의
False Sharing: 캐시라인(64B) 분리로 해결
Producer-Consumer: condition_variable 기반 BoundedQueue
Thread Pool: 스레드 재사용, CPU수 ≈ 코어수(CPU-bound)
C++: std::mutex/atomic/future/shared_mutex/condition_variable
memory_order: relaxed(카운터) → acquire/release(플래그) → seq_cst(기본)
```

### 파일시스템 & 저장장치

```
inode: 메타데이터 + 블록 포인터, 하드링크 = 동일 inode
파일시스템: ext4(저널링), NTFS(MFT), FAT32(단순)
RAID: 0(속도) / 1(미러) / 5(패리티 1개) / 6(패리티 2개) / 10(1+0)
DMA: CPU 개입 없이 I/O↔메모리 직접 전송
```

### 인터럽트 & 시스템 콜

```
인터럽트: 하드웨어(비동기) vs 트랩/예외(동기)
시스템콜: 유저모드 → 트랩 → 커널모드 → 처리 → 복귀
커널구조: 모놀리식(Linux) vs 마이크로커널(QNX/seL4)
```
