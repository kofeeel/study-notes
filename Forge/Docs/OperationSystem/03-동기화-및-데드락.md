## 1. Race Condition & Critical Section

### Race Condition 이란?

두 개 이상의 프로세스/스레드가 **공유 데이터에 동시에 접근**하고, 실행 순서에 따라 결과가 달라지는 상황.

```c
// 전형적인 Race Condition 예시 — 은행 계좌
// 초기 balance = 1000

// Thread A                      // Thread B
int tmp = balance;               int tmp = balance;   // 둘 다 1000 읽음
tmp = tmp + 500;                 tmp = tmp - 200;
balance = tmp;                   balance = tmp;
// 결과: balance = 1500 OR 800  (1300이 되어야 함)
```

**CPU 명령어 레벨 분해** — `balance++` 는 원자적이지 않다:

```
LOAD  R1, balance    ; R1 = 5
ADD   R1, 1          ; R1 = 6
STORE balance, R1    ; balance = 6
```

컨텍스트 스위치가 LOAD와 STORE 사이에 발생하면 갱신 손실(lost update) 발생.

---

### Critical Section (임계 구역)

**공유 자원에 접근하는 코드 영역**. 한 번에 하나의 프로세스만 실행해야 한다.

```
while (true) {
    [entry section]      // 진입 허가 요청
    critical section     // 공유 자원 접근
    [exit section]       // 진입 허가 반납
    remainder section    // 나머지 코드
}
```

### Critical Section 해결을 위한 3가지 요구조건

| # | 조건 | 설명 |
|---|------|------|
| 1 | **Mutual Exclusion (상호 배제)** | 한 프로세스가 CS 실행 중이면 다른 프로세스는 진입 불가 |
| 2 | **Progress (진행)** | CS를 실행 중인 프로세스가 없고 진입을 원하는 프로세스가 있으면, 진입 결정이 무한정 연기되지 않아야 함 |
| 3 | **Bounded Waiting (한정 대기)** | 한 프로세스가 진입 요청 후 허가받기까지 다른 프로세스가 CS에 진입하는 횟수에 상한이 존재 |

> 💡 **면접 포인트**: 세 조건을 순서대로 외우되, **Progress vs Bounded Waiting의 차이**를 명확히 설명할 수 있어야 한다. Progress는 "결국 누군가는 들어가야 한다"(starvation 방지 아님), Bounded Waiting은 "특정 프로세스가 무한 대기하지 않는다"(starvation 방지).

## 2. Peterson's Solution

소프트웨어 기반 해결책. **두 프로세스(i, j)** 에 대해 3가지 요구조건 모두 만족.

```c
// 공유 변수
int turn;           // 누구 차례인지
bool flag[2];       // 진입 의사 표명

// Process Pi (i=0 or 1, j=1-i)
void process_i() {
    while (true) {
        // Entry Section
        flag[i] = true;          // "나 들어가고 싶다"
        turn = j;                // "상대방 먼저 해도 된다"
        while (flag[j] && turn == j)
            ;  // busy-wait: 상대가 원하고 상대 차례면 대기

        // Critical Section
        /* ... 공유 자원 접근 ... */

        // Exit Section
        flag[i] = false;         // "나 다 했다"

        // Remainder Section
        /* ... */
    }
}
```

**정확성 증명:**
- **상호 배제**: Pi와 Pj 둘 다 CS에 있으려면 `flag[i]=true && turn==i` 이고 동시에 `flag[j]=true && turn==j` 여야 하는데, turn은 동시에 i와 j가 될 수 없으므로 모순.
- **진행**: 어느 쪽도 CS에 없을 때 while 조건이 false가 되어 진입 가능.
- **한정 대기**: Pi가 대기 중이면 `turn==j`이고, Pj가 CS를 나오면 `flag[j]=false`가 되어 Pi는 최대 1회만 기다린다.

> 💡 **면접 포인트**: Peterson's solution은 **load/store가 원자적**이라는 가정 하에 동작한다. 현대 CPU의 instruction reordering 때문에 실제로는 **memory barrier**(fence 명령어)가 필요하다.

## 3. 하드웨어 동기화 기법

### 3.1 Memory Barrier (Memory Fence)

CPU와 컴파일러의 명령어 재정렬(reordering)을 막는 명령어.

```c
// x86: mfence, lfence, sfence
// ARM: DMB, DSB, ISB
// GCC: __sync_synchronize()
__sync_synchronize();   // full memory barrier
```

### 3.2 test_and_set (TAS)

```c
// 하드웨어가 원자적으로 실행하는 명령어
bool test_and_set(bool *target) {
    bool rv = *target;
    *target = true;    // 항상 true로 설정
    return rv;         // 이전 값 반환
}

// 사용 예시 — Lock 구현
bool lock = false;

void acquire_lock() {
    while (test_and_set(&lock))   // lock이 false였으면 진입, true면 대기
        ;  // busy-wait (spin-lock)
}

void release_lock() {
    lock = false;
}
```

> TAS 기반 단순 mutex는 **Bounded Waiting을 보장하지 않는다** — 특정 스레드가 영원히 못 들어갈 수 있음. bounded waiting 보장을 위해 waiting array 필요.

### 3.3 Compare-And-Swap (CAS) — 현대 CPU의 핵심

```c
// 하드웨어 원자 명령어
int compare_and_swap(int *value, int expected, int new_value) {
    int temp = *value;
    if (*value == expected)
        *value = new_value;
    return temp;   // 이전 값 반환
}

// Lock 구현
int lock = 0;  // 0: free, 1: held

void acquire_lock() {
    while (compare_and_swap(&lock, 0, 1) != 0)
        ;  // lock이 0이 아니면 계속 대기
}

void release_lock() {
    lock = 0;
}
```

**CAS 기반 Lock-Free 스택 예시:**

```c
typedef struct Node {
    int value;
    struct Node *next;
} Node;

Node *top = NULL;

void push(int val) {
    Node *new_node = malloc(sizeof(Node));
    new_node->value = val;
    do {
        new_node->next = top;
    } while (!__sync_bool_compare_and_swap(&top, new_node->next, new_node));
    // CAS 실패 시(다른 스레드가 top 변경) 재시도
}
```

> 💡 **면접 포인트**: CAS는 **ABA problem**이 있다. A→B→A로 변경된 후 CAS가 A를 보고 변경 없음으로 판단하는 오류. 해결: **tagged pointer**(버전 번호 부착) 또는 C++의 `std::atomic` + 버전 카운터 조합.

## 4. Mutex Lock

**가장 단순한 동기화 도구**. 한 번에 하나의 스레드만 lock 획득 가능.

```c
// POSIX pthread mutex
#include <pthread.h>

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void critical_section() {
    pthread_mutex_lock(&mutex);     // acquire
    /* ... 공유 자원 접근 ... */
    pthread_mutex_unlock(&mutex);   // release
}
```

### Spinlock vs Blocking Mutex

| | Spinlock | Blocking Mutex |
|---|---|---|
| 대기 방식 | busy-wait (CPU 소모) | sleep (CPU 반납) |
| 적합한 CS 길이 | 매우 짧음 (수 사이클) | 길 수 있음 |
| Context Switch | 없음 | 있음 |
| 멀티코어 | 효율적 | 단일 코어도 OK |
| 사용처 | 커널 인터럽트 핸들러 | 일반 애플리케이션 |

> 💡 **면접 포인트**: Spinlock은 **멀티코어 환경에서 CS가 짧을 때** 유리하다. 단일 코어에서 spinlock을 쓰면 lock을 가진 스레드가 CPU를 못 받아 deadlock처럼 동작할 수 있다.

## 5. Semaphore

정수형 변수 S로 여러 자원을 관리하거나 순서를 제어.

```c
// 세마포어 두 연산 (원자적으로 실행)
wait(S):   // P 연산, acquire
    while (S <= 0) ;   // busy-wait 또는 sleep
    S--;

signal(S): // V 연산, release
    S++;
```

### Binary Semaphore vs Counting Semaphore

```c
// Binary Semaphore (= Mutex처럼 동작)
semaphore mutex = 1;

wait(mutex);
/* critical section */
signal(mutex);

// Counting Semaphore — 자원 3개 관리
semaphore resource = 3;

wait(resource);    // 자원 1개 획득 (S: 3→2)
/* 자원 사용 */
signal(resource);  // 자원 반납 (S: 2→3)
```

### Semaphore 구현 (sleep/wakeup 버전)

```c
typedef struct {
    int value;
    struct process *waiting_list;
} semaphore;

void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        // 프로세스를 waiting list에 추가
        add_to_list(S->waiting_list, current_process);
        block();   // 프로세스 sleep
    }
}

void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        // waiting list에서 하나 꺼냄
        struct process *p = remove_from_list(S->waiting_list);
        wakeup(p);  // 프로세스 깨움
    }
}
```

> 💡 **면접 포인트**: value < 0인 경우 `|value|`가 대기 중인 프로세스 수를 나타낸다. `wait()`와 `signal()` 자체도 임계 구역이므로 단일 CPU에서는 **인터럽트 비활성화**, 멀티CPU에서는 **spinlock**으로 보호.

### Semaphore로 실행 순서 제어

```c
// S1이 S2보다 먼저 실행되어야 할 때
semaphore sync = 0;

// Thread 1
S1;
signal(sync);   // S1 완료 알림

// Thread 2
wait(sync);     // S1 완료 대기
S2;
```

## 6. Monitor & Condition Variable

**고수준 동기화 추상화**. 상호 배제를 자동으로 보장하여 프로그래머 실수를 줄인다.

### Monitor 구조

```
monitor monitor_name {
    // 공유 변수 선언
    shared variable declarations;

    // 진입할 때 자동으로 mutual exclusion 획득
    procedure P1(...) { ... }
    procedure P2(...) { ... }

    // 초기화 코드
    initialization code(...) { ... }
}
```

- Monitor 내부는 **한 번에 하나의 프로세스**만 활성화
- Condition variable로 **내부에서 대기/신호** 처리

### Condition Variable

```c
condition x, y;

x.wait();    // 호출 프로세스 일시 중단, monitor 잠금 해제
x.signal();  // wait 중인 프로세스 하나 재개 (없으면 no-op)
```

**signal-and-wait vs signal-and-continue:**

| | signal-and-wait (Hoare) | signal-and-continue (Mesa) |
|---|---|---|
| signal() 후 | signaler가 대기, signaled 즉시 실행 | signaled가 ready queue에 추가, signaler 계속 실행 |
| 조건 재확인 | if 문 OK | **while 문 필수** |
| 구현 난이도 | 복잡 | 단순 (실제 언어에서 사용) |
| 사용 언어 | 이론적 | C++ `condition_variable`, POSIX (실제 구현) |

### C++ `std::mutex` / `std::condition_variable`

```cpp
#include <mutex>
#include <condition_variable>
#include <vector>

class BoundedBuffer {
    std::vector<int> buffer;
    int count = 0, in = 0, out = 0;
    std::mutex mtx;
    std::condition_variable cv;  // 단일 condition variable (notifyAll 패턴)

public:
    explicit BoundedBuffer(int size) : buffer(size) {}

    // Monitor entry — unique_lock이 mutual exclusion 보장
    void produce(int item) {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, [this] { return count < (int)buffer.size(); });  // Mesa semantics: while 대신 predicate
        buffer[in] = item;
        in = (in + 1) % buffer.size();
        count++;
        cv.notify_all();  // 대기 중인 모든 스레드 깨움
    }

    int consume() {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, [this] { return count > 0; });
        int item = buffer[out];
        out = (out + 1) % buffer.size();
        count--;
        cv.notify_all();
        return item;
    }
};
```

> 💡 **면접 포인트**: C++의 `condition_variable::wait(lock, predicate)`는 Mesa semantics이므로 **predicate를 while 루프와 동등하게** 내부에서 재확인한다. `notify_one()`은 임의의 스레드 하나를 깨우고, `notify_all()`은 전부 깨운다. Spurious wakeup 때문에도 predicate 재확인이 필요하다.

### C++ `std::mutex` + 두 개의 `std::condition_variable`

```cpp
#include <mutex>
#include <condition_variable>
#include <vector>

class BoundedBuffer {
    std::vector<int> buffer;
    int count = 0, in = 0, out = 0;
    std::mutex mtx;
    std::condition_variable not_full;   // producer 대기용
    std::condition_variable not_empty;  // consumer 대기용

public:
    explicit BoundedBuffer(int size) : buffer(size) {}

    void produce(int item) {
        std::unique_lock<std::mutex> lock(mtx);
        not_full.wait(lock, [this] { return count < (int)buffer.size(); });  // buffer full — 대기
        buffer[in] = item;
        in = (in + 1) % buffer.size();
        count++;
        not_empty.notify_one();  // consumer 깨움
    }

    int consume() {
        std::unique_lock<std::mutex> lock(mtx);
        not_empty.wait(lock, [this] { return count > 0; });  // buffer empty — 대기
        int item = buffer[out];
        out = (out + 1) % buffer.size();
        count--;
        not_full.notify_one();  // producer 깨움
        return item;
    }
};
```

## 7. Mutex vs Semaphore vs Monitor 비교

| 특성 | Mutex Lock | Counting Semaphore | Binary Semaphore | Monitor |
|------|-----------|-------------------|-----------------|---------|
| **소유 개념** | O (lock 소유자만 unlock) | X | X | O (내부 프로시저) |
| **자원 수** | 1 | N개 | 1 | 1 (내부 자동) |
| **순서 제어** | X | O | O | O (condition var) |
| **상호 배제** | O | O (binary일 때) | O | O (자동) |
| **실수 가능성** | 낮음 | 높음 (wait/signal 순서 착오) | 높음 | 낮음 (언어 지원) |
| **언어 지원** | pthread, C++ std | POSIX sem | POSIX sem | C++ `condition_variable`, POSIX |
| **DeadLock 위험** | 중간 | 높음 (wait/signal 누락) | 높음 | 낮음 |
| **사용 사례** | 단순 mutual exclusion | 연결 풀, 리소스 풀 | 이진 신호 | 복잡한 조건 동기화 |

**실수 패턴 비교:**

```c
// Semaphore 실수 1: signal 먼저 → mutual exclusion 위반
signal(mutex);
critical_section();   // 다른 프로세스도 동시 진입 가능
wait(mutex);

// Semaphore 실수 2: wait 두 번 → deadlock
wait(mutex);
critical_section();
wait(mutex);          // 자기 자신을 deadlock

// Semaphore 실수 3: wait/signal 누락
wait(mutex);
critical_section();
// signal 없음 → 다른 프로세스 영원히 대기

// Monitor: 컴파일러/언어가 entry/exit 자동 처리 → 위 실수 불가
```

> 💡 **면접 포인트**: Mutex와 Binary Semaphore의 차이 — **Mutex는 소유 개념**이 있어 lock을 획득한 스레드만 unlock 가능. Semaphore는 한 스레드가 wait()하고 다른 스레드가 signal()해도 된다(신호 전달용도).

## 8. 고전적 동기화 문제 — 완전 코드

### 8.1 Bounded-Buffer Problem (생산자-소비자)

**문제**: 고정 크기 버퍼를 공유하는 생산자/소비자 스레드 동기화

```c
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <stdlib.h>

#define BUFFER_SIZE 5

typedef int item;
item buffer[BUFFER_SIZE];
int in = 0, out = 0;

sem_t empty;   // 빈 슬롯 개수 (초기값: BUFFER_SIZE)
sem_t full;    // 채워진 슬롯 개수 (초기값: 0)
pthread_mutex_t mutex;  // 버퍼 접근 mutual exclusion

void *producer(void *arg) {
    item next_produced;
    while (1) {
        next_produced = rand() % 100;   // 아이템 생산

        sem_wait(&empty);               // 빈 슬롯 대기 (empty--)
        pthread_mutex_lock(&mutex);     // 버퍼 잠금

        buffer[in] = next_produced;
        in = (in + 1) % BUFFER_SIZE;
        printf("Produced: %d\n", next_produced);

        pthread_mutex_unlock(&mutex);   // 버퍼 잠금 해제
        sem_post(&full);               // 채워진 슬롯 증가 (full++)
    }
    return NULL;
}

void *consumer(void *arg) {
    item next_consumed;
    while (1) {
        sem_wait(&full);                // 채워진 슬롯 대기 (full--)
        pthread_mutex_lock(&mutex);     // 버퍼 잠금

        next_consumed = buffer[out];
        out = (out + 1) % BUFFER_SIZE;
        printf("Consumed: %d\n", next_consumed);

        pthread_mutex_unlock(&mutex);   // 버퍼 잠금 해제
        sem_post(&empty);              // 빈 슬롯 증가 (empty++)
    }
    return NULL;
}

int main() {
    pthread_t prod_tid, cons_tid;

    sem_init(&empty, 0, BUFFER_SIZE);  // 초기 빈 슬롯 = BUFFER_SIZE
    sem_init(&full,  0, 0);            // 초기 채워진 슬롯 = 0
    pthread_mutex_init(&mutex, NULL);

    pthread_create(&prod_tid, NULL, producer, NULL);
    pthread_create(&cons_tid, NULL, consumer, NULL);

    pthread_join(prod_tid, NULL);
    pthread_join(cons_tid, NULL);

    sem_destroy(&empty);
    sem_destroy(&full);
    pthread_mutex_destroy(&mutex);
    return 0;
}
```

**동작 분석:**
- `empty`: 생산자가 버퍼 다 찼을 때 대기, 소비자가 소비 후 신호
- `full`: 소비자가 버퍼 비었을 때 대기, 생산자가 생산 후 신호
- `mutex`: 버퍼 배열 접근 시 상호 배제

> 💡 **면접 포인트**: **wait 순서가 중요하다** — 항상 `sem_wait(empty/full)` 먼저, `mutex_lock` 나중. 반대로 하면 deadlock 가능 (`mutex` 잡고 `empty` 대기 → 소비자가 `mutex`를 못 잡아 `full`을 signal 못함).

### 8.2 Readers-Writers Problem

**문제**: 공유 데이터에 여러 Reader는 동시 접근 가능, Writer는 단독 접근.

#### 1st Readers-Writers (Reader 우선 — Writer Starvation 가능)

```c
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>

sem_t rw_mutex;      // writer와 reader 간 mutual exclusion
pthread_mutex_t mutex;   // read_count 보호
int read_count = 0;  // 현재 읽고 있는 reader 수

void *writer(void *arg) {
    int id = *(int *)arg;
    while (1) {
        sem_wait(&rw_mutex);      // write lock 획득
        // --- Writing ---
        printf("Writer %d: writing\n", id);
        sem_post(&rw_mutex);      // write lock 해제
    }
    return NULL;
}

void *reader(void *arg) {
    int id = *(int *)arg;
    while (1) {
        pthread_mutex_lock(&mutex);
        read_count++;
        if (read_count == 1)      // 첫 번째 reader가 writer 차단
            sem_wait(&rw_mutex);
        pthread_mutex_unlock(&mutex);

        // --- Reading --- (다수 reader 동시 가능)
        printf("Reader %d: reading\n", id);

        pthread_mutex_lock(&mutex);
        read_count--;
        if (read_count == 0)      // 마지막 reader가 writer 허용
            sem_post(&rw_mutex);
        pthread_mutex_unlock(&mutex);
    }
    return NULL;
}
```

#### 2nd Readers-Writers (Writer 우선 — Reader Starvation 가능)

```c
// 추가 변수
sem_t read_mutex;     // reader 진입 gate
sem_t rw_mutex;       // writer exclusive lock
pthread_mutex_t rmutex, wmutex;  // 카운터 보호
int read_count = 0, write_count = 0;

void *writer(void *arg) {
    while (1) {
        pthread_mutex_lock(&wmutex);
        write_count++;
        if (write_count == 1)     // 첫 writer: reader 진입 차단
            sem_wait(&read_mutex);
        pthread_mutex_unlock(&wmutex);

        sem_wait(&rw_mutex);      // 단독 write lock
        printf("Writer: writing\n");
        sem_post(&rw_mutex);

        pthread_mutex_lock(&wmutex);
        write_count--;
        if (write_count == 0)     // 마지막 writer: reader 허용
            sem_post(&read_mutex);
        pthread_mutex_unlock(&wmutex);
    }
    return NULL;
}

void *reader(void *arg) {
    while (1) {
        sem_wait(&read_mutex);    // writer 대기 중이면 여기서 block
        pthread_mutex_lock(&rmutex);
        read_count++;
        if (read_count == 1)
            sem_wait(&rw_mutex);
        pthread_mutex_unlock(&rmutex);
        sem_post(&read_mutex);    // 다음 reader 허용

        printf("Reader: reading\n");

        pthread_mutex_lock(&rmutex);
        read_count--;
        if (read_count == 0)
            sem_post(&rw_mutex);
        pthread_mutex_unlock(&rmutex);
    }
    return NULL;
}
```

**실무 대안 — pthread_rwlock:**

```c
pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

// Reader
pthread_rwlock_rdlock(&rwlock);   // 다수 reader 동시 허용
/* ... read ... */
pthread_rwlock_unlock(&rwlock);

// Writer
pthread_rwlock_wrlock(&rwlock);   // 단독 접근
/* ... write ... */
pthread_rwlock_unlock(&rwlock);
```

> 💡 **면접 포인트**: 1st variant는 reader가 계속 오면 writer가 starvation. 2nd variant는 writer가 대기 중이면 새 reader를 막아 writer를 우선시. 실무에서는 `pthread_rwlock`이나 C++17의 `std::shared_mutex` 사용.

### 8.3 Dining Philosophers Problem

**문제**: 5명의 철학자, 5개의 젓가락(각 사이에 1개). 양쪽 젓가락 모두 집어야 식사 가능.

#### 세마포어 해결책 (DeadLock 위험 있는 버전 → 해결 버전)

```c
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>

#define N 5
#define LEFT  (i)
#define RIGHT ((i + 1) % N)

sem_t chopstick[N];   // 각 젓가락 = semaphore (초기값 1)

// DeadLock 위험한 버전 (모두 왼쪽 집으면 deadlock)
void philosopher_unsafe(int i) {
    sem_wait(&chopstick[LEFT]);    // 왼쪽 젓가락
    sem_wait(&chopstick[RIGHT]);   // 오른쪽 젓가락
    /* eat */
    sem_post(&chopstick[LEFT]);
    sem_post(&chopstick[RIGHT]);
}

// 해결책 1: 비대칭 — 짝수 번호는 왼쪽 먼저, 홀수는 오른쪽 먼저
void philosopher_asymmetric(int i) {
    if (i % 2 == 0) {
        sem_wait(&chopstick[LEFT]);
        sem_wait(&chopstick[RIGHT]);
    } else {
        sem_wait(&chopstick[RIGHT]);
        sem_wait(&chopstick[LEFT]);
    }
    printf("Philosopher %d eating\n", i);
    sem_post(&chopstick[LEFT]);
    sem_post(&chopstick[RIGHT]);
}

// 해결책 2: 최대 4명만 동시 시도 (비둘기집 원리로 항상 하나는 양쪽 가능)
sem_t room;  // 초기값 4 (N-1)

void philosopher_room(int i) {
    sem_wait(&room);               // 식탁에 앉을 자리 확보
    sem_wait(&chopstick[LEFT]);
    sem_wait(&chopstick[RIGHT]);
    printf("Philosopher %d eating\n", i);
    sem_post(&chopstick[RIGHT]);
    sem_post(&chopstick[LEFT]);
    sem_post(&room);               // 자리 반납
}
```

#### 모니터 해결책 (상태 기반 — Starvation-Free)

```c
#include <pthread.h>
#include <stdio.h>

#define N 5
#define THINKING 0
#define HUNGRY   1
#define EATING   2
#define LEFT  ((i + N - 1) % N)
#define RIGHT ((i + 1) % N)

int state[N];                    // 각 철학자 상태
pthread_mutex_t monitor_mutex;  // monitor lock
pthread_cond_t  cond[N];        // 각 철학자 condition variable

void test(int i) {
    // 내가 배고프고 양쪽이 먹고 있지 않을 때만 먹기 시작
    if (state[i] == HUNGRY &&
        state[LEFT]  != EATING &&
        state[RIGHT] != EATING) {
        state[i] = EATING;
        pthread_cond_signal(&cond[i]);  // 자신을 깨움 (pickup에서 대기 중)
    }
}

void pickup(int i) {
    pthread_mutex_lock(&monitor_mutex);
    state[i] = HUNGRY;
    test(i);                        // 바로 먹을 수 있는지 확인
    while (state[i] != EATING)      // 못 먹으면 대기
        pthread_cond_wait(&cond[i], &monitor_mutex);
    pthread_mutex_unlock(&monitor_mutex);
}

void putdown(int i) {
    pthread_mutex_lock(&monitor_mutex);
    state[i] = THINKING;
    test(LEFT);    // 왼쪽 이웃이 먹을 수 있는지 확인
    test(RIGHT);   // 오른쪽 이웃이 먹을 수 있는지 확인
    pthread_mutex_unlock(&monitor_mutex);
}

void *philosopher(void *arg) {
    int i = *(int *)arg;
    while (1) {
        printf("Philosopher %d thinking\n", i);
        /* think */
        pickup(i);
        printf("Philosopher %d eating\n", i);
        /* eat */
        putdown(i);
    }
    return NULL;
}

int main() {
    pthread_t tids[N];
    int ids[N];
    pthread_mutex_init(&monitor_mutex, NULL);
    for (int i = 0; i < N; i++) {
        ids[i] = i;
        state[i] = THINKING;
        pthread_cond_init(&cond[i], NULL);
    }
    for (int i = 0; i < N; i++)
        pthread_create(&tids[i], NULL, philosopher, &ids[i]);
    for (int i = 0; i < N; i++)
        pthread_join(tids[i], NULL);
    return 0;
}
```

> 💡 **면접 포인트**: 세마포어 해결책의 세 가지 DeadLock 방지법 — (1) 최대 N-1명 동시 시도, (2) 비대칭 집기, (3) 양쪽 모두 가능할 때만 집기(원자적). 모니터 해결책은 starvation도 방지하려면 추가 fairness 로직 필요(FIFO 대기열).

### 9.2 futex (Fast Userspace muTEX)

**사용자 공간 + 커널 공간 혼합** — 경쟁이 없을 때는 커널 개입 없이 사용자 공간에서 처리.

```c
#include <linux/futex.h>
#include <sys/syscall.h>
#include <stdatomic.h>

// futex 기반 mutex (간략화)
typedef struct {
    atomic_int state;   // 0: unlocked, 1: locked (no waiters), 2: locked (waiters)
} futex_mutex_t;

void futex_lock(futex_mutex_t *m) {
    int c;
    // Fast path: unlocked → locked (커널 개입 없음)
    if ((c = atomic_compare_exchange_strong(&m->state, &(int){0}, 1)) == 0)
        return;
    // Slow path: 이미 잠겨 있음 → 커널에 sleep 요청
    do {
        if (c == 2 || atomic_compare_exchange_strong(&m->state, &(int){1}, 2))
            syscall(SYS_futex, &m->state, FUTEX_WAIT, 2, NULL, NULL, 0);
    } while ((c = atomic_compare_exchange_strong(&m->state, &(int){0}, 2)) != 0);
}

void futex_unlock(futex_mutex_t *m) {
    if (atomic_fetch_sub(&m->state, 1) != 1) {
        atomic_store(&m->state, 0);
        // 대기자 있으면 커널에 wake 요청
        syscall(SYS_futex, &m->state, FUTEX_WAKE, 1, NULL, NULL, 0);
    }
}
```

> 💡 **면접 포인트**: futex는 **경쟁이 없는 경우 커널 시스템 콜 없이** 사용자 공간 CAS만으로 lock/unlock 완료. 경쟁이 발생할 때만 커널을 호출. glibc의 `pthread_mutex_t`가 내부적으로 futex를 사용.

## 10. Deadlock

### 10.1 4가지 필요조건 (Coffman, 1971)

4가지 **모두 동시에** 성립해야 deadlock 발생. 하나라도 깨면 deadlock 불가.

| # | 조건 | 설명 |
|---|------|------|
| 1 | **Mutual Exclusion (상호 배제)** | 자원은 한 번에 하나의 프로세스만 사용 가능 |
| 2 | **Hold and Wait (점유 대기)** | 자원을 가진 채로 다른 자원을 기다림 |
| 3 | **No Preemption (비선점)** | 자원을 강제로 빼앗을 수 없음, 자발적 반납만 가능 |
| 4 | **Circular Wait (순환 대기)** | P1→R1→P2→R2→P1 형태의 순환 대기 사슬 |

```
DeadLock 발생 필요충분조건:
4가지 모두 필요조건이지만, RAG(Resource Allocation Graph)에 cycle이 있어도
자원 인스턴스가 여러 개면 deadlock이 아닐 수 있다.
자원 인스턴스가 1개씩이면 cycle = deadlock.
```

### 10.2 Resource Allocation Graph (RAG)

```
노드: 
  - 원(○): 프로세스 (P1, P2, P3)
  - 사각형(□): 자원 (R1, R2) — 내부 점이 인스턴스 수

간선:
  - Request edge:  Pi → Rj  (Pi가 Rj를 요청 중)
  - Assignment edge: Rj → Pi (Rj 인스턴스가 Pi에 할당됨)

Deadlock 판별:
  - 사이클 없음 → deadlock 없음
  - 사이클 있음 + 각 자원 인스턴스 1개 → deadlock
  - 사이클 있음 + 자원 인스턴스 여러 개 → deadlock일 수도, 아닐 수도
```

**RAG 예시 (deadlock):**
```
P1 → R1 → P2 → R2 → P1    (cycle → deadlock, 각 자원 1개 인스턴스)
```

**RAG 예시 (no deadlock despite cycle):**
```
R1 (2개 인스턴스): →P1, →P2
P3 → R1              (P3가 R1 요청)
P2 → R2 → P3         (P2가 R2 요청, P3가 R2 보유)

P1이 R1 반납하면 P3 진행 가능 → cycle 있지만 deadlock 아님
```

### 10.3 Deadlock Prevention (예방)

4가지 조건 중 하나를 원천 차단.

| 조건 차단 | 방법 | 단점 |
|----------|------|------|
| Mutual Exclusion | read-only 자원은 공유 허용 | 본질적으로 배타적 자원은 불가 |
| Hold and Wait | 실행 전 모든 자원 한꺼번에 요청 | 자원 낭비, starvation 가능 |
| No Preemption | 자원 강제 선점 허용 | 상태 저장/복원 복잡, CPU/메모리만 적합 |
| Circular Wait | **자원 번호 부여, 오름차순으로만 요청** | 프로그래밍 제약, 번호 설계 어려움 |

**Circular Wait 방지 — 자원 순서 정하기:**

```c
// 자원에 전역 번호 부여: mutex_account(1) < mutex_db(2) < mutex_log(3)
// 항상 번호 오름차순으로만 획득

// 올바른 순서
pthread_mutex_lock(&mutex_account);  // (1)
pthread_mutex_lock(&mutex_db);       // (2) > (1) OK
/* ... */
pthread_mutex_unlock(&mutex_db);
pthread_mutex_unlock(&mutex_account);

// 잘못된 순서 (circular wait 가능)
pthread_mutex_lock(&mutex_db);       // (2)
pthread_mutex_lock(&mutex_account);  // (1) < (2) → 위험!
```

### 10.4 Deadlock Avoidance — Banker's Algorithm

**안전 상태(Safe State)**: 모든 프로세스가 순서대로 실행 완료 가능한 상태.  
시스템이 항상 안전 상태를 유지하도록 자원 요청을 조건부 허가.

#### 핵심 자료구조 (n개 프로세스, m개 자원 유형)

```
Available[m]      : 현재 사용 가능한 각 자원 인스턴스 수
Max[n][m]         : 프로세스 i가 자원 j를 최대 몇 개 요청할 수 있는지
Allocation[n][m]  : 현재 프로세스 i에 할당된 자원 j의 수
Need[n][m]        : 프로세스 i가 앞으로 추가로 필요한 자원 j의 수
                    Need[i][j] = Max[i][j] - Allocation[i][j]
```

#### Safety Algorithm (안전 상태 검사)

```
1. Work = Available 복사
   Finish[i] = false for all i

2. Find i such that:
   - Finish[i] == false
   - Need[i] <= Work  (모든 j에 대해 Need[i][j] <= Work[j])

3. If found:
   Work = Work + Allocation[i]   (Pi 완료, 자원 반납)
   Finish[i] = true
   goto step 2

4. If Finish[i] == true for all i → SAFE STATE
   Otherwise → UNSAFE STATE
```

#### Resource-Request Algorithm (자원 요청 처리)

```
Request_i = Pi의 자원 요청 벡터

1. If Request_i > Need[i] → error (최대 요구 초과)

2. If Request_i > Available → wait (자원 부족)

3. Pretend to allocate:
   Available    = Available - Request_i
   Allocation[i] = Allocation[i] + Request_i
   Need[i]      = Need[i] - Request_i

4. Run Safety Algorithm:
   - SAFE → 실제로 할당 허가
   - UNSAFE → 롤백, Pi 대기
```

#### Banker's Algorithm 단계별 예제

**초기 상태 (5 프로세스, 3 자원 A,B,C):**

```
         Allocation    Max      Available
         A  B  C    A  B  C    A  B  C
P0       0  1  0    7  5  3    3  3  2
P1       2  0  0    3  2  2
P2       3  0  2    9  0  2
P3       2  1  1    2  2  2
P4       0  0  2    4  3  3
```

```
Need = Max - Allocation:
         A  B  C
P0       7  4  3
P1       1  2  2
P2       6  0  0
P3       0  1  1
P4       4  3  1
```

**Safety Check:**

```
Step 1: Work = [3,3,2], Finish = [F,F,F,F,F]

Step 2-3:
  P1: Need[1]=[1,2,2] <= Work=[3,3,2]? YES
      Work = [3,3,2] + [2,0,0] = [5,3,2], Finish[1]=T

  P3: Need[3]=[0,1,1] <= Work=[5,3,2]? YES
      Work = [5,3,2] + [2,1,1] = [7,4,3], Finish[3]=T

  P4: Need[4]=[4,3,1] <= Work=[7,4,3]? YES
      Work = [7,4,3] + [0,0,2] = [7,4,5], Finish[4]=T

  P0: Need[0]=[7,4,3] <= Work=[7,4,5]? YES
      Work = [7,4,5] + [0,1,0] = [7,5,5], Finish[0]=T

  P2: Need[2]=[6,0,0] <= Work=[7,5,5]? YES
      Work = [7,5,5] + [3,0,2] = [10,5,7], Finish[2]=T

Safe Sequence: <P1, P3, P4, P0, P2>  → SAFE STATE
```

**P1이 Request=[1,0,2] 요청:**

```
1. Request[1]=[1,0,2] <= Need[1]=[1,2,2]? YES
2. Request[1]=[1,0,2] <= Available=[3,3,2]? YES
3. Pretend:
   Available    = [3,3,2] - [1,0,2] = [2,3,0]
   Allocation[1]= [2,0,0] + [1,0,2] = [3,0,2]
   Need[1]      = [1,2,2] - [1,0,2] = [0,2,0]

4. Safety Check with Work=[2,3,0]:
   P1: Need=[0,2,0] <= [2,3,0]? YES → Work=[2,3,0]+[3,0,2]=[5,3,2]
   P3: Need=[0,1,1] <= [5,3,2]? YES → Work=[5,3,2]+[2,1,1]=[7,4,3]
   ... (이하 동일)
   → SAFE → 요청 허가
```

> 💡 **면접 포인트**: Banker's Algorithm의 **한계** — (1) 프로세스 수 N, 자원 종류 M이 고정이라는 비현실적 가정, (2) 최대 자원 요구를 사전에 알아야 함, (3) O(N²M) 복잡도로 실시간 시스템에 부적합. 실제 OS(Linux, Windows)는 Deadlock Avoidance를 **사용하지 않는다**.

### 10.5 Deadlock Detection & Recovery

#### 단일 인스턴스 자원 — Wait-for Graph

```
Wait-for Graph: RAG에서 자원 노드 제거
Pi → Pj: Pi가 Pj의 자원 반납을 기다림

사이클 탐지 = DFS, O(n²)
```

#### 다중 인스턴스 자원 — Detection Algorithm

Safety Algorithm과 유사하나 **현재 상태** 기준으로 실행.

```
자료구조:
  Available[m]      — 현재 가용 자원
  Allocation[n][m]  — 현재 할당
  Request[n][m]     — 현재 요청 (Need 아님!)

알고리즘:
  Work = Available
  Finish[i] = (Allocation[i] == 0) ? true : false

  Find i: Finish[i]==false && Request[i] <= Work
  If found: Work += Allocation[i], Finish[i] = true, repeat
  
  Finish[i]==false인 프로세스 집합 → DeadLocked Processes
```

#### Recovery 방법

| 방법 | 설명 | 단점 |
|------|------|------|
| **Process Termination** | 교착 프로세스 모두 종료 | 많은 연산 손실 |
| **Selective Termination** | 사이클 깰 때까지 하나씩 종료 | 오버헤드 |
| **Resource Preemption** | 자원 강제 선점 | Starvation, 롤백 복잡 |

**프로세스 선택 기준 (Victim Selection):**
- 지금까지 사용한 CPU 시간 (적을수록 선택)
- 보유 자원 수 (많을수록 선택)
- 완료까지 남은 시간
- 프로세스 우선순위

> 💡 **면접 포인트**: Detection + Recovery는 **deadlock이 드물 때** 적합. 감지 알고리즘 실행 빈도를 결정해야 하는데, 너무 자주 실행하면 오버헤드, 너무 드물게 실행하면 deadlock 지속 시간 증가.

## 11. 실무 데드락 시나리오

### 11.1 데이터베이스 Lock — 트랜잭션 교착

```sql
-- Transaction T1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Lock row 1
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- Wait for row 2

-- Transaction T2 (동시 실행)
BEGIN;
UPDATE accounts SET balance = balance - 50  WHERE id = 2;  -- Lock row 2
UPDATE accounts SET balance = balance + 50  WHERE id = 1;  -- Wait for row 1
-- → Circular Wait → DeadLock
```

**DB Deadlock 해결:**
- **Timeout**: 일정 시간 대기 후 하나 rollback (가장 일반적)
- **Wait-for Graph**: DB 엔진이 자동 감지 후 victim 선택 (MySQL InnoDB, PostgreSQL)
- **Consistent Lock Ordering**: 항상 ID 오름차순으로 row 잠금

```c
// C 예시 — CAS 기반 낙관적 락으로 deadlock 방지
// version 카운터를 원자적으로 비교 후 업데이트
typedef struct {
    int balance;
    atomic_int version;  // 낙관적 락: 충돌 감지, 재시도
} Account;

bool update_balance(Account *acc, int expected_ver, int delta) {
    // CAS로 버전 확인 후 업데이트 — 충돌 시 실패 반환, 호출자가 재시도
    return atomic_compare_exchange_strong(&acc->version,
                                          &expected_ver, expected_ver + 1);
}
```

### 11.2 분산 시스템 Deadlock

```
서비스 A → 서비스 B 호출 (HTTP, lock B's resource)
서비스 B → 서비스 A 호출 (HTTP, lock A's resource)
→ 분산 Circular Wait
```

**해결 방법:**
- **Circuit Breaker**: 응답 지연 감지 시 빠른 실패 (Resilience4j, Hystrix)
- **Timeout + Retry with backoff**: 모든 원격 호출에 timeout 필수
- **Saga Pattern**: 분산 트랜잭션 대신 보상 트랜잭션 사용
- **Lock-Free/Optimistic Design**: 가능하면 낙관적 동시성 제어

### 11.3 C++ 멀티스레딩 Deadlock 예시 및 감지

```cpp
// DeadLock 재현
#include <mutex>
#include <thread>
#include <chrono>
#include <cstdio>

std::mutex lockA, lockB;

void thread1() {
    std::unique_lock<std::mutex> a(lockA);
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::unique_lock<std::mutex> b(lockB);  // lockB 대기 → DeadLock
    printf("T1 got both\n");
}

void thread2() {
    std::unique_lock<std::mutex> b(lockB);
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::unique_lock<std::mutex> a(lockA);  // lockA 대기 → DeadLock
    printf("T2 got both\n");
}

int main() {
    std::thread t1(thread1);
    std::thread t2(thread2);
    t1.join();  // 영원히 block
    t2.join();
    // → DeadLock
}
```

**C++ DeadLock 감지 — gdb:**
```bash
# gdb로 프로세스에 attach 후 스레드 덤프
gdb -p <pid>
(gdb) thread apply all bt   # 모든 스레드 백트레이스 출력

# 출력 예시:
# Thread 1 (LWP 1234):
#   #0  __lll_lock_wait () ...
#   #1  pthread_mutex_lock () ...
#   #2  thread1() ...
# Thread 2 (LWP 1235):
#   #0  __lll_lock_wait () ...
#   #1  pthread_mutex_lock () ...
#   #2  thread2() ...
# → 두 스레드가 서로의 mutex를 기다리는 순환 구조 확인
```

**컴파일 타임/런타임 감지 — ThreadSanitizer (TSan):**
```bash
# 빌드 시 TSan 활성화 (gcc/clang)
g++ -fsanitize=thread -g -o deadlock_demo deadlock_demo.cpp

# 실행하면 TSan이 데드락 및 데이터 레이스 자동 감지
./deadlock_demo
# WARNING: ThreadSanitizer: lock-order-inversion (potential deadlock)
#   Thread T1 locks mutex M1 while holding mutex M2
#   Thread T2 locks mutex M2 while holding mutex M1

# 해결책: std::lock()으로 여러 mutex를 원자적으로 동시 획득
std::lock(lockA, lockB);  // deadlock-free multi-lock
std::unique_lock<std::mutex> la(lockA, std::adopt_lock);
std::unique_lock<std::mutex> lb(lockB, std::adopt_lock);
```

## 12. 핵심 요약 — 면접 치트시트

### Critical Section 3요구조건

```
상호 배제 → 동시에 하나만
진행      → 결국 누군가는 들어감 (무한 연기 없음)
한정 대기 → 굶어 죽지 않음 (대기 횟수 상한 존재)
```

### 동기화 도구 선택 기준

```
단순 mutual exclusion (1개 자원):  → Mutex Lock
N개 자원 관리 (연결 풀 등):        → Counting Semaphore
실행 순서 제어 (A after B):        → Semaphore(0으로 초기화)
복잡한 조건 동기화:                 → Monitor + Condition Variable
Read 많고 Write 드문 구조:         → pthread_rwlock / std::shared_mutex
Lock-Free 필요:                    → CAS / Atomic 연산
```

### Deadlock 4조건 vs 해결 전략

```
조건              예방(Prevention)     회피(Avoidance)    감지(Detection)
상호 배제         공유 가능 자원만      -                  -
점유 대기         선점 or 일괄 요청     Banker's           Wait-for Graph
비선점            선점 허용            -                  -
순환 대기         자원 순서 강제        -                  -
전체              -                   Banker's + Safe    DFS + Recovery
```

### Banker's Algorithm 핵심 공식

```
Need[i][j] = Max[i][j] - Allocation[i][j]

Safe State: 모든 프로세스를 완료할 수 있는 실행 순서 존재
요청 허가: Request <= Need AND Request <= Available AND 결과가 Safe State
```

### 고전 문제 해결 요약

| 문제 | 세마포어 구성 | 핵심 포인트 |
|------|------------|------------|
| Bounded-Buffer | empty(N) + full(0) + mutex(1) | wait 순서: empty/full 먼저, mutex 나중 |
| Readers-Writers | rw_mutex(1) + mutex(1) + read_count | 1st: reader 우선, 2nd: writer 우선 |
| Dining Philosophers | chopstick[N](1) + room(N-1) | 비대칭 또는 최대 N-1명 허용 |

### 면접 자주 나오는 질문 & 핵심 답변

**Q: Mutex와 Semaphore의 차이는?**
> A: Mutex는 소유권 개념이 있어 lock을 획득한 스레드만 unlock 가능. Semaphore는 소유권 없음 — wait()한 스레드와 signal()한 스레드가 달라도 됨 (신호 전달 패턴 가능). Binary Semaphore != Mutex.

**Q: Deadlock과 Starvation의 차이는?**
> A: Deadlock은 관련 프로세스 모두가 진행 불가(영원히 대기). Starvation은 특정 프로세스만 자원을 계속 못 받음 — 다른 프로세스는 정상 동작. Deadlock은 항상 Starvation이지만, Starvation이 항상 Deadlock은 아님.

**Q: Peterson's Solution이 현대 CPU에서 동작하지 않는 이유는?**
> A: 현대 CPU와 컴파일러는 성능을 위해 메모리 접근 순서를 재배열(reordering)함. Peterson's에서 `flag[i]=true`와 `turn=j` 순서가 보장되어야 하는데, 재배열로 깨질 수 있음. Memory Barrier(fence)로 해결.

**Q: 왜 wait()를 while 루프 안에 써야 하나?**
> A: (1) Mesa semantics — signal() 후 즉시 실행 보장 안 됨, 다른 스레드가 먼저 조건 변경 가능. (2) Spurious wakeup — OS가 이유 없이 스레드를 깨울 수 있음. 두 경우 모두 조건 재확인 필요.

**Q: Banker's Algorithm을 실제 OS가 사용하지 않는 이유?**
> A: (1) 프로세스가 시작 전에 최대 자원 요구량을 선언해야 함 (비현실적). (2) 자원 수와 프로세스 수가 동적으로 변함. (3) O(N²M) 연산 비용. Linux는 deadlock을 그냥 허용하고 application이 처리하게 함.
