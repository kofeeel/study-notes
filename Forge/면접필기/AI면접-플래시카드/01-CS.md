## 프로세스 · 스레드

<details>
<summary><b>Q1. 프로세스와 스레드의 차이는?</b></summary>

- **프로세스** = 독립된 메모리 공간(코드·데이터·힙·스택). 통신은 IPC, 하나가 죽어도 다른 프로세스는 무관(크래시 격리).
- **스레드** = 프로세스 안에서 코드·데이터·힙을 **공유**하고 **스택만 독립**. 통신이 빠르고 컨텍스트 스위칭이 가볍지만, 하나가 죽으면 프로세스 전체가 영향받음.
- 한 줄: "스레드는 메모리를 공유하는 실행 흐름, 프로세스는 메모리를 격리한 실행 단위."

</details>

<details>
<summary><b>Q2. 컨텍스트 스위칭이란? 비용은 왜 드나?</b></summary>

실행 중인 프로세스/스레드의 상태(PC, 레지스터, SP)를 PCB에 저장하고 다음 것의 상태를 복원하는 일.
비용: 저장/복원 자체 + **캐시·TLB가 무효화**되어 뒤이어 캐시 미스가 늘어남. 같은 프로세스의 스레드 간 스위칭은 주소공간이 같아 TLB 플러시가 없어 더 저렴.

</details>

<details>
<summary><b>Q3. 프로세스 상태 전이를 말해보세요.</b></summary>

New → Ready → Running → (Waiting ↔) → Terminated.
Running에서 I/O 요청하면 Waiting, 완료되면 Ready로 복귀. 타임슬라이스가 끝나면 Running → Ready(선점).

</details>

## 스케줄링

<details>
<summary><b>Q4. CPU 스케줄링 알고리즘 종류와 특징은?</b></summary>

- **FCFS**: 도착 순. 긴 작업이 앞에 오면 전체 대기 증가(convoy).
- **SJF**: 짧은 작업 우선. 평균 대기시간 최소지만 긴 작업 기아 가능.
- **Round Robin**: 타임슬라이스 순환. 응답성 좋음, 슬라이스가 너무 작으면 스위칭 비용 증가.
- **MLFQ**: 다단계 큐 + 피드백. 짧은 작업은 높은 큐, CPU를 오래 쓰면 강등. 현대 OS 표준(적응형).

</details>

<details>
<summary><b>Q5. 선점형과 비선점형 스케줄링 차이는?</b></summary>

- **비선점**: 실행 중인 프로세스가 스스로 CPU를 놓을 때까지 유지. 단순하지만 응답성 나쁨.
- **선점**: 타이머 인터럽트나 더 높은 우선순위 도착 시 강제로 CPU 회수. 응답성 좋지만 공유 데이터 동기화가 필요해짐.

</details>

## 동기화

<details>
<summary><b>Q6. Race Condition이란? 예시로 설명하세요.</b></summary>

여러 스레드가 공유 자원에 동시 접근해 실행 순서에 따라 결과가 달라지는 상황.
예) `count++`는 읽기→수정→쓰기 3단계라, 두 스레드가 동시에 읽으면 둘 다 같은 값에 +1 해서 한 번 증가가 사라짐. 해결은 임계구역을 뮤텍스로 보호하거나 atomic 연산 사용.

</details>

<details>
<summary><b>Q7. 뮤텍스와 세마포어의 차이는?</b></summary>

- **뮤텍스**: 소유권 있음(잠근 스레드만 해제). 0/1. 단일 자원의 상호배제용.
- **세마포어**: 소유권 없음, 0 이상 카운팅. N개 자원 관리나 스레드 간 시그널링(생산자-소비자)에 사용.
- 한 줄: "뮤텍스는 자물쇠, 세마포어는 입장권 카운터."

</details>

<details>
<summary><b>Q8. 스핀락은 언제 쓰나?</b></summary>

락을 얻을 때까지 잠들지 않고 busy-wait으로 돌며 확인하는 락. 컨텍스트 스위칭 비용이 없어 **임계구역이 매우 짧고 멀티코어**일 때 유리. 오래 기다리면 CPU만 태우므로 긴 구간엔 뮤텍스.

</details>

<details>
<summary><b>Q9. 데드락 4조건과 대응 방법은?</b></summary>

암기 "**상점비순**": **상**호배제 / **점**유대기 / **비**선점 / **순**환대기. 넷 다 성립해야 발생하므로 하나만 깨면 됨.
- 예방: 조건 하나를 구조적으로 차단(예: 락 획득 순서 고정 → 순환대기 제거)
- 회피: Banker's 알고리즘(안전 상태만 허용)
- 탐지·회복: 주기적으로 검출 후 프로세스 강제 종료

</details>

<details>
<summary><b>Q10. CAS(Compare-And-Swap)란?</b></summary>

"메모리 값이 기대값과 같으면 새 값으로 바꾸고, 아니면 실패"를 **원자적**으로 수행하는 하드웨어 명령. lock-free 자료구조와 `std::atomic`의 기반. 실패 시 재시도 루프로 락 없이 동기화.

</details>

## 메모리

<details>
<summary><b>Q11. 가상 메모리란? 왜 쓰나?</b></summary>

프로세스마다 독립된 큰 가상 주소공간을 주고, MMU가 페이지 테이블로 물리 주소로 변환하는 구조.
이점: ① 프로세스 간 격리·보호 ② 물리 메모리보다 큰 공간 ③ 실제 쓰는 페이지만 로드(Demand Paging) ④ 공유·스왑 가능.

</details>

<details>
<summary><b>Q12. 페이지 폴트 처리 흐름을 단계별로 말해보세요.</b></summary>

1. CPU가 가상주소 접근 → 2. MMU가 페이지 테이블 조회, present 비트 없음 → 3. 페이지 폴트 예외, OS로 제어 이동 → 4. 디스크(스왑)에서 페이지 탐색 → 5. 빈 프레임에 로드(없으면 교체 알고리즘으로 하나 내보냄) → 6. 페이지 테이블 갱신 → 7. 중단된 명령어 재실행.
폴트가 과다하면 **스래싱**(실행보다 스왑에 시간 소비).

</details>

<details>
<summary><b>Q13. TLB란?</b></summary>

가상→물리 주소 변환 결과를 캐싱하는 작은 하드웨어 캐시. 페이지 테이블은 메모리에 있어 매번 조회하면 느리므로, TLB 히트 시 수 사이클에 변환 완료. 컨텍스트 스위칭 시 플러시되거나 ASID로 구분.

</details>

<details>
<summary><b>Q14. 내부 단편화와 외부 단편화 차이는?</b></summary>

- **내부**: 할당 단위(페이지)보다 실제 사용이 작아 블록 안에 남는 낭비. 고정 분할·페이징에서 발생.
- **외부**: 빈 공간 총합은 충분한데 조각나서 연속 할당이 안 되는 것. 가변 분할에서 발생. 페이징이 해결.

</details>

<details>
<summary><b>Q15. 페이지 교체 알고리즘을 비교하세요.</b></summary>

- **FIFO**: 먼저 들어온 것 교체. 단순하지만 Belady's anomaly(프레임 늘려도 폴트 증가).
- **LRU**: 가장 오래 안 쓴 것 교체. 지역성에 근거해 성능 좋지만 구현 비용 큼.
- **Clock**: 참조 비트로 LRU 근사. 실제 OS에서 흔히 사용.
- **Optimal**: 앞으로 가장 늦게 쓸 것 교체. 이론적 최적, 미래를 몰라 실현 불가(비교 기준용).

</details>

<details>
<summary><b>Q16. 스택과 힙의 차이는?</b></summary>

- **스택**: 함수 호출 프레임(지역변수, 리턴주소). LIFO, 컴파일러가 자동 관리, 매우 빠름, 크기 제한(오버플로 위험).
- **힙**: `new`/`malloc` 동적 할당. 크기 자유, 수명을 프로그래머가 관리(누수·단편화 위험), 할당이 상대적으로 느림.
게임에선 힙 할당을 프레임 중 피하려고 풀링·프리할당을 씀.

</details>

## 캐시 · 컴퓨터구조

<details>
<summary><b>Q17. 캐시가 왜 필요하고, 지역성이란?</b></summary>

CPU와 DRAM 속도 차이가 수백 배(Memory Wall)라 그 사이에 작고 빠른 메모리를 둠.
- **시간 지역성**: 최근 쓴 데이터를 곧 다시 씀(루프 변수).
- **공간 지역성**: 인접 주소를 곧 씀(배열 순회). 캐시는 64B 라인 단위로 가져오므로 배열이 연결리스트보다 빠른 이유.

</details>

<details>
<summary><b>Q18. 캐시 친화적 코드란?</b></summary>

공간 지역성을 살리는 코드. 예) 2차원 배열은 행 우선 저장이므로 안쪽 루프를 열(j)로 돌려 연속 접근. 포인터 체이싱(연결리스트, 가상함수 다형 컨테이너)은 프리패처가 예측 못 해 느림. 게임에서 AoS 대신 **SoA**로 데이터를 배치하는 것도 같은 이유(ECS의 근거).

</details>

<details>
<summary><b>Q19. Write-through와 Write-back 차이는?</b></summary>

- **Write-through**: 캐시와 메모리에 동시에 씀. 일관성 쉽고 단순하지만 매 쓰기가 느림.
- **Write-back**: 캐시에만 쓰고 dirty 비트 표시, 라인 교체 때 메모리에 반영. 빠르지만 일관성 관리 복잡. 현대 CPU L1/L2 표준.

</details>

<details>
<summary><b>Q20. False Sharing이란?</b></summary>

서로 다른 변수가 같은 캐시 라인(64B)에 있을 때, 한 코어가 자기 변수를 고치면 라인 전체가 무효화돼 다른 코어도 캐시 미스를 겪는 현상. 실제로 공유하지 않는데 성능이 떨어짐. 해결: `alignas(64)` 패딩으로 코어별 데이터를 다른 라인에 배치.

</details>

<details>
<summary><b>Q21. 분기 예측 실패가 왜 비싼가? 게임에서 어떻게 피하나?</b></summary>

파이프라인에 미리 넣은 명령어를 전부 플러시하고 다시 fetch해야 해서 파이프라인 깊이만큼(15~20사이클) 낭비. 예측 불가능한 분기가 많은 핫루프는 분기 없는 코드로 바꿈. 예) `if (v>0) sum+=v;` → `sum += (v>0)*v;`

</details>

<details>
<summary><b>Q22. 리틀 엔디언과 빅 엔디언 차이는?</b></summary>

- **리틀**: 최하위 바이트를 낮은 주소에(x86, ARM 기본). `0x12345678` → `78 56 34 12`.
- **빅**: 최상위 바이트를 낮은 주소에. 네트워크 바이트 오더.
네트워크 전송·파일 포맷·다른 플랫폼 세이브 호환 시 변환 필요(`htonl` 등).

</details>
