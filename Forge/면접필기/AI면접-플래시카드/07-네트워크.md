# 07. 네트워크 (18장)

[← 목차](README.md)

---

## 기초

<details>
<summary><b>Q1. OSI 7계층과 TCP/IP 4계층을 말해보세요.</b></summary>

OSI: 물리 → 데이터링크 → 네트워크(IP) → 전송(TCP/UDP) → 세션 → 표현 → 응용.
TCP/IP: 네트워크 액세스 → 인터넷 → 전송 → 응용. 게임 프로그래머는 전송 계층(TCP/UDP)과 응용 계층(자체 프로토콜)을 주로 다룸.

</details>

<details>
<summary><b>Q2. 소켓이란? IP와 포트의 역할은?</b></summary>

OS가 제공하는 통신 끝점. **IP**(어느 컴퓨터) + **포트**(그 컴퓨터의 어느 프로그램)로 식별. 스트림 소켓(TCP)과 데이터그램 소켓(UDP)이 있고, 만들 때 프로토콜이 정해짐.

</details>

<details>
<summary><b>Q3. TCP와 UDP의 차이는?</b></summary>

| | TCP | UDP |
|---|---|---|
| 연결 | 3-way handshake | 없음 |
| 신뢰성 | ACK+재전송으로 보장 | 없음 |
| 순서 | 보장 | 없음 |
| 혼잡/흐름 제어 | 있음 | 없음 |
| 헤더 | 20B | 8B |
| HOL Blocking | 있음 | 없음 |
| 용도 | 웹, 로그인, 채팅 | 실시간 게임, 음성 |

</details>

<details>
<summary><b>Q4. TCP 3-way handshake와 4-way 종료를 설명하세요.</b></summary>

연결: 클라 **SYN** → 서버 **SYN-ACK** → 클라 **ACK**. 3번인 이유는 양방향 각각 시퀀스 번호를 동기화·확인해야 해서.
종료: FIN → ACK → FIN → ACK. 양쪽이 각각 "더 보낼 것 없음"을 알리므로 4번. 먼저 닫는 쪽은 TIME_WAIT 유지.

</details>

<details>
<summary><b>Q5. TCP는 어떻게 신뢰성을 보장하나?</b></summary>

시퀀스 번호로 순서 추적, 수신 측이 ACK 응답, 일정 시간 안에 ACK 없으면 재전송. 흐름 제어(수신 윈도우)로 받는 쪽 버퍼 초과 방지, 혼잡 제어(slow start, AIMD)로 네트워크 과부하 시 속도 자동 감속.

</details>

## 게임 네트워크

<details>
<summary><b>Q6. 실시간 게임은 왜 UDP를 쓰나?</b></summary>

TCP의 **HOL Blocking** 때문. 패킷 하나가 손실되면 뒤에 이미 도착한 패킷도 재전송이 올 때까지 앱에 안 넘어가 끊김·입력 지연이 생김. 게임에서 33ms 전 위치는 이미 낡은 정보라 기다릴 가치가 없음. UDP는 막히지 않고 혼잡 제어도 없어 송신 타이밍을 직접 통제. 필요한 데이터만 골라 신뢰성을 직접 얹음.

</details>

<details>
<summary><b>Q7. HOL(Head-of-Line) Blocking이란?</b></summary>

줄 맨 앞이 막히면 뒤 전부 못 가는 현상. TCP는 순서 보장 약속 때문에 #5가 손실되면 #6~#8이 버퍼에 있어도 #5 재전송(RTT 1회 추가)까지 전달 보류. 그동안 화면이 멈춤.

</details>

<details>
<summary><b>Q8. UDP 위에 신뢰성을 얹는다는 게 무슨 뜻인가?</b></summary>

시퀀스 번호 + ACK/NAK + 재전송을 **앱(엔진)이 직접 구현**하되, 필요한 메시지에만 적용. 위치 업데이트는 다음 패킷이 곧 오니 불필요, "사망·아이템 획득"은 한 번 놓치면 치명적이라 필요. 언리얼에선 `Reliable`/`Unreliable` RPC로 노출.

</details>

<details>
<summary><b>Q9. 패킷 손실·재정렬·지터를 각각 설명하세요.</b></summary>

- **손실**: 라우터 혼잡·무선 간섭으로 사라짐. TCP는 재전송, UDP는 앱이 대응.
- **재정렬**: 경로가 달라 #1,#3,#2 순으로 도착. UDP는 시퀀스 번호를 직접 붙여야 함.
- **지터**: 도착 간격이 들쭉날쭉. 캐릭터가 끊기거나 순간이동하는 원인. 수신 측 **지터 버퍼**로 잠깐 모았다 일정 간격으로 소비.

</details>

<details>
<summary><b>Q10. RTT, 대역폭, MTU 각각 한 줄로.</b></summary>

- **RTT**: 왕복 시간 = 핑. 20~50ms 좋음, 100ms 넘으면 체감 렉. 편도 지연 ≈ RTT/2.
- **대역폭**: 초당 데이터량(도로 폭). 넓어도 거리가 멀면 RTT는 그대로 → "인터넷 빠른데 렉" 원인은 대역폭이 아니라 RTT·손실.
- **MTU**: 한 패킷 최대 크기, 이더넷 1500B. 넘으면 IP 단편화되고 조각 하나만 잃어도 전체 폐기. UDP 페이로드 실용 상한 약 1472B.

</details>

<details>
<summary><b>Q11. 서버 권위(Server-Authoritative) 모델이란?</b></summary>

서버 1대만 진짜 게임 상태를 갖고, 클라는 그 복사본을 보며 입력만 보냄. 클라가 자기 HP를 바꿔도 다음 동기화에 서버 값으로 덮어써짐. 치트 방지·일관성의 기본. 대신 입력 반응이 RTT만큼 늦어지는 문제 → 클라 예측으로 해결.

</details>

<details>
<summary><b>Q12. 클라이언트 예측과 서버 보정(rollback)을 설명하세요.</b></summary>

1. 클라가 입력 즉시 로컬에서 이동을 계산해 화면에 반영하고, 그 무브를 저장(SavedMoves).
2. 같은 입력을 서버에 보냄(UE는 unreliable ServerMove).
3. 서버가 진짜 위치를 계산. 일치하면 ACK, 다르면 "진짜 위치는 여기" 전송.
4. 클라는 서버 위치로 되감고 저장된 이후 입력들을 다시 적용(replay).
틀렸을 때만 보정하므로 평소엔 즉각 반응.

</details>

<details>
<summary><b>Q13. 보간과 외삽 차이는? 남의 캐릭터를 어떻게 그리나?</b></summary>

남의 캐릭터(Simulated Proxy)는 서버 업데이트(예: 30Hz)만 받아 화면 주사율(60~240Hz)보다 드문드문 옴.
- **보간**: 받은 과거 두 위치 사이를 부드럽게 채움. 약간 과거를 보지만 매끄러움.
- **외삽**: 마지막 속도로 다음 위치 추정. 빗나가면 튐.
UE는 `NetworkSmoothingMode`(Linear/Exponential)로 받은 위치에 수렴시키는 보간을 씀.

</details>

<details>
<summary><b>Q14. Lag Compensation이란?</b></summary>

내 화면 속 적은 핑만큼 과거 위치라 "분명 맞췄는데 안 맞음"이 생김. 서버가 각 캐릭터의 과거 위치 히스토리를 들고 있다가, 클라가 보고한 발사 시각으로 **되감아** 그때 자리에서 명중 판정. UE5는 이걸 엔진 표준으로 제공하지 않아 직접 구현하거나 플러그인 사용.

</details>

<details>
<summary><b>Q15. 언리얼 네트워킹 3층 구조(NetDriver/Connection/Channel)는?</b></summary>

- **UNetDriver**: 월드당 1개, 전체 송수신·리플리케이션 tick.
- **UNetConnection**: 상대 머신 1대와의 연결. 서버는 클라 수만큼.
- **UChannel**: 연결 안의 데이터 경로. Control(접속), Actor(복제 액터당 1개), Voice.
Packet은 실제 UDP 전송 단위(헤더 + 여러 bunch), **Bunch**는 액터 하나의 변경·RPC 묶음.

</details>

<details>
<summary><b>Q16. Reliable RPC를 남발하면 왜 위험한가?</b></summary>

Reliable은 ACK 올 때까지 송신 측이 보관하고 재전송하며, 앞 RPC가 ACK될 때까지 뒤 실행이 대기. 매 Tick 호출하면 미확인 버퍼(기본 256)가 넘쳐 **연결이 끊김**. 이동·이펙트는 Unreliable, 사망·매치 종료 같은 1회성만 Reliable.

</details>

<details>
<summary><b>Q17. Relevancy(관련성)와 Ownership은?</b></summary>

- **Relevancy**: 서버는 모든 액터를 모든 클라에 보내지 않음. `bAlwaysRelevant`, 소유 관계, `NetCullDistanceSquared`(거리)로 클라별 전송 대상 결정 → 대역폭 절약.
- **Ownership**: Server RPC는 그 액터를 **소유한 클라**만 호출 가능. Owner 체인 끝의 PlayerController가 NetConnection을 가져야 라우팅됨. 소유 안 된 액터에서 부르면 무시.

</details>

<details>
<summary><b>Q18. 게임 서버 구조: 데디케이티드 vs 리슨 vs P2P?</b></summary>

- **데디케이티드**: 렌더링 없는 전용 서버 프로세스. 공정·안정, 비용 발생. 경쟁 게임 표준.
- **리슨**: 플레이어 한 명이 서버 겸 클라. 비용 없지만 호스트 이점·호스트 이탈 문제.
- **P2P**: 서버 없이 서로 교환. 격투 게임의 롤백 넷코드(입력만 교환, 결정론적 시뮬레이션)에 사용. 치트에 취약.

</details>
