## A. 얕은 복사 / 깊은 복사

**정의.** 얕은 복사는 멤버 값을 그대로 복사(포인터면 주소만). 깊은 복사는 포인터가 가리키는 대상까지 새로 할당해 복사.

**왜 문제인가.** 컴파일러가 자동으로 만드는 복사 생성자는 얕은 복사다. 자원을 직접 소유하는 클래스에서 이걸 그대로 쓰면:

```cpp
struct Buf { int* p; Buf(){ p = new int[10]; } ~Buf(){ delete[] p; } };
Buf a;
Buf b = a;      // 얕은 복사: b.p == a.p
// 스코프 끝 → a 소멸자 delete[] p, b 소멸자 delete[] p → 이중 해제, 크래시
```

**해결 2가지.**
1. 복사 생성자·복사 대입·소멸자를 직접 작성(Rule of 3; 이동까지 하면 Rule of 5).
2. raw 포인터 대신 `std::vector`, `unique_ptr`를 멤버로 → 자동 생성 함수가 알아서 옳게 동작(Rule of Zero). 현대 C++ 기본.

**면접 한 줄.** "얕은 복사는 포인터만 복사해 두 객체가 같은 메모리를 가리키므로 이중 해제가 납니다. 자원을 소유하면 깊은 복사를 직접 쓰거나, 그보다 vector·unique_ptr에 맡겨 복사 문제 자체를 없앱니다."

## B. volatile

**정의.** "이 변수는 프로그램 밖(하드웨어, 시그널 핸들러, 다른 스레드)에서 바뀔 수 있으니, 컴파일러는 값을 레지스터에 캐시하거나 읽기를 생략하지 말고 **매번 메모리에서 읽고 써라**."

**왜 필요한가.** 컴파일러는 루프 안에서 변하지 않는다고 본 변수를 최적화한다.

```cpp
bool done = false;
while (!done) { }     // 컴파일러: done은 루프 안에서 안 바뀜 → while(true)로 바꿔버릴 수 있음
volatile bool done;   // 매번 메모리 확인 → 밖에서 true로 바꾸면 빠져나옴
```

**함정(면접 포인트).** volatile은 **스레드 동기화 도구가 아니다.** 원자성(반쯤 쓰인 값을 읽을 수 있음)도, 순서 보장(다른 변수와의 순서가 재배치될 수 있음)도 없다. 멀티스레드 플래그는 `std::atomic<bool>`, 데이터 공유는 뮤텍스.

**면접 한 줄.** "volatile은 컴파일러 최적화를 막아 매번 메모리를 읽게 하는 키워드이고, 하드웨어 레지스터 같은 데 씁니다. 스레드 동기화에는 원자성과 순서 보장이 없어서 atomic이나 뮤텍스를 써야 합니다."

## C. shared_ptr 구조와 weak_ptr

**구조.** shared_ptr 하나 = 포인터 2개(객체 주소, 컨트롤 블록 주소). 컨트롤 블록은 힙에 1개, 같은 객체를 가리키는 모든 shared/weak가 공유.

```
shared_ptr A ──┐
shared_ptr B ──┼──▶ [컨트롤 블록: strong=2, weak=1, deleter] ──▶ [객체]
weak_ptr   W ──┘
```

| 동작 | 카운트 변화 |
|---|---|
| shared_ptr 복사 | strong +1 (원자적) |
| shared_ptr 소멸 | strong -1. **0이 되면 객체 delete** |
| weak_ptr 생성 | weak +1. 객체 수명엔 영향 없음 |
| weak_ptr 소멸 | weak -1. strong·weak 둘 다 0이면 **컨트롤 블록 delete** |
| `weak.lock()` | strong > 0이면 shared_ptr 반환(strong +1), 아니면 빈 포인터 |

**왜 카운트 증감이 원자적인가.** 여러 스레드가 같은 객체의 shared_ptr을 복사·소멸할 수 있으므로 `++`가 레이스 없이 정확해야 한다. 그래서 unique_ptr보다 복사 비용이 있다.

**순환 참조.** A→B, B→A를 둘 다 shared_ptr로 들면 strong이 1 밑으로 안 내려가 둘 다 영원히 삭제 안 됨. 한쪽(보통 자식→부모, 관찰자)을 weak_ptr로.

```cpp
struct Node { shared_ptr<Node> next; weak_ptr<Node> prev; };   // 양방향 리스트의 전형
```

**make_shared.** `shared_ptr<T>(new T)`는 객체·블록을 따로 2회 할당. `make_shared<T>()`는 둘을 한 덩어리로 1회 할당 → 빠르고 캐시 친화. 또한 `f(shared_ptr<T>(new T), g())`에서 g()가 예외를 던지면 new T가 누수될 수 있는 문제도 없앰.

**면접 한 줄.** "shared_ptr은 컨트롤 블록의 강한 카운트로 객체 수명을, 약한 카운트로 블록 수명을 관리합니다. weak_ptr은 소유하지 않고 살아있는지만 확인하는 포인터라 순환 참조를 끊는 데 씁니다."

## D. lvalue / rvalue / std::move / 이동 시맨틱

**정의.**
- **lvalue**: 이름이 있고 주소를 취할 수 있으며 문장이 끝나도 살아있는 것. `x`, `arr[i]`, `*p`.
- **rvalue**: 문장이 끝나면 사라지는 임시값. `x + y`, `f()`의 반환값, `5`, `std::string("a")`.
- 구분 기준은 "주소가 있냐"보다 **"이 값이 곧 사라지는가"**. 곧 사라지는 값이면 그 안의 자원을 훔쳐도 안전하다.

**std::move의 정체.** 아무것도 옮기지 않는다. `static_cast<T&&>(x)` 로 **lvalue를 rvalue로 취급하겠다고 표시**만 한다. 그 표시를 보고 컴파일러가 복사 생성자 대신 **이동 생성자**를 고르고, 실제로 훔치는 일은 이동 생성자가 한다.

```cpp
class Str {
    char* p; size_t n;
    Str(const Str& o) : n(o.n) { p = new char[n]; memcpy(p, o.p, n); }   // 복사: 할당 + 복사
    Str(Str&& o) noexcept : p(o.p), n(o.n) { o.p = nullptr; o.n = 0; }   // 이동: 포인터만 가져오고 원본 비움
};
Str a("hello");
Str b = a;               // 복사 생성자
Str c = std::move(a);    // 이동 생성자. a는 비어 있음(유효하지만 값은 미지정)
```

**왜 빠른가.** 복사는 힙 할당 + 바이트 복사. 이동은 포인터 3개 대입. **힙 할당이 사라지는 것**이 속도의 실체다. `vector<string>`이 커질 때 재할당하면서 문자열 1만 개를 옮긴다고 하면, 복사면 힙 할당 1만 번, 이동이면 0번.

**어디서 자동으로 일어나나.** 함수 반환값, 임시 객체를 넣을 때(`v.push_back(std::string("a"))`), `std::move`로 명시할 때. `noexcept`가 붙어야 vector 재할당 시 이동을 선택한다(예외 안전 보장 때문).

**함정.** `return std::move(local);`은 RVO를 막아 오히려 손해. 지역 변수를 값으로 반환하면 그냥 `return local;`.

**면접 한 줄.** "std::move는 실제 이동이 아니라 rvalue 캐스팅이고, 이동은 이동 생성자가 포인터 소유권만 넘겨받는 방식으로 일어납니다. 깊은 복사와 힙 할당이 사라져서 빠릅니다."

## E. 캐스팅 4종

| 캐스트 | 시점 | 하는 일 | 검사 | 쓰는 곳 |
|---|---|---|---|---|
| `static_cast` | 컴파일 | **관련 있는 타입** 간 변환. 숫자 간, void*↔T*, 상속 관계 업/다운캐스트 | 관계 없으면 컴파일 에러. 다운캐스트는 **실제 타입 검사 없음** | 기본 선택 |
| `dynamic_cast` | 런타임 | 다형 타입(가상함수 있음)의 다운/사이드캐스트. RTTI로 실제 타입 확인 | 실패 시 포인터 nullptr, 참조는 예외 | "이 Actor가 Enemy인가?" 안전 확인. 느림 |
| `reinterpret_cast` | 컴파일 | **비트를 그대로** 다른 타입으로 해석. 포인터↔정수, 무관한 포인터끼리 | 없음. 이식성 없음 | 직렬화, 메모리 덤프, 하드웨어 주소. 거의 안 씀 |
| `const_cast` | 컴파일 | const/volatile 제거·추가 | 원래 const 객체를 수정하면 UB | 레거시 API에 넘길 때 |

```cpp
Base* b = new Derived;
Derived* d1 = static_cast<Derived*>(b);    // 빠름. b가 진짜 Derived일 때만 안전
Derived* d2 = dynamic_cast<Derived*>(b);   // 아니면 nullptr. 안전하지만 느림
int addr = reinterpret_cast<intptr_t>(b);  // 주소를 정수로
```

**C 스타일 `(T)x`를 피하는 이유.** 위 넷 중 뭘 하는지 안 보이고, 상황에 따라 reinterpret까지 조용히 해버린다. 검색도 안 됨.

**UE 연결.** `Cast<T>()`는 dynamic_cast 대신 UE 리플렉션으로 타입을 확인하는 UE판 dynamic_cast. 더 빠르고 UObject 전용.

**면접 한 줄.** "static_cast는 컴파일 타임에 관련 타입끼리, dynamic_cast는 런타임에 실제 타입을 검사해서 실패하면 nullptr, reinterpret_cast는 비트 재해석이라 저수준 전용, const_cast는 const 제거입니다. C 캐스트는 의도가 안 보여서 안 씁니다."

## F. 프로세스 vs 스레드 (반대로 말했던 것)

```
프로세스 A                          프로세스 B
┌──────────────────────┐            ┌──────────────────┐
│ 코드 │ 데이터 │ 힙    │  ← 공유 X →│ 코드│데이터│힙   │
│ 스레드1 스택 │ 스레드2 스택 │       │ 스레드1 스택     │
└──────────────────────┘            └──────────────────┘
   ↑ 같은 프로세스의 스레드끼리는 코드·데이터·힙 공유, 스택·레지스터만 각자
```

| | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | 전부 독립(주소공간 분리) | 코드·데이터·힙 **공유**, 스택·레지스터·PC만 독립 |
| 통신 | IPC 필요(파이프, 공유메모리, 소켓) | 그냥 변수 읽기(대신 동기화 필요) |
| 생성·전환 비용 | 큼(주소공간, TLB 플러시) | 작음 |
| 하나가 죽으면 | 다른 프로세스 무관 | 프로세스 전체 사망 |
| 게임 예 | 런처↔게임, 에디터↔셰이더 워커 | 게임/렌더/오디오/로딩 스레드 |

**IPC(Inter-Process Communication).** 프로세스는 서로 메모리를 못 보니 OS가 주는 통로로 통신하는 것. 파이프(한 방향 바이트 흐름), 공유 메모리(OS가 같은 물리 페이지를 양쪽에 매핑, 가장 빠름), 소켓(네트워크도 가능), 메시지 큐.

**면접 한 줄.** "스레드는 한 프로세스 안에서 코드·데이터·힙을 공유하고 스택만 따로 갖는 실행 흐름이라 통신이 빠르지만 하나가 죽으면 전체가 죽습니다. 프로세스는 주소공간이 완전히 분리돼 격리되지만 IPC가 필요하고 전환 비용이 큽니다."

## G. 컨텍스트 스위칭 시간 측정

**문제의 의도.** 정답 수치가 아니라 "측정 불가능해 보이는 걸 어떻게 실험 설계하나"를 본다.

**설계.**
1. 프로세스(또는 스레드) 2개를 파이프 2개로 연결.
2. A가 1바이트를 보내고 B의 답을 기다림(블록). B는 받으면 바로 1바이트 답장. → 왕복 1회마다 A→B, B→A 컨텍스트 스위칭이 **강제로 2번** 일어남.
3. 왕복을 N=100만 번 반복해 총 시간 T 측정. 스위칭 1회 ≈ T / (2N).
4. 정확도 높이기: 두 프로세스를 **같은 코어에 고정**(affinity, 안 그러면 병렬로 돌아 스위칭이 안 일어남), 파이프 자체 비용은 같은 프로세스 안에서 파이프만 왕복시켜 빼기.

**면접 한 줄.** "두 프로세스가 파이프로 핑퐁하게 만들어 스위칭을 강제하고, 수십만 번 반복한 총 시간을 횟수로 나눕니다. 같은 코어에 고정하고 파이프 오버헤드는 따로 재서 뺍니다."

## H. 데드락 4조건 (문제 목록과 섞었던 것)

**정의.** 둘 이상이 서로가 가진 자원을 기다리며 영원히 멈춤.

**4조건 — 상점비순.** 넷이 **동시에** 성립해야만 발생. 하나만 깨면 데드락 불가.

| 조건 | 뜻 | 깨는 법 |
|---|---|---|
| **상**호배제 | 자원을 한 번에 하나만 사용 | 자원 자체를 공유 가능하게(현실적으로 어려움) |
| **점**유대기 | 하나 쥔 채로 다른 걸 기다림 | 필요한 락을 한 번에 전부 획득(`std::lock(a, b)`) |
| **비**선점 | 남이 쥔 걸 강제로 못 뺏음 | 못 얻으면 쥔 것도 놓기(`try_lock` 후 back-off) |
| **순**환대기 | A→B→A 원형 | **락 순서 전역 고정** (실무 1순위 해법) |

```cpp
// 데드락: 스레드1은 a→b, 스레드2는 b→a 순으로 잠금
// 해결: 항상 a→b 순서로만 잠근다 (순환대기 제거)
std::lock(a, b);                        // 또는 둘을 원자적으로 동시에 획득
std::lock_guard<std::mutex> ga(a, std::adopt_lock), gb(b, std::adopt_lock);
```

**헷갈렸던 것 정리.** 기아(starvation)=우선순위 낮아 계속 밀림, 경쟁 상태(race)=순서에 따라 결과 달라짐, 스핀락=락 구현 방식. 전부 **데드락 조건이 아니라 별개 개념**.

**면접 한 줄.** "상호배제·점유대기·비선점·순환대기 넷이 다 있어야 데드락이 나므로 하나만 깨면 됩니다. 실무에선 락 획득 순서를 전역으로 고정해 순환대기를 없애는 게 가장 흔합니다."

## I. 식사하는 철학자

**설정.** 원탁에 철학자 5명, 사이사이 젓가락 5개. 먹으려면 양쪽 젓가락 2개가 필요. 각자 "왼쪽 들고 → 오른쪽 들고 → 먹고 → 놓기".

**왜 데드락인가.** 5명이 동시에 왼쪽을 들면 젓가락 5개가 전부 한 개씩 점유됨. 모두 오른쪽(= 옆 사람의 왼쪽)을 기다림 → **순환대기** 완성. H의 4조건이 전부 보이는 교과서 예제.

**해결 3가지.**
1. **순서 깨기**: 한 명(또는 홀수 번호)만 오른쪽부터 들게 함 → 순환이 안 만들어짐. (H의 "락 순서 고정"과 같은 원리)
2. **동시 입장 제한**: 세마포어로 최대 4명만 식탁에 앉게 → 최소 한 명은 반드시 양쪽을 얻음.
3. **둘 다 못 잡으면 놓기**: 왼쪽 잡고 오른쪽이 없으면 왼쪽도 내려놓고 재시도(비선점 깨기). 단, 모두가 같은 타이밍에 반복하면 라이브락 가능.
