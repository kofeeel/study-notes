# 05. 그래픽스 (18장)

## 파이프라인 · 변환

<details>
<summary><b>Q1. 렌더링 파이프라인 단계를 순서대로 말해보세요.</b></summary>

IA(정점·인덱스 버퍼 조립) → **VS**(정점 변환) → [테셀레이션] → [지오메트리 셰이더] → **래스터라이저**(삼각형 → 픽셀 조각) → **PS**(픽셀 색 계산) → OM(깊이/스텐실 테스트, 블렌딩) → 프레임버퍼.
VS는 정점 수만큼, PS는 픽셀 수만큼 실행되므로 보통 PS가 병목.

</details>

<details>
<summary><b>Q2. MVP 변환(좌표계 변환)을 설명하세요.</b></summary>

Local → (**M**odel) → World → (**V**iew) → View/Camera → (**P**rojection) → Clip → (w로 나눔, perspective divide) → NDC(-1~1) → (뷰포트) → Screen.
`clip = P × V × M × v`. 오른쪽부터 적용되므로 곱 순서는 P·V·M. 모델 행렬은 스케일 → 회전 → 이동 순(TRS).

</details>

<details>
<summary><b>Q3. 원근 투영과 직교 투영 차이는?</b></summary>

- **원근**: 멀수록 작게. w에 깊이를 넣어 나눔. 3D 게임 카메라.
- **직교**: 거리와 무관하게 같은 크기. UI, 2D, 그림자맵(방향광), 에디터 뷰.

</details>

<details>
<summary><b>Q4. 깊이 버퍼(Z-buffer)와 Z-Fighting은?</b></summary>

픽셀마다 가장 가까운 깊이를 저장해 뒤에 있는 것을 버림(가시성 판정). Z-Fighting은 깊이 정밀도 부족으로 겹친 면이 번갈아 그려져 깜빡이는 것. 해결: near plane을 멀리(정밀도는 near에 민감), 폴리곤 오프셋, reverse-Z/로그 깊이.

</details>

<details>
<summary><b>Q5. 무게중심 좌표(Barycentric)는 어디에 쓰나?</b></summary>

삼각형 안의 점 P = αA + βB + γC (α+β+γ=1). 래스터라이저가 이걸로 정점 속성(UV, 색, 법선)을 **보간**해 픽셀 셰이더에 넘김. 셋 다 0 이상이면 삼각형 내부 판정. 레이-삼각형 교차에도 사용.

</details>

## 셰이딩 · 라이팅

<details>
<summary><b>Q6. 정점 셰이더와 픽셀 셰이더의 역할은?</b></summary>

- **VS**: 정점 하나당 실행. 위치 변환(MVP), 스키닝, 법선 변환, UV 전달.
- **PS**: 래스터라이즈된 조각 하나당 실행. 텍스처 샘플링, 라이팅, 최종 색.
비싼 계산은 가능하면 VS(적게 실행)로 올리거나 사전 계산.

</details>

<details>
<summary><b>Q7. 포워드 렌더링과 디퍼드 렌더링 차이는?</b></summary>

- **포워드**: 오브젝트마다 라이팅까지 한 번에. 조명 수 × 오브젝트 수로 비용 증가, 반투명·MSAA 쉬움. 모바일·VR.
- **디퍼드**: 먼저 GBuffer(알베도, 법선, 깊이, 러프니스 등)에 기록 후, 화면 공간에서 라이팅 한 번. 조명 많아도 비용 일정. 반투명·MSAA 어려움, 메모리 대역폭 큼. UE5 데스크탑 기본.

</details>

<details>
<summary><b>Q8. PBR이란? 입력 텍스처는?</b></summary>

물리 기반 렌더링. 에너지 보존과 미세표면 이론(BRDF)에 따라 조명을 계산해 어떤 조명 환경에서도 일관된 재질을 얻음. 입력: Albedo(BaseColor), Metallic, Roughness, Normal, AO. 기존 퐁 모델의 "스페큘러 파워"보다 아티스트 파라미터가 물리적 의미를 가짐.

</details>

<details>
<summary><b>Q9. 노멀 맵은 어떻게 디테일을 만드나?</b></summary>

표면 법선 방향을 텍스처에 저장(탄젠트 공간, RGB = XYZ). 픽셀 셰이더에서 그 법선으로 라이팅을 계산하니 폴리곤을 늘리지 않고 요철이 보임. 실루엣은 안 바뀜(그건 디스플레이스먼트/테셀레이션).

</details>

<details>
<summary><b>Q10. 그림자 맵의 원리는?</b></summary>

광원 시점에서 깊이를 렌더링해 텍스처로 저장. 카메라 시점에서 각 픽셀을 광원 공간으로 변환해 저장된 깊이보다 멀면 그림자. 문제: 해상도 부족(계단), acne(자기 그림자 → bias), 넓은 장면 → 캐스케이드(CSM).

</details>

## 최적화 · 텍스처

<details>
<summary><b>Q11. 드로우콜이란? 줄이는 방법은?</b></summary>

CPU가 GPU에 "이 메시를 이 재질로 그려라" 명령 한 번. 드라이버 오버헤드가 CPU 병목이 됨. 줄이기: **배칭**(같은 재질 합치기), **인스턴싱**(같은 메시를 한 콜에 N개), 텍스처 아틀라스, 컬링, LOD.

</details>

<details>
<summary><b>Q12. 컬링 종류를 말해보세요.</b></summary>

- **Frustum Culling**: 카메라 절두체 밖 오브젝트 제외.
- **Occlusion Culling**: 다른 물체에 완전히 가려진 것 제외(HZB, 쿼리).
- **Backface Culling**: 카메라를 등진 삼각형 제외(래스터 단계).
- 거리 컬링/LOD: 멀면 안 그리거나 저폴리로.

</details>

<details>
<summary><b>Q13. Overdraw란? 줄이는 방법은?</b></summary>

같은 픽셀이 여러 번 칠해지는 것. PS 비용 낭비, 모바일에서 특히 치명적. 대응: 불투명은 앞→뒤 정렬(Early-Z로 뒤쪽 PS 스킵), **Z-prepass**(깊이만 먼저 그리고 색은 보이는 것만), 반투명·큰 파티클 최소화.

</details>

<details>
<summary><b>Q14. 밉맵이란? 왜 쓰나?</b></summary>

텍스처를 1/2씩 축소한 피라미드를 미리 만들어 거리에 따라 적절한 레벨을 샘플링. 이점: 멀리서 고해상도 텍스처를 샘플할 때 생기는 **모아레/반짝임 제거**(에일리어싱), 캐시 효율 향상. 메모리 +33%.

</details>

<details>
<summary><b>Q15. 안티에일리어싱 종류 비교.</b></summary>

- **MSAA**: 픽셀당 여러 샘플로 커버리지 계산, 셰이딩은 1회. 품질 좋지만 디퍼드와 궁합 나쁨, 메모리 큼.
- **FXAA**: 후처리로 엣지 블러. 싸지만 흐릿.
- **TAA**: 이전 프레임을 재투영해 누적. 싸고 품질 좋지만 고스팅·흐림. UE 기본.

</details>

<details>
<summary><b>Q16. 텍스처 압축을 왜 하나? 포맷은?</b></summary>

GPU 메모리와 대역폭 절약, 그대로 샘플링 가능(블록 압축). PC: BC1~BC7(DXT), 모바일: ETC2, **ASTC**(가변 블록, 품질 좋음). 노멀맵은 BC5, HDR은 BC6H처럼 용도별 선택.

</details>

## 모바일 GPU

<details>
<summary><b>Q17. TBR과 IMR 차이, 모바일이 TBR인 이유는?</b></summary>

- **IMR**(데스크탑): 삼각형이 오는 대로 프레임버퍼에 바로 씀. 대역폭 많이 씀.
- **TBR**(모바일): 화면을 타일(16×16 등)로 나눠 타일별로 온칩 메모리에서 렌더 후 한 번에 씀. 메모리 대역폭이 전력·성능 병목인 모바일에 유리. 대신 정점 단계에서 비닝 비용.
- **TBDR**(Apple, PowerVR): 타일 안에서 가려진 픽셀을 먼저 제거(HSR)해 오버드로 제거.

</details>

<details>
<summary><b>Q18. DX12 / Vulkan / Metal의 공통 특징은?</b></summary>

저수준 API: 명시적 동기화·메모리 관리, 멀티스레드 커맨드 기록, 드라이버 오버헤드 감소. DX12=Windows/Xbox, Vulkan=크로스플랫폼(Android·Switch), Metal=Apple. 대신 DX11/OpenGL보다 코드 책임이 훨씬 큼.

</details>
