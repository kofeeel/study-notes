## 오브젝트 · 리플렉션 · GC

<details>
<summary><b>Q1. UObject 메모리는 어떻게 관리되나?</b></summary>

참조 카운팅이 아니라 **가비지 컬렉션(mark & sweep)**. 루트 세트에서 `UPROPERTY` 포인터를 따라 도달 가능한 오브젝트만 살리고 나머지를 주기적으로 수거. 비-UObject(구조체, 일반 클래스)는 `TSharedPtr`/`TUniquePtr`로 관리.

</details>

<details>
<summary><b>Q2. UPROPERTY를 안 붙인 UObject 포인터는 어떻게 되나?</b></summary>

GC가 그 참조를 **못 보므로** 다른 참조가 없으면 오브젝트가 수거(파괴)되고, C++ 포인터는 남아 **댕글링 → 크래시**. "무시되는" 게 아니라 "지워진다". 해결: `UPROPERTY()`, UE5 권장 `TObjectPtr<>`, 특수 케이스는 `AddToRoot()`. TArray 원소도 동일.

</details>

<details>
<summary><b>Q3. UE 리플렉션 시스템이란? C++ RTTI와 차이는?</b></summary>

UHT(Unreal Header Tool)가 `UCLASS/UPROPERTY/UFUNCTION` 매크로를 파싱해 `.generated.h`를 만들고 클래스·프로퍼티·함수 메타데이터를 런타임에 제공. RTTI는 타입명·상속만 알지만 UE 리플렉션은 프로퍼티 이름/타입/값, 함수 목록, 메타데이터까지 → 에디터 디테일 패널, 블루프린트 노출, 직렬화, 리플리케이션, GC가 전부 여기에 의존. `Cast<T>()`는 이걸 이용해 `dynamic_cast`보다 빠르고 안전.

</details>

<details>
<summary><b>Q4. GENERATED_BODY()는 뭘 하나?</b></summary>

UHT가 생성한 코드를 그 자리에 삽입하는 매크로. `StaticClass()`, `Super` typedef, 직렬화·리플리케이션 함수, CDO 초기화 코드, 리플렉션 등록. 없으면 UObject 기능이 동작 안 함.

</details>

<details>
<summary><b>Q5. CDO(Class Default Object)란?</b></summary>

클래스 로드 시 자동 생성되는 기본 인스턴스. 에디터 디테일 패널의 기본값의 실체이며, 스폰 시 CDO에서 값을 복사해 새 인스턴스를 만듦. 생성자에서 설정한 값이 CDO에 박힘. 생성자는 CDO 생성에도 호출되므로 게임 로직을 넣으면 안 됨.

</details>

<details>
<summary><b>Q6. 액터 생성 순서(생성자 → BeginPlay)는?</b></summary>

Spawn → **생성자**(컴포넌트 생성, 기본값. 가상함수·월드 접근 X) → `PostInitializeComponents`(컴포넌트 초기화 완료 후) → **BeginPlay**(월드에 등록된 후 게임 로직 시작). 다른 액터 참조나 GetWorld는 BeginPlay 이후가 안전.

</details>

<details>
<summary><b>Q7. Hard Reference와 Soft Reference 차이는?</b></summary>

- **Hard**(`UPROPERTY() UTexture* T` 또는 `TSubclassOf`): 이 에셋이 로드되면 참조 대상도 **함께 로드**. 의존성 체인이 커지면 로딩 시간·메모리 폭발.
- **Soft**(`TSoftObjectPtr`, `FSoftObjectPath`): 경로만 들고 있다가 필요할 때 비동기 로드(`StreamableManager`). 캐릭터 → 모든 스킨 같은 관계에 사용.

</details>

## 게임 프레임워크

<details>
<summary><b>Q8. GameMode / GameState / PlayerController / PlayerState / Pawn 역할과 수명은?</b></summary>

- **GameInstance**: 앱 시작~종료. 레벨 넘어도 유지(세이브, 옵션). 로컬.
- **GameMode**: 레벨 단위. **서버에만** 존재. 규칙, 리스폰(`RestartPlayer`).
- **GameState**: 레벨 단위. 서버+모든 클라. 게임 전체 상태(웨이브, 시간).
- **PlayerController**: 접속~종료. Pawn이 죽어도 **살아남음**. 입력·카메라.
- **PlayerState**: 접속~종료, 모두에게 복제. Pawn 죽어도 유지할 데이터(점수, 킬).
- **Pawn/Character**: 스폰~Destroy. 현재 HP·콤보 같은 "몸" 데이터.

</details>

<details>
<summary><b>Q9. 데이터를 어디에 둘지 결정하는 기준은?</b></summary>

레벨 넘어 유지? → GameInstance. 플레이어별인데 죽어도 유지? → PlayerState, 아니면 Pawn. 게임 규칙? → GameMode(서버). 모두가 봐야 하는 게임 상태? → GameState.

</details>

<details>
<summary><b>Q10. Actor와 Component 차이는?</b></summary>

Actor는 월드에 배치되는 단위(Transform 소유, 스폰/파괴, 리플리케이션 1급 시민). Component는 Actor에 붙어 기능을 조립(메시, 콜리전, 무브먼트, 커스텀 로직). "상속 대신 컴포지션"이 UE 설계 기본. SceneComponent는 Transform이 있고 ActorComponent는 없음.

</details>

<details>
<summary><b>Q11. Tick 비용을 줄이는 방법은?</b></summary>

`PrimaryActorTick.bCanEverTick=false`로 필요 없는 Tick 끄기, Tick 간격 조절(`SetActorTickInterval`), 타이머/델리게이트로 이벤트 기반 전환, 멀리 있는 액터는 Significance/Tick 비활성. Tick이 수천 개면 CPU 게임 스레드 병목.

</details>

## 네트워크 · GAS

<details>
<summary><b>Q12. 프로퍼티 리플리케이션과 RPC는 언제 각각 쓰나?</b></summary>

지속 **상태**(HP, 위치, 팀)는 `UPROPERTY(Replicated)` — 값이 바뀔 때만 전송되고 늦게 접속한 클라도 현재 값을 받음. 일회성 **이벤트**(발사, 폭발음)는 RPC — 그 순간만 의미. 직관: "나중 접속자가 알아야 하면 프로퍼티, 순간이면 RPC".

</details>

<details>
<summary><b>Q13. Server / Client / NetMulticast RPC 차이는?</b></summary>

- **Server**: 소유 클라가 호출 → 서버에서 실행. `WithValidation`으로 치트 검증(실패 시 강제 접속 종료).
- **Client**: 서버가 호출 → 그 액터의 소유 클라 1명에서 실행.
- **NetMulticast**: 서버가 호출 → 서버 + 관련 있는 모든 클라. 클라가 부르면 로컬만 실행.
기본은 Unreliable. 놓치면 안 되는 것만 `Reliable`.

</details>

<details>
<summary><b>Q14. 리플리케이션 설정 시 흔한 실수는?</b></summary>

① `bReplicates = true` 안 켬 ② `GetLifetimeReplicatedProps`에 `DOREPLIFETIME` 등록 안 함(컴파일은 통과) ③ `Super::GetLifetimeReplicatedProps` 누락(부모 프로퍼티 복제 안 됨) ④ 클라에서 `HasAuthority()` 게이트 없이 상태 변경(서버 값으로 덮어써짐) ⑤ 매 프레임 Reliable RPC(큐 넘쳐 접속 끊김).

</details>

<details>
<summary><b>Q15. OnRep(RepNotify)은 언제 호출되나?</b></summary>

`UPROPERTY(ReplicatedUsing=OnRep_Health)`로 등록하면 서버가 보낸 값이 **클라에서** 갱신될 때 자동 호출(UI 갱신 등 연출). 서버 자신은 기본적으로 안 불리므로 서버에도 같은 처리가 필요하면 값 변경 직후 직접 호출.

</details>

<details>
<summary><b>Q16. GAS의 핵심 구성요소는?</b></summary>

- **ASC**(AbilitySystemComponent): 어빌리티·이펙트·어트리뷰트를 관리하는 허브.
- **GameplayAbility**(GA): 스킬 로직(활성화 조건, 코스트, 쿨다운).
- **GameplayEffect**(GE): 어트리뷰트를 바꾸는 데이터(즉시/지속/주기). 데미지·버프.
- **AttributeSet**: HP, 공격력 같은 수치.
- **GameplayTag**: 상태·분류의 계층적 이름표. **GameplayCue**: 비주얼/사운드 분리.
장점: 데이터 주도, 네트워크 예측 내장, 디자이너가 BP로 조합.

</details>

<details>
<summary><b>Q17. 메타 어트리뷰트(IncomingDamage)를 왜 쓰나?</b></summary>

Health는 영속 값이지만 IncomingDamage는 데미지가 들어올 때만 채웠다 즉시 비우는 **1회용 통로**. 데미지의 단일 진입점을 만들어 `PostGameplayEffectExecute` 한 곳에서 패링 → 방어 → 경감 → 사망을 순서대로 처리. (ProjectKD에서 실제 사용.)

</details>

## 애니메이션 · 전투 · AI

<details>
<summary><b>Q18. 애님 몽타주와 애님 노티파이는?</b></summary>

몽타주: 애님 그래프 밖에서 코드로 재생하는 애니메이션 묶음(섹션, 슬롯). 공격·스킬 같은 일회성 동작. 노티파이: 몽타주/시퀀스의 특정 프레임(또는 구간, NotifyState)에 이벤트 발생 → 히트 판정 창, 발소리, 콤보 입력 창을 애니 타이밍에 정확히 맞춤.

</details>

<details>
<summary><b>Q19. 히트스탑을 어떻게 구현하나?</b></summary>

`AActor::CustomTimeDilation`을 때린 쪽·맞은 쪽 둘 다 0.05 수준으로 낮추고 2~4프레임(약공 0.033s, 강공 0.067s) 후 타이머로 1.0 복구. 글로벌 타임 딜레이션은 파티클·UI·물리까지 멈춰 버그처럼 보이므로 대형 순간(처형, 완벽 패링)에만. 트리거는 AnimNotify 히트 윈도우에서.

</details>

<details>
<summary><b>Q20. Motion Warping이란?</b></summary>

몽타주의 **루트모션** 이동·회전을 지정 타겟으로 보정해 공격이 상대에 정확히 닿게 하는 기능. 인플레이스 애니는 이동량이 0이라 워프 불가. Min/Max 거리 게이트로 너무 가깝거나 멀면 원본 재생.

</details>

<details>
<summary><b>Q21. Behavior Tree와 Blackboard, EQS의 관계는?</b></summary>

- **Blackboard**: AI의 메모리(타겟, 목적지 같은 키-값).
- **BT**: Selector/Sequence/Decorator/Service/Task로 의사결정. Blackboard 값을 읽고 씀.
- **EQS**: 환경 질의. Generator(후보 지점) → Test(Filter로 탈락, Score로 점수) → 최고점 반환. 카이팅 위치, 엄폐 찾기를 선언적으로 디자이너가 튜닝.

</details>

<details>
<summary><b>Q22. Enhanced Input 구조는?</b></summary>

**InputAction**(IA: "점프"라는 추상 행동, 값 타입) + **InputMappingContext**(IMC: 키 → IA 매핑, 우선순위)를 분리. 컨텍스트를 상황(전투/메뉴/탈것)에 따라 추가·제거해 키 충돌 관리. Modifier/Trigger로 데드존, 홀드, 탭을 데이터로 처리.

</details>
